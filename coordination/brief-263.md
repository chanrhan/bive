## 해야 할 것 (수용 기준 순서)
1. **[문제만] 토글.** 지금 뜻이 없는 토글이다. 둘 중 하나로 정해 ADR-123에 적는다: (가) 뜻을 준다(예: 확인 풀림과 테스트 변경만 남김. 무엇이 "문제"인지는 화면 정의서 SCR-17과 ADR-119의 예외 표시에서 가져온다), (나) 감춘다. 화면 정의서에 근거가 있으면 (가), 없으면 더 작은 (나)를 고른다. `e2e/scr-17.spec.ts`가 단언한다. (가)라면 걸러진 뒤의 건수 · 빈 상태 · 다른 필터 칩과의 조합을 단언한다. 목록은 여전히 `confirmation.list` 응답에서만 만든다(NFR-03. 화면이 새 분류를 지어내지 않는다. 응답에 있는 종류 · 예외 값으로만 거른다).
2. **대상 링크와 죽은 코드.** 확인할 것 상세의 대상 링크(규칙, 요구사항)를 누르면 규칙 화면 · 요구사항 화면이 **그 카드를 고른 상태**로 열린다(상세가 열리고 목록에서 그 카드가 선택 표시). 폐기된 규칙을 가리키면 [폐기 포함]이 켜져야 보이는 점을 처리한다. 없는 대상(지워진 요구사항)이면 어떻게 되는지 정하고 단언한다. 공용 카드의 쓰이지 않는 안 읽음 점(`unread`)과 상태 배지의 처리 결과(`decision`) 코드를 지운다(지우기 전에 쓰는 곳이 정말 없는지 grep으로 확인하고, 지운 뒤 타입 검사로 고정된다).
3. **실행 종료 사유 표시.** 지금 실행 실패 사유가 화면 어디에도 글로 나오지 않는다(SCR-05 파이프라인에 "실패 · Red 확인" · "중단"만). 
   - 사유가 보일 **자리**를 화면 정의서에서 찾는다(SCR-05 파이프라인 · SCR-06 실행 상세 · 규칙 상세 실행 이력 가운데 명세가 실행 결과 · 실패 이유를 보이라고 한 자리). 명세에 자리가 없으면 가장 작은 자리 하나(실행 상세)를 골라 ADR-123에 적는다. 새 화면 · 새 탭을 만들지 않는다.
   - 사유 값(`target_rule_retired`, `objection_applied`, `existing_rule_contradiction`, `project_daily_budget_exceeded`, `step_error` 등 **shared의 실행 종료 사유 형식에 든 전부**)마다 한국어 표시명을 둔다. 표는 shared에 두고(판단 주제 표와 같은 방식) app은 그 표로 그린다. **형식의 값 집합 = 표의 키 집합**임을 시험으로 고정한다(값이 늘면 표가 빠져 빨강). 표시명은 화면 정의서 1.1(명사형, 이모지 없음, 코드 표기 없음)을 따르고 문서 기호(ADR 번호, ⓐ 등)를 넣지 않는다. 모르는 값(옛 행)은 영어 식별자를 그대로 내지 않고 정한 한 가지 글(예: "알 수 없는 사유")로 보인다.
   - 사유의 **상세**(`exitDetail`)에 든 글 가운데 에이전트 · 판정 출력에서 온 것은 화면에 그대로 내지 않거나 `visibleText`류 도우미를 거친다(`brief-common.md` 표시 규칙). 무엇을 보이고 무엇을 안 보이는지 ADR에 적는다.
   - 규칙 상세 속성 줄의 확인 상태 낱말 겹침("확인됨 확인됨" 같은 중복)을 없앤다.
   - 코멘트의 두 몫도 여기서 판정한다: (a) 규칙 상세 "실행 이력"이 한 실행을 두 줄(검사와 병합 재검사 판정)로 보이는 것, Red 확인에서 실패한 실행만 있는 규칙이 "실행 이력 없음"으로 나오는 것. 화면 정의서가 "실행 이력"을 실행 단위로 정의하면 실행당 한 줄로 고치고, 판정 단위로 정의하면 그대로 두고 줄에 어느 판정인지 드러낸다. 응답에 필요한 값이 없어 app만으로 못 고치면(오케스트레이터 RPC 변경 필요) **고치지 말고 사실과 필요한 변경을 보고한다**(후속 이슈). (b) 사람 주체로도 날 수 있는 오류 메시지 원문(`confirmation-service.ts`의 확인 근거 거부 3곳, `proposal-service.ts`의 거절 사유 누락. 문서 기호가 들어 있다)이 화면에 **그대로 나오는 경로가 있는지** app 코드를 훑는다(RPC 오류의 `message`를 그리는 자리 전부). 있으면 app이 오류 코드로 자체 문구를 내도록 고치고, 없으면 "없음"과 확인한 자리 목록을 보고한다. 오케스트레이터의 메시지 문구는 고치지 않는다.
4. **화면 시험 보강.** 아래를 각각 단언한다.
   - 상세 다시 읽기 횟수: 규범 변경 알림(`event.normChange.appended`) 한 번에 상세 읽기 RPC가 한 번만 나간다(호출 수를 센다. 두 번 나가면 빨강).
   - 규칙 편집 뒤 `replace`로 이동했을 때 상세가 다시 읽힌다.
   - `visibleLines`가 U+2028 · U+2029로 줄을 만들지 않는다(단위 시험).
   - 검증 화면(SCR-05)의 사람 확인 기준에서 '없음'을 누르면 빈 목록이다.
