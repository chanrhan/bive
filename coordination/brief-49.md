## (가) 등록과 규범 입력
1. **`contract.register(file, kind)`.** 승인 대기 제안 없이 한 트랜잭션에서: 계약(등록 단위 = 파일, 내용 해시, 종류), `contract` 검사 규칙, 규범 변경 기록. 정해야 할 것(ADR-129):
   - **주체별 기록(ADR-100 C2).** 사람의 CLI 등록: 계약은 확인됨(근거 = 계약의 작성 주체 기록), **승인 기록에 남는다**. 그에 따라 오케스트레이터가 만드는 `contract` 검사 규칙의 생성은 규범 변경 기록에 남는다. 에이전트 반영: 미확인, 규범 변경 기록에만. 승인 기록의 행동 값: 지금 `approval_log.action`에는 확인 · 규칙 편집 · 계약 편집만 있고 "등록"이 없다. 계약 편집 값을 쓸지 새 값을 더할지 정한다. 새 값을 더하려고 `approval_log` 표를 다시 만들어야 한다면(추가 전용 · 해시 체인 · 0021의 `approval_log_actor_human` 등 기존 트리거 전부 복원, 옛 행 그대로, 체인 유효) 그 비용과 위험을 재서, 다시 만들지 않는 길(기존 값 + 상세 칸으로 구별)이 무결성을 해치지 않으면 그쪽이 가장 작다. `ApprovalLogEntry` 읽기 스키마는 넓히기만 한다(옛 행이 깨지지 않게).
   - **에이전트 반영 경로가 이 이슈에 있는가.** 수용 기준은 "에이전트 반영이면 미확인 … 규범 변경 기록에만"을 단언하라고 한다. 에이전트가 계약을 반영하는 도구(예: 계약 제안 · 반영 도구)가 지금 있는지 확인한다. 없으면 **새 에이전트 도구를 만들지 말고**(역할의 고정 도구를 넓히는 일은 범위가 크고 무결성 결정이다) 반영 모듈 수준(에이전트 주체로 부르는 내부 함수)에서 그 기록 규칙을 시험으로 고정하고, 도구 배선은 뒤 이슈(M3-10)에 넘긴다고 ADR에 적는다. 수용 기준을 이렇게 만족시키는 것이 문장과 맞지 않다고 판단되면 멈추고 보고한다.
   - **`contract.register` RPC의 주체.** 사람 주체만 받는가(에이전트가 RPC로 부르면 거부). `blocks.set` · `confirmation.set`과 같은 장치를 쓴다. 판정 중인 코드가 사람 주체 RPC를 위조할 수 있다는 기존 한계(#117)는 그대로다(한 줄).
   - **파일과 해시.** `file`은 프로젝트 루트 기준 상대 경로다: 절대 경로 · `..` · 기호 링크로 프로젝트 밖 · 디렉터리 · 없는 파일 · 너무 큰 파일 · 종류와 안 맞는 확장자를 어떻게 다루는가(거부가 기본). 해시는 무엇의 해시인가(작업 트리의 파일? 기준 브랜치 커밋의 파일?). 사람이 등록한 뒤 파일이 바뀌면(구현 역할이 계약 파일을 고침) 계약은 어떻게 되는가: 이 이슈에서는 "등록 때의 해시를 저장하고, 어긋남을 조회에서 알 수 있게 한다"까지가 가장 작다(변경 반영은 M3-10). 구현 역할이 계약 파일을 쓸 수 있는지(경로 가드)를 확인해 ADR에 사실대로 적는다.
   - 같은 파일을 두 번 등록, 같은 파일을 다른 종류로 등록, 등록 단위와 요구사항 연결(파일 단위, ADR-019)을 정한다. `contract` 검사 규칙의 부모 요구사항(NRM-02는 내장 규칙만 부모 없음을 허용한다: 계약 검사 규칙의 부모가 무엇인지 ADR-019 · 명세로 정한다), 대상 블록 · 위험도(M3-01은 에이전트 도구 경로에서만 필수), 확인 상태, **자동 시작**(M3-03처럼 실행 유형 B가 생기기 전에는 자동으로 실행을 만들지 않고, `run.create`의 대상이 되면 어떻게 되는지 정한다).
   - 조회: `contract.list`(또는 기존 조회)로 계약의 표시 ID · 종류 · 원본 파일 · 해시 · 확인 상태가 나온다. 표시 ID 규칙(명세의 접두).
   - 저장: 새 표가 필요하면 0024 하나에. 사람 주체 · 추가 전용 등 DB 제약(트리거)과 옛 DB 이행 시험(0023 상태 데이터 DB에 0024만 올림, 스키마 객체 목록, 두 해시 체인).
2. **CLI.** `pnpm --filter @bive/app cli contract register <dir> <file> <kind>`가 `contract.register`를 사람 주체로 부른다(`cli blocks set`과 같은 방식 · 종료 코드 규칙). `app/test/cli-contract.test.ts`.
3. **규범 입력.** 효력 있는 계약(표시 ID, 종류, 원본 파일)이 **모든 역할 세션**의 규범 입력에 M7-07 · M7-08과 같은 형식과 상한으로 더해진다. `rule-writer.test.ts`와 `implementer.test.ts`의 프롬프트 스냅샷이 단언한다. 계약 **내용**을 싣는가, 목록(표시 ID · 종류 · 파일 경로)만 싣는가: 수용 기준 문장은 "표시 ID, 종류, 원본 파일"이다(목록). 파일 경로는 사람이 등록한 값이지만 표시 값 처리 · 상한을 다른 규범 자료와 같게 둔다. 계약이 없으면 절이 어떻게 보이는지(기존 시나리오의 프롬프트 기준값이 바뀌지 않아야 한다: 계약이 없는 프로젝트는 지금과 글자까지 같다).

## (나) 계약 검사 실행기
4. **도구.** ADR-033이 정한 도구를 오케스트레이터(또는 새 내부 모듈)의 의존성으로 더하고 버전을 고정한다: `@redocly/cli`, `@stoplight/prism-cli`, `prisma`(픽스처가 쓰는 판과의 관계를 확인), `@asyncapi/cli`. 설치가 네트워크 정책에 막히거나, 설치 스크립트(postinstall, 네이티브 빌드, 엔진 내려받기)가 필요해 `onlyBuiltDependencies`를 넓혀야 하거나, 잠금 파일이 수백 패키지 늘어 CI 설치 시간이 크게 는다면 **멈춰서** 실측값과 함께 보고한다(도구별로 나눠 적는다. 예: `@asyncapi/cli`만 무겁다).
5. **실행기.** 종류별로 무엇을 부르는지를 `orchestrator/test/contract-runner.test.ts`가 단언한다: OpenAPI = `@redocly/cli lint`(유효성)와 판정 서버 앞 `@stoplight/prism-cli proxy --errors`(구현 일치: 인수 테스트 트래픽을 프록시로 검증), Prisma = `prisma validate`와 `prisma migrate diff --exit-code`, AsyncAPI = `@asyncapi/cli validate`만.
   - 도구의 출력(종료 코드 · JSON)을 **변환만** 한다(판정 로직을 직접 만들지 않는다, ADR-033). 결과 모양: 계약별 `pass` · `fail`과 위반 요약(상한 · 표시 값), 오류는 결과와 섞이지 않는 닫힌 쪽(시간 초과 · 도구 없음 · 깨진 출력 · 0이 아닌 예기치 않은 종료가 `pass`로 읽히지 않는다).
   - **이 이슈는 실행기와 그 시험까지다.** 검사 단계 · 병합 재검사에 잇는 일(판정 기록 저장, 회귀 규칙, 실행 종료 사유)은 수용 기준에 없다: M3-06 몫으로 넘기고 "넘길 사실"에 실행기의 입력 · 출력 · 부르는 시점(구조 검사처럼 판정 커밋의 깨끗한 체크아웃에서)을 적는다. 다만 prism 프록시는 판정 서버 앞에 서야 하므로, 판정 러너(`judge/`)에 프록시를 끼울 수 있는 자리(선택 옵션)를 어떻게 둘지는 여기서 정해야 한다: 판정 러너의 기존 동작 · 지문 · 격리를 바꾸지 않는 선택 옵션으로만 더하고, 옵션이 없으면 지금과 글자까지 같아야 한다.
6. **픽스처와 변형.** 픽스처에 `openapi.yaml`을 더하고(지금 픽스처의 실제 라우트와 맞게. 원본에서 `pass`), `scripts/make-variant.sh`에 `contract-mismatch` 변형(응답 필드 타입 위반, 마이그레이션 없는 스키마 필드)을 더한다(이름별 함수, 변형마다 커밋 하나, `scripts/test-make-variant.sh`에 검사 추가). `contract-runner.test.ts`가 변형에서 OpenAPI와 Prisma 계약 판정 `fail`을, 원본에서 `pass`를 단언한다. 픽스처 원본에 파일을 더하면 파서의 미분류 목록 · 예제 블록 선언 · 기존 시험의 파일 목록 단언이 달라질 수 있다: 바뀐 단언을 보고에 적는다. 실제 도구를 돌리는 시험이 이 VM(프록시가 필요한 네트워크, 판정 설치 시간 초과 제약: `dev-env` 스킬)에서 돌 수 없으면 CI에서만 도는 시험으로 두지 말고 멈춰서 보고한다(로컬에서 확인할 수 없는 시험은 받지 않는다. 다만 도구 자체는 로컬 의존성에서 돌므로 판정 서버 설치와 무관한 부분은 돌 것이다).

## 멈춤 조건 (닿으면 구현을 멈추고 근거와 함께 보고한다)
- **도구가 대상 프로젝트의 코드를 실행하는 길을 끌 수 없을 때.** 계약 파일과 프로젝트 파일은 구현 역할이 쓸 수 있다. 도구가 프로젝트 안의 설정 · 플러그인 · 코드(`redocly.yaml`의 플러그인 · 사용자 규칙 JS, `prisma.config.ts`, 스키마의 `generator` 블록이 가리키는 실행 파일, `.asyncapi-cli` 설정, `package.json` 스크립트, `$ref`가 가리키는 원격 URL · 프로젝트 밖 파일)를 읽어 실행하거나 네트워크로 나가는 길을 도구별로 문서 · 소스에서 확인해 목록과 끈 방법을 ADR-129에 적고, 파서의 `isolation.test.ts`와 같은 방식(대조군 포함)으로 시험한다. 끌 수 없는 길이 있으면 그 도구는 구현하지 말고 보고한다(판정 격리 안에서 돌릴지는 조율자가 정한다).
- 판정 러너 · 판정 격리(ADR-026)의 기존 동작을 바꿔야만 prism 프록시를 끼울 수 있을 때.
- `prisma migrate diff`가 그림자 데이터베이스 · 실제 DB 접속 · 엔진 내려받기를 요구해 닫힌 환경에서 돌 수 없을 때(픽스처의 DB 종류에서 무엇이 필요한지 먼저 확인).
- 사람 단계가 새로 필요하거나 기존 완료 흐름이 막히는 결정에 닿을 때(조율자가 사람 결정 이슈로 올린다).

## 반드시 지킬 것
- 엔진 · 단계 코드에 확인 상태를 들이지 않는다. 실행 종료는 `runEnding()` 한 곳. 규범 변경 기록 · 승인 기록 · 규칙 생성 쓰기는 구조 시험의 허용 목록 파일에서만(목록을 고치면 이유를 PR 본문에). `integrity.test.ts`를 느슨하게 만들지 않는다. 에이전트 역할의 고정 도구 목록을 바꾸지 않는다.
- `NormChangeDetail` · `ApprovalLogEntry` 읽기 스키마는 넓히기만 한다(옛 행 · 두 해시 체인이 유효해야 한다). 표를 다시 만들면 그 표의 색인 · 트리거 전부(0016 · 0018 · 0021 · 0023이 더한 것 포함)를 복원하고 시험으로 고정한다.
- 자식 프로세스: 실행 파일은 BIVE 자신의 의존성에서(대상 프로젝트의 `node_modules/.bin`이 아니다), 인자는 배열, 환경 변수는 비우고 필요한 것만(프록시 환경 변수를 도구 자식에 넘기지 않는다 · 값을 출력하지 않는다), 작업 폴더 통제, 시간 제한과 출력 상한, 중단 신호. Electron 위에서는 `ELECTRON_RUN_AS_NODE` 하나(파서의 `childEnv` 방식).
- 계약 내용 · 도구 출력 · 파일 경로는 구현 역할이 정할 수 있는 글이다: 기록 · 세션 입력 · 화면으로 가는 자리마다 상한과 표시 값 변환을 둔다.
- 방어 · 판정 규칙마다 "빼면 빨강"인 시험을 두고 변이 결과 표를 PR 본문에 낸다.
- 기존 시나리오와 파이프라인 e2e의 기준값이 바뀌면 안 된다(계약이 없는 프로젝트는 지금과 같다). `docs/spec/*` · `docs/roadmap.md` · `CLAUDE.md`를 고치지 않는다. 의미 있는 단위마다 로컬 커밋을 남긴다(컨테이너 재시작 대비).
- 완료 조건 명령: 설치 · 린트 · 타입 · 빌드 · 형식 · 단위 테스트(격리 `TMPDIR`, 알려진 두 시험만 실패 허용) · `scripts/test-make-variant.sh` · 파이프라인 e2e(픽스처 설치 뒤, 격리 `TMPDIR`, PR 전 한 번). 새 의존성으로 설치 · CI `checks` 시간이 얼마나 늘었는지 보고한다.

## 보고
공통 지침의 보고 항목에 더해: 수용 기준 4개별 한 일과 근거 시험, 정한 것들(승인 기록의 행동 값, 에이전트 반영 경로의 처리, 해시의 대상, `contract` 규칙의 부모 · 확인 · 자동 시작, 규범 입력에 싣는 것)과 근거 문장, 도구별 버전 · 부르는 방식 · 프로젝트 코드를 실행하거나 네트워크로 나가는 길의 목록과 끈 방법 · 시험, 마이그레이션 사용 여부와 다시 만든 객체, 잠금 파일 · 설치 시간 변화, 변이 결과 표, M3-05 · M3-06 · M3-10에 넘길 사실, 멈춤 조건에 닿았는지, 발견했지만 고치지 않은 것. 짧게, 한국어로.
