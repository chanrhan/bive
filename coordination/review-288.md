## 꼭 판정할 것
1. **범위.** `git diff 78d5ee0...HEAD --stat`. 화면 · 시나리오 · 마이그레이션 · 파이프라인 e2e 파일 · `docs/spec/*` · `CLAUDE.md`가 바뀌지 않았는가. `judge/report.ts` · `runner.ts` · `red-check.ts`의 변경이 "글자를 상수로 낸 것"뿐이고 판정 동작 · 문구가 글자까지 같은가(`-` · `+` 줄을 하나씩 대조).
2. **길이 정말 닫혔는가.** Red 확인 결과에서 온 글(케이스 이름, 오류 메시지, 위치, 훅 실패 안내)이 테스트 작성 세션의 입력(작업 지시, 시스템 프롬프트, 세션 디렉터리의 파일)에 들어가는 자리를 네가 직접 전부 찾는다(`describeUnmet` · `previousFeedback` · `notFailedCases` · `problems` · `exitDetail`을 grep). 구현자의 목록(ADR-128의 7자리)에 없는 자리가 있는가.
   - 통과 케이스: "위치가 커밋의 대상 규칙 폴더 파일이고 이름이 리터럴과 맞으면 `- 파일:줄 이름`으로 싣는다". **위치(파일 · 줄)는 어디서 오는가.** 판정 러너의 결과에서 온다면 구현 코드가 지어낼 수 있는 값인가(줄 번호, 경로). 경로가 "커밋의 대상 규칙 폴더 파일"인지 무엇과 대조하는가(커밋의 파일 목록과 정확 일치인가, 접두 비교인가. `bive-acceptance/RULE-001/../../x` 같은 경로, 대소문자, 기호 링크). 줄 번호가 숫자 형식으로만 실리는가.
   - "알 수 없는 케이스 N건"의 N과, 원문이 다른 칸(같은 메시지의 다른 줄, 훅 실패 안내)으로 새지 않는가.
   - **스위트 훅 실패 안내의 "앞부분"을 그대로 싣는다**고 했다: 그 앞부분이 BIVE가 만든 고정 글자인가, 어디까지가 고정이고 어디부터가 러너 · 구현 코드의 글인가. 자르는 방식이 구현 코드의 글을 한 글자도 싣지 않는가(접두 일치 뒤 나머지를 버리는가, 길이로 자르는가).
   - 고정 문구 세 개(`케이스 0개` · `인수 테스트 파일 없음` · `수집된 테스트 0개`)를 "그대로 싣는" 판정: 메시지가 그 문구와 **정확히 같을 때만**인가(포함 · 접두 비교라면 구현 코드가 그 문구로 시작하는 글을 지어 나머지를 실을 수 있다).
3. **기준 글의 출처.** 앞 시도 Red 확인 단계 결과의 `exitDetail.commit`. 그 값이 어디서 쓰이고(엔진 · `red-check.ts`) 에이전트 · 판정 프로세스가 바꿀 수 없는가. "판정 결과 쪽 같은 이름 칸도 덮는다"는 주장(판정 러너 결과에 `commit` 칸이 있어도 실행기가 끝에 덧쓴다)을 코드로 확인한다: 덧쓰는 순서가 뒤바뀌면 판정 결과(구현 코드가 영향을 줄 수 있는 쪽)의 값이 이긴다. 그 커밋의 `bive-acceptance/<대상 규칙>/` 파일은 테스트 작성 역할만 쓸 수 있는가. 대상 규칙이 여러 개일 때, 다른 규칙 폴더의 리터럴로 이 규칙의 이름을 통과시키지 않는가. 커밋을 못 읽으면 전부 모르는 쪽인가. git 객체에서 읽는가(작업 트리 아님, `--no-replace-objects`, 커밋 형식 검사: 기존 함수를 그대로 쓰는가).
4. **수집 오류 (가) 방식의 타당성.** 메시지 원문을 빼면 테스트 작성 역할이 런타임 수집 오류(없는 모듈 import 등)를 고칠 단서가 위치뿐이다. 구현자는 "문법 오류와 금지된 import는 테스트 작성 단계의 import 검사가 커밋 전에 자기 소스만 보고 원문을 준다"를 근거로 들었다. 그 검사가 실제로 무엇을 잡는지(`judge/acceptance-lint.ts`) 확인하고, 남는 경우(없는 상대 모듈, 없는 패키지, 타입 오류가 아닌 런타임 오류)에서 회귀가 헛도는 한계가 ADR-128에 사실대로 적혔는가. 이 선택이 지시서의 기본 방침과 맞는가.
5. **저장된 원문.** 단계 결과에는 원문이 그대로 남는다(저장 형식을 바꾸지 않음). 그 원문이 흐르는 다른 길: `run.get` 등의 응답(앱 main · CLI). 앱 렌더러가 `exitDetail`을 그리지 않는다는 주장을 grep으로 확인한다. 다른 역할의 세션 입력(규칙 작성 판단, 구현 세션의 앞 시도 사유, 이의 판단)으로 흐르는 길이 없는가. CLI가 원문을 보이는 한계가 ADR에 적혔는가.
6. **구조 시험.** `integrity.test.ts`의 `-` 줄이 0인가(더하기만). 새 단언이 무엇을 고정하는가: Red 확인 결과를 읽는 파일 목록, `notFailedCases`를 쓰는 파일 목록, git 객체를 읽는 곳이 한 곳, 기준이 필수 인자. 새 자리(다른 파일이 Red 확인 결과의 글을 세션 입력에 싣는 코드)를 더하면 빨강이 되는가를 직접 해 본다.
7. **ADR.** ADR-128의 닫은 길 · 남는 길 · 흐르는 자리 목록 · 테스트 작성 역할이 받는 구현 산출 입력(`prisma/schema.prisma` 사본, `routes.md`, 다른 규칙의 `*.acc.ts`, `blocks.json`)의 처리 설명이 코드와 맞는가(문장마다). 악용 절차가 적혀 있지 않은가. ADR-121은 ⓒ 표기만 바뀌었는가. 구현자가 한계로 적은 두 가지(`routes.md`에 구현이 만든 폴더 이름이 거르지 않고 실림 · 줄 나눔 글자가 든 폴더 이름이면 줄이 생김, `prisma/schema.prisma` 사본에 상한 · 변환이 없음)가 사실인지 코드로 확인하고, 심각도를 판정한다(이 PR의 범위 밖이다. 새 이슈가 필요한 수준인지, 어떤 방어가 가장 작은지 제안만 한다).
8. **기존 흐름.** 사유 글의 모양이 바뀌었다: 기존 시나리오(Red 확인이 회귀하는 것)와 파이프라인 e2e 기준값 파일이 바뀌지 않았는가. 정상적인(구현 코드가 개입하지 않은) Red 회귀에서 테스트 작성 역할이 받는 사유가 여전히 쓸모 있는가(통과한 케이스의 이름과 위치가 리터럴이면 그대로 보인다).
9. **변이.** 구현자의 5종과 겹치지 않게 7종 안팎. 후보: ⓐ 고정 문구 판정을 정확 일치에서 접두 일치로, ⓑ 훅 실패 안내를 전부 싣기, ⓒ 위치의 경로 대조를 접두 비교로(`bive-acceptance/RULE-001/../x`가 통과), ⓓ 대상 규칙이 아닌 다른 규칙 폴더의 리터럴도 받기, ⓔ `exitDetail.commit` 대신 판정 결과 쪽 커밋 칸을 쓰기(덧쓰기 순서 뒤집기), ⓕ "알 수 없는 케이스" 건수 대신 원문 길이 등 다른 값을 싣기 / 0건일 때도 줄을 내기, ⓖ 줄 번호를 형식 검사 없이 싣기, ⓗ 앞 시도가 Red 확인이 아닐 때(테스트 작성 자체의 미충족)도 대조 기준을 요구해 정상 사유가 빠지게. 변이마다 어느 시험이 빨강이 됐는지 표로 낸다. 빨강이 안 된 변이는 차단 후보다.
