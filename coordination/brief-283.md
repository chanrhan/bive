## 해야 할 것 (수용 기준 순서)
1. **규칙 기준 실행 조회.** 규칙 상세의 실행 이력이 상한 없는 `run.list`(프로젝트의 모든 실행) 대신, 그 규칙의 실행 이력 줄에 필요한 실행만 돌려주는 조회를 **1회** 부르게 한다. 필요한 실행 = 그 규칙이 대상인 실행 + 그 규칙을 판정한 실행(판정 기록에 그 규칙이 있는 실행. 대상이 아니어도 병합 재검사 등으로 판정될 수 있는지 코드로 확인한다).
   - 모양은 기존 방식에 맞춘다: `run.list`에 선택 인자(`ruleId`)를 더하는 쪽과 새 메서드 가운데, 응답 형식을 넓히기만 하고 옛 호출(인자 없음)의 결과가 글자까지 같은 쪽을 고른다. 근거를 ADR-135에 적는다.
   - 질의는 색인(`run_target_rules_rule`, `judgments`의 규칙 색인)을 쓰고 `runs` 전체를 훑지 않는다. `EXPLAIN QUERY PLAN` 결과를 보고에 적는다. 깨진 행의 처리는 기존 실행 목록(ADR-094 · ADR-120: 그 행만 건너뜀)과 같게 한다. 순서는 기존 실행 목록과 같다(표시 ID 순, 자리수 넘김 포함).
   - `orchestrator/test/run.test.ts`가 조회 결과를 단언한다: 대상인 실행, 판정만 한 실행, 둘 다, 무관한 실행은 빠짐, 여러 규칙 대상 실행, 실행 없음, 없는 규칙 ID · 다른 프로젝트(기존 오류 방식), 순서(EXE-999 · EXE-1000), 인자 없는 호출은 그대로.
   - `e2e/scr-06-rule.spec.ts`가 호출 횟수와 인자를 단언한다: 규칙 상세를 열 때 그 조회가 그 규칙 ID로 1회이고 인자 없는 `run.list`는 규칙 상세 때문에 나가지 않는다. 다시 읽기(실행 알림)에도 같다. 규칙 화면의 다른 자리(목록 등)가 `run.list`를 쓰고 있으면 그것은 건드리지 않고 시험이 구분해 센다.
   - M3-16의 `rule.get`(최신 실행 줄)과 이 조회가 겹치는 읽기를 합칠 수 있어 보여도 합치지 않는다(범위 밖). 다만 두 값이 서로 어긋나 보이는 경우(최신 실행 줄의 실행이 실행 이력에 없는 경우 등)가 있으면 사실을 ADR 한계에 적는다.
2. **알림 하나에 `rule.list` 한 번.** 요구사항 상세가 열린 요구사항 화면에서 규범 변경 알림 하나에 `rule.list`가 지금 인자가 다른 두 조회로 두 번 나간다. 한 번만 나가게 한다(한 조회 결과를 두 자리가 함께 쓰거나, 한쪽이 다른 쪽 결과에서 골라 쓴다). 두 조회의 인자가 왜 달랐는지(요구사항 기준 · 프로젝트 전체) 확인하고, 합친 뒤에도 두 자리가 보이는 값이 전과 같은지 기존 시험으로 지킨다. `e2e/scr-06-requirement.spec.ts`가 알림 하나 뒤 `rule.list` 호출 수가 정확히 1 늘어남과 화면 값이 새 응답으로 바뀜을 단언한다(상세가 닫힌 경우의 호출 수도 그대로인지 확인).
3. **블록 선언이 바뀐 뒤 다시 읽기.** 블록 선언이 바뀌었을 때(누가 어떻게 바꾸는지: 파서 재실행 · 실행 병합 · 설정 편집 등 실제 경로를 코드에서 찾는다) 열린 규칙 상세와 요구사항 상세가 새 선언으로 "선언 외"를 판단하게 한다.
   - 계기를 정해 ADR-135에 적는다. 기존 알림 가운데 선언이 바뀌는 모든 경로에서 이미 나가는 것이 있으면 그것에 얹는다(가장 작은 변경). 없으면 새 알림을 더하되 shared 프로토콜 · 오케스트레이터의 내보내는 자리 · 앱의 구독 묶음에 함께 더하고, 선언이 바뀌는 경로마다 나가는지 오케스트레이터 시험으로 지킨다. 선언이 화면 밖(파일 직접 편집)에서 바뀌어 알림이 없는 경로가 남으면 한계에 적는다(폴링을 새로 만들지 않는다).
   - 늦은 응답이 새 선언을 덮지 않는다(요청 순번, M3-35 방식). 다른 프로젝트의 알림에는 읽지 않는다.
   - 두 e2e 파일이 단언한다: 선언에 없던 이름이 선언에 생기면 "선언 외" 표시가 사라지고, 선언에서 빠지면 생긴다(알림 뒤, 화면을 다시 열지 않고).
4. **실행 이력 줄의 상태 칸 한 줄.** 상세가 접히지 않는 창 폭(접힘 기준 폭은 코드의 값에서 읽는다)에서 실행 이력 줄의 상태 칸이 줄 바꿈되지 않게 한다. CSS만으로 고친다(칸의 줄 바꿈 금지와 최소 폭. 다른 칸이 줄어들거나 잘려야 하면 공통 툴팁의 기존 잘림 방식을 쓴다). 가장 긴 상태 표시명(종료 사유 표시명 포함, ADR-123의 표에서 찾는다)으로 시험한다.
   - 시험은 글자 폭에 기대지 않는다(CI의 한글 글꼴 폭이 다르다): 상태 칸의 계산된 스타일(`white-space`)과, 칸의 높이가 같은 줄의 한 줄짜리 칸(표시 ID 칸 등)과 같음(= 줄이 하나)처럼 **상대 비교**로 단언한다. 픽셀 값 · 줄 바꿈 위치를 숫자로 단언하지 않는다. 좁은 폭(접힌 상태)에서 넘침 · 가로 스크롤이 생기지 않는지도 기존 방식으로 본다.

## 반드시 지킬 것
- 응답 형식은 넓히기만 한다. 인자 없는 `run.list`, `rule.list`, `judgment.list`, `rule.get`의 기존 결과가 글자까지 같다(기존 시험의 단언을 고치지 않는다. 고쳐야 하면 왜인지 보고).
- 값은 저장된 기록에서만 만든다(NFR-03). 목 데이터는 시험 코드 안에만. 시험용 가짜 응답은 shared 스키마를 지나는 것만.
- 방어 · 표시 조건마다 "빼면 빨강"인 시험과 변이 결과 표: 조회에서 판정만 한 실행 빼기, 무관한 실행 섞기, 규칙 상세가 옛 `run.list`를 부르게 되돌리기, `rule.list` 두 번 나가게 되돌리기, 선언 다시 읽기 계기 빼기, 선언 늦은 응답이 덮기, 다른 프로젝트 알림에 읽기, 상태 칸 줄 바꿈 금지 빼기, 재접속 때 다시 읽기 빼기(새로 더한 읽기마다).
- 화면 시험: `waitForTimeout` 금지, 글자 폭 · 픽셀 단언 금지, 숨은 글자는 이스케이프(역슬래시-u 표기)로.
- UI 문구를 새로 만들지 않는 것이 기본이다(이 이슈는 동작 다듬기다). 꼭 필요하면 1.1을 따르고 ADR에 적는다.

- 바뀐 파일이 20개를 넘을 것 같으면 멈추고 보고한다. 네 항목 가운데 하나가 예상보다 크면(새 알림이 여러 경로에 걸치는 등) 그 항목의 설계만 보고에 적고 나머지 셋을 끝낸 뒤 멈춘다(조율자가 쪼갠다).
