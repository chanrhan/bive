## 꼭 판정할 것
1. **범위.** `git diff 10a5348...HEAD --stat`. 화면 · 시나리오 · 마이그레이션 · 파이프라인 e2e 파일 · `docs/spec/*` · `docs/roadmap.md` · `CLAUDE.md`가 바뀌지 않았는가. 다른 입력 사본(`rules/*.md` · 다른 규칙의 `*.acc.ts` · `blocks.json`)과 앞 시도 사유(`describeUnmet`)의 동작이 글자까지 그대로인가(`inputs.ts`의 `-` · `+` 줄을 하나씩 본다). `prompts.ts`의 한 줄이 필요한 만큼만인가.
2. **조각 패턴이 정말 닫는가.** `isSafeRouteSegment`와 그것을 부르는 자리를 읽는다.
   - 패턴이 받는 글자: 구현자 보고는 이름 `[A-Za-z0-9._%-]+`, 동적 조각, 경로 그룹 `(이름)`, 병렬 `@이름`, 가로채기 `(.)` · `(..)` · `(..)(..)` · `(...)`다. 줄 나눔(`\n` · `\r` · U+2028 · U+2029 · U+0085) · 제어 글자 · 공백류(탭, 비ASCII 공백) · 따옴표 · 백틱 · 마크다운 구조 글자(`#` · `*` · `` ` `` · `|` · `<` · `>` · `[`와 `]`의 짝이 안 맞는 꼴 · `(`와 `)`의 짝이 안 맞는 꼴)가 **어느 가지로도** 통과하지 못하는가. 정규식에 `$`를 쓰면 끝의 줄 나눔 앞에서 맞을 수 있다(`m` 깃발 · `$`와 `\n`): 실제로 `'a\n'`, `'[x]\n'`, `'(g)\n'`, `'@s\n'`을 넣어 본다. `%`를 받는 근거(퍼센트 부호화된 폴더 이름)와 `%0A` 같은 글자 열이 `routes.md`에서 줄 나눔으로 읽히지 않는지(글자 그대로 실리는가).
   - 정규식이 선형인가: 겹친 반복 · 선택 가지의 겹침이 없는가. 길이 100자 확인이 정규식보다 **먼저**인가. 100자짜리 최악 입력(`(..)`의 반복, `[[...` 뒤 긴 글)으로 시간을 재 본다.
   - "라우트가 지난 폴더 이름을 모두 본다": 경로 그룹처럼 URL에 나오지 않는 폴더도 보는가(새 칸 `RouteEntry.folders`). 보지 않는 폴더 이름이 `routes.md`에 실리는 길이 있는가(예: 종류 칸, 파일 이름, 메서드 이름). **메서드 이름은 어디서 오는가**: `route.*` 파일 내용에서 뽑는다면 구현 역할의 글이다. 뽑는 방식이 고정 목록(GET · POST …)과의 대조인지, 파일에서 찾은 글자를 그대로 싣는지 확인한다(그대로 싣는다면 차단).
   - 패턴 밖 경로를 "통째로 빼고 수만" 싣는가. 원문이 머리줄 · 오류 메시지 · 로그 · 단계 결과(`exitDetail`) 어디에도 새지 않는가.
   - 픽스처 `fixtures/sample-next-app`의 실제 라우트가 전부 실리고 `routes.md` 글이 이 PR 전과 글자까지 같은가(main의 `renderRoutes` 결과와 직접 비교한다).
3. **상한과 결정성.** `ROUTES_LIMITS`(경로 200자 · 폴더 이름 100자 · 항목 50건 · 줄 합 4000자). 경계값 시험이 "같음"과 "하나 넘음"을 둘 다 보는가. 넘친 수가 정확한가(패턴 밖으로 뺀 수와 상한으로 뺀 수가 섞이거나 두 번 세이지 않는가). 정렬이 코드 단위 비교이고 파일 시스템 나열 순서 · 로캘에 기대지 않는가(`localeCompare`가 남은 자리가 없는가). 머리줄의 고정 문장이 `routes.md`를 읽는 프롬프트 문장과 어긋나지 않는가. 라우트 나열 자체에 깊이 · 개수 상한이 없으면 폴더 10만 개짜리 트리에서 테스트 작성 단계가 오래 걸리는가(이 PR의 범위 밖이면 비차단으로 적고 크기만 잰다).
4. **스키마 사본.** 1 MiB 상한. `lstat`으로 먼저 크기를 보고 넘으면 열지 않는가. 연 핸들이 일반 파일인지 다시 보는가(`O_NOFOLLOW | O_NONBLOCK`: FIFO · 장치 파일에서 멈추지 않는가. FIFO를 `prisma/schema.prisma`에 두고 실제로 돌려 본다). 상한 + 1바이트까지만 읽어 읽은 바이트로 다시 막는가. 핸들을 실패 경로에서도 닫는가. 넘칠 때 사본을 두지 않고 고정 문장으로 알리는가(잘린 사본이 남지 않는가. **앞 시도가 남긴 옛 사본이 세션 폴더에 그대로 남아 읽히는 길**이 없는가: 세션 입력 폴더가 시도마다 새로 만들어지는지 확인한다). 내용이 바이트 그대로인가(바꾸지 않는 것이 이 이슈의 결정이다).
5. **기호 링크.** 상위 `prisma/`가 링크(작업 공간 안 · 밖)면 사본이 없는가. `src`가 링크일 때 `src/app` 나열을 따라가지 않는가(`isRealDirPath`가 구간마다 `lstat`으로 보는가, 작업 공간 루트 자체는 어떻게 다루는가). 앱 폴더 안의 링크 폴더 · 링크 파일(`page.tsx`가 링크)을 따라가지 않는가. 확인과 사용 사이의 틈(TOCTOU)이 ADR-131에 한계로 사실대로 적혔는가. `prisma`나 `src`가 일반 파일일 때 던지지 않게 한 수정이 다른 오류(권한 거부 `EACCES` 등)까지 삼키지 않는가: 삼킨다면 닫힌 쪽(사본 없음 · 라우트 없음)인지, 조용히 "라우트 없음"으로 보여 테스트 작성 역할을 오도하지 않는지 판정한다.
6. **ADR.** ADR-131의 닫은 길 · 남는 길(ⓐ ~ ⓔ) · 상한 값 · 근거가 코드와 맞는가(문장마다). 악용 절차가 적혀 있지 않은가. ADR-128은 해당 한계 문장 세 곳에 표기만 더했는가(`git diff 10a5348...HEAD -- docs/decisions.md`에서 ADR-128 구간의 `-` 줄과 `+` 줄을 대조). ADR 머리줄이 129 · 130 · 131 순서인가.
7. **기존 흐름.** 테스트 작성 세션 프롬프트 스냅샷 · 파이프라인 e2e 기준값 파일이 바뀌지 않았는가. 정상 프로젝트에서 테스트 작성 역할이 받는 입력이 여전히 쓸모 있는가(비ASCII 폴더 이름의 라우트가 빠지는 한계가 ADR에 있는가).
8. **변이.** 구현자의 13종(PR 본문 표)과 겹치지 않게 7종 안팎. 후보: ⓐ 정규식의 끝 고정을 느슨하게(끝의 줄 나눔 허용), ⓑ 경로 그룹 폴더(`folders`)를 검사에서 빼고 URL 조각만 보기, ⓒ 패턴 밖 경로를 빼는 대신 문제 조각만 지우고 싣기, ⓓ 넘친 수를 틀리게 세기(패턴 밖과 상한 초과를 합치지 않기 · 하나 어긋나게), ⓔ 스키마가 넘칠 때 상한까지 잘라 싣기, ⓕ 스키마 파일 자체가 링크일 때의 기존 검사를 빼기(새 상위 폴더 검사만 남기기), ⓖ `prisma`가 일반 파일일 때 다시 던지게, ⓗ 메서드 · 종류 칸에 파일에서 온 글을 그대로 싣게, ⓘ 길이 확인을 정규식 뒤로 옮기기(시험이 순서를 고정하는가). 변이마다 어느 시험이 빨강이 됐는지 표로 낸다. 빨강이 안 된 변이는 차단 후보다(ⓘ처럼 동작이 같아 시험으로 가를 수 없는 것은 그렇게 적는다).
