## 해야 할 것 (수용 기준 순서)
1. **내장 규칙 생성.** 블록 선언이 저장될 때(`blocks.set`) 내장 규칙 `structure.public-api-only`와 `structure.declared-direction`이 부모 요구사항 없이 생기고 `rule.list`에 나온다(`orchestrator/test/structure-check.test.ts`). 정해야 할 것(ADR-127):
   - 생성 시점과 멱등: 선언 저장과 **같은 트랜잭션**에서 없으면 만들고, 있으면 그대로 둔다(판이 올라가도 다시 만들지 않는다). 선언이 없는 프로젝트에는 없다. 옛 DB에 선언은 있는데 내장 규칙이 없는 경우(이 PR 전에 `blocks.set`을 한 프로젝트)를 어떻게 메우는가(기동 때, 또는 다음 `blocks.set` 때. 가장 작은 쪽).
   - 주체 · 기록: 누가 만든 것으로 남는가(오케스트레이터. 사람의 `blocks.set`에 따라 오케스트레이터가 만든다. ADR-100 C2의 계약 등록과 같은 틀이 있으면 맞춘다). 규범 변경 기록 `created`가 남는가, 확인 상태는 무엇인가(사람의 선언에서 나온 규칙이다. 확인할 것 목록에 떠야 하는가를 ADR-100 문장으로 판정). **자동 시작**(규칙마다 실행 1개, ADR-110)이 내장 규칙에도 걸리는가: 내장 규칙은 테스트 작성 대상이 아니고 실행 유형 B(M3-06)가 아직 없다. 이 PR에서는 내장 규칙 생성이 실행을 자동으로 시작하지 않게 하고(근거와 함께 ADR에), 사람의 [실행]이 지금 파이프라인(유형 A)에서 내장 규칙을 대상으로 받으면 어떻게 되는지 정한다(M3-06 전까지 거부가 가장 작다. 거부 사유 값과 화면 문구가 필요하면 표시명 표에 더한다).
   - 대상 블록 · 위험도: M3-01은 내장 규칙 경로에 두 칸을 필수로 하지 않았다. 내장 규칙의 대상 블록(전체? 빈 목록?)과 위험도를 정한다(명세에 문장이 있으면 그것, 없으면 빈 값으로 두고 ADR에).
   - 식별자 · 표시 ID · 진술 문구(화면 정의서 1.1). 필요한 저장 칸이 이미 있는지 먼저 확인하고, 없을 때만 0023을 쓴다.
2. **검사 단계 통합.** 검사 단계가 구조 검사를 실행해 `undeclared-import` 변형에서 해당 내장 규칙의 판정 `fail`을 저장한다. 정해야 할 것(M3-02가 넘긴 6가지 포함):
   - **어디서 · 어떤 트리를 분석하는가.** 판정과 같은 커밋의 깨끗한 체크아웃(`judgeCommit`의 체크아웃. 미추적 · 무시된 파일 0개가 이미 확인된다)에서, **의존성 설치 전**에(설치 산출물이 소스로 섞이지 않게) 돌리는 것이 기본 방침이다. git이 추적하는 파일만 판정 대상이 되게 하고, `node_modules` · 빌드 산출물이 추적 대상이면 어떻게 되는지 정한다(파서의 `unanalyzed` · `packages`를 써서 통과로 읽히지 않게). 파서는 대상 코드를 실행하지 않지만 오케스트레이터 프로세스에서 자식 프로세스를 띄운다: 판정 격리(ADR-026) 밖에서 도는 것이 받아들일 만한 근거를 ADR-125의 확인 결과로 적는다. 엔진의 중단 신호 · 시간 제한을 파서 호출에 잇는다.
   - **판정으로 옮기는 규칙.** 통과는 `outcome.status === 'checked'`이고 그 규칙 종류의 위반이 0건일 때뿐이다. `structure.declared-direction` 위반 → 그 내장 규칙 `fail`, `structure.public-api-only` 위반 → 그 내장 규칙 `fail`. **`structure.no-cycle`**(로드맵에 대응하는 내장 규칙이 없다): 어느 내장 규칙의 실패로 볼지, 판정하지 않고 드러내기만 할지를 명세(JDG-05 · 기획서 3.4)에서 정한다. 새 내장 규칙 식별자를 더하는 것은 명세가 요구할 때만이다(로드맵 완료 흐름과 수용 기준은 두 개만 말한다). 모호하면 "순환은 두 내장 규칙의 판정에 넣지 않고 결과에만 남긴다"와 "방향 규칙의 실패로 본다" 가운데 무결성을 더 지키는 쪽을 고르고 ADR에 적는다.
   - `overlap`(선언이 한 파일을 두 블록에 넣음: 사람이 고칠 일) · `incomplete`(분석하지 못한 대상) · `ParserError`(시간 초과 · 출력 상한 등)는 **통과가 아니다**. 각각 두 내장 규칙의 `fail`인가, 단계 `failed`(판정 실행기 오류 계열)인가를 정한다: 구현 역할이 고칠 수 있는 것(`incomplete`, 큰 순환)은 구현 회귀로, 구현 역할이 고칠 수 없는 것(`overlap`, 파서 설치 문제)은 회귀를 돌려도 소용없으므로 단계 실패로 가는 것이 기본 방침이다. 새 실행 종료 사유 값을 더하면 shared `RunFailureReason` 표와 app 표에 표시명을 더한다(`app/test/run-history-view.test.ts`가 고정한다).
   - `incomplete`를 만드는 허용 형식(`.mdx` · `.graphql` · `.wasm` · `.txt`)과 풀리지 않는 패키지 이름 import(`unresolved` + `checked`)의 취급: 이 PR에서는 파서 결과 그대로(`incomplete`는 통과 아님, `unresolved`는 판정에 넣지 않음) 가고 한계를 ADR에 적는 것이 가장 작다. 픽스처와 완료 흐름이 이 때문에 막히면 멈추고 보고한다.
   - 선언이 없는 프로젝트(`structure === null`)는 구조 검사를 하지 않고 지금과 똑같이 돈다(기존 시나리오 · 파이프라인 e2e 기준값이 그대로여야 한다).
   - 판정 기록: 내장 규칙의 판정 기록에 무엇을 남기는가(위반 건수, 위반 목록의 상한, `ParserError.code`). 위반의 파일 경로는 구현 역할이 정할 수 있는 글이다: 기록 · 화면 · 세션 입력에 실을 때 상한과 표시 값 변환을 거친다. `ParserError.message`는 싣지 않는다(`code`만).
   - **병합 재검사**에도 같은 구조 검사가 도는가(병합 커밋의 깨끗한 체크아웃). 검사 단계와 같아야 한다.
3. **회귀 규칙.** 대상이 그 내장 규칙인 실행은 회귀 규칙에 따라 `failed`다(1번에서 유형 A가 내장 규칙을 대상으로 받지 않기로 했다면, 이 수용 기준을 무엇으로 시험하는지 이슈 문장과 맞춰 정한다: 엔진 수준에서 대상이 내장 규칙인 실행을 직접 만들어 검사 → 구현 회귀 → 상한 초과 → `failed`를 단언할 수 있으면 그렇게 한다. 수용 기준을 만족할 수 없으면 멈추고 보고한다).
4. **대상이 아닌 실행에서 내장 규칙이 깨질 때.** ADR-118은 "내장 구조 규칙이 실패하면 판단 없이 지금처럼 다룬다(검사 → 구현 회귀, 병합 재검사 → `check_failed`)"고 이미 정했다. 내장 규칙은 폐기 · 대체의 대상이 아니므로(ADR-100 B⑨) 판단 세션을 열지 않고 구현 회귀로 간다(구현 역할이 자기 코드를 고친다). 회귀 상한을 넘으면 실행 `failed`. 구현 세션이 받는 "앞 시도의 사유"에 구조 위반을 어떻게 싣는가(구현 역할이 고치려면 무엇을 어겼는지 알아야 한다: 내장 규칙 이름과 위반한 파일 쌍. 이 글은 구현 역할 자신의 파일 경로라 같은 역할로 돌아가는 글이다. 상한과 표시 값 변환을 둔다). "새 규칙 쪽의 폐기"가 필요한 경우(새 규칙의 요구 자체가 블록 선언과 양립할 수 없을 때)를 이 PR에서 다루는가: 가장 작은 쪽은 "구현 재시도만, 상한 초과면 실패, 새 규칙의 폐기는 구현 역할의 이의 제기(기존 도구)로"다. 이 처리를 ADR-127에 적고 시험이 단언한다.
5. **준수 지표와 추적성 결함.** 내장 규칙이 준수 지표의 판정 가능 항목에 들어가고 추적성 결함(부모 없는 규칙)에서는 빠짐을 `orchestrator/test/verification.test.ts`가 단언한다. 판정 기록이 아직 없는 내장 규칙(선언 저장 직후)이 지표에서 어떻게 세어지는가(다른 규칙의 "판정 없음"과 같게).
6. **폐기 · 대체 거부.** 규칙 작성 역할의 폐기 도구와 대체 도구가 이 내장 규칙을 `denied`로 거부하고 규칙이 효력 상태로 남음을 단언한다(M7-09의 기존 거부가 새로 만든 내장 규칙 행에도 그대로 듣는지 확인하고 시험으로 고정). 이의 제기 도구가 내장 규칙을 겨눌 때도 같은지 본다. 사람의 `rule.update`로 내장 규칙을 고치거나 사람이 폐기할 수 있는가(명세에서 정하고 ADR에). 화면: 내장 규칙이 `rule.list`에 나오면 SCR-03에 보인다. 기존 화면이 `builtin` 규칙을 이미 그릴 수 있는지 확인하고, 깨지는 곳(부모 링크, 편집 버튼, 확인 버튼)이 있으면 **그 최소만** 고쳐 화면 시험으로 고정한다(그때는 화면 e2e · 스모크도 완료 조건이다). 새 화면 요소는 만들지 않는다.

## 반드시 지킬 것 (무결성)
- 엔진 · 단계 코드에 확인 상태를 들이지 않는다(구조 시험의 `/confirm/i` 금지). 실행 종료 상태는 `runEnding()` 한 곳. 규범 변경 기록 쓰기는 허용 목록의 파일에서만(목록을 고치면 이유를 PR 본문에). 구조 시험 `integrity.test.ts`를 느슨하게 만들지 않는다.
- 구조 검사의 결과는 파서 출력에서만 나온다(JDG-01: 판정 근거는 실행기 결과만. 세션 보고 문장 · 에이전트의 글을 쓰지 않는다). 오케스트레이터가 위반을 스스로 계산하지 않는다(ADR-033).
- 구조 검사가 **돌지 않았는데 통과로 저장되는 길**이 없어야 한다: 파서 호출 건너뜀, 예외 삼킴, 선언을 못 읽음(`StoredBlockDeclarationError`), 중단 신호, 시간 초과 각각에서 닫힌 쪽임을 시험으로 고정한다.
- 선언이 판정 도중 바뀌는 경우(사람이 `blocks.set`): 판정은 시작 때 읽은 판을 쓰고, 판정 기록에 그 판 번호를 남긴다.
- 방어 · 판정 규칙마다 "빼면 빨강"인 시험을 두고 변이 결과 표를 PR 본문에 낸다.
- 기존 시나리오와 파이프라인 e2e의 기준값(기록 순서 · 실행 수)이 바뀌면 안 된다(선언 없는 프로젝트는 지금과 같다). 구조 검사가 도는 새 흐름은 단위 · 통합 시험으로 고정하고, 파이프라인 e2e 새 파일은 이 PR에서 더하지 않는다(로드맵의 완료 흐름 시험은 뒤 이슈 몫. 더해야 수용 기준을 만족한다고 판단되면 묶음 시간과 함께 보고한다).
- `docs/spec/*` · `docs/roadmap.md` · `CLAUDE.md`를 고치지 않는다. 의미 있는 단위마다 로컬 커밋을 남긴다(컨테이너 재시작 대비).
- 바뀐 파일이 45개를 넘을 것 같으면 멈추고 보고한다. 쪼갤 경계는 "(1 · 5 · 6) 내장 규칙의 생성 · 지표 · 거부" / "(2 · 3 · 4) 검사 단계 통합과 회귀"다. 제품 흐름을 바꾸는 결정(예: 선언이 있으면 구조 검사 실패 때문에 기존 완료 흐름이 막힌다, 사람 단계가 새로 필요하다)에 닿으면 구현하지 말고 멈춰서 근거와 영향 범위를 보고한다(조율자가 사람 결정 이슈로 올린다).
- 완료 조건 명령: 설치 · 린트 · 타입 · 빌드 · 형식 · 단위 테스트(격리 `TMPDIR`, 알려진 두 시험만 실패 허용) · 파이프라인 e2e(픽스처 설치 뒤, 격리 `TMPDIR`, PR 전 한 번). 화면을 고쳤으면 화면 e2e · 스모크.

## 보고
공통 지침의 보고 항목에 더해: 수용 기준별 한 일과 근거 시험, 정한 것들(내장 규칙의 주체 · 확인 상태 · 자동 시작 · 대상 블록, 분석하는 트리와 시점, 순환 · `overlap` · `incomplete` · `ParserError`의 판정, 대상이 아닌 실행에서의 처리, 판정 기록에 남기는 것)과 근거 문장, 더한 실행 종료 사유 값과 표시명, 마이그레이션 사용 여부, 구조 검사의 비용(픽스처에서 검사 단계가 얼마나 늘었는가), 변이 결과 표, M3-06(#51)에 넘길 사실, 발견했지만 고치지 않은 것. 짧게, 한국어로.
