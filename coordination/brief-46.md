## 해야 할 것
1. **블록 선언 모델과 저장.** shared에 블록 선언 스키마(이름, 종류, include, public, dependsOn, risk)를 둔다. 칸의 뜻과 허용 값은 명세에서 가져오고, 명세에 없는 것은 뒤 이슈(M3-02 파서의 블록 판정, M3-03 구조 검사)가 읽을 수 있는 가장 작은 모양으로 정해 ADR-122에 적는다(이름 중복, 없는 블록을 가리키는 `dependsOn`, 순환, include 패턴이 겹칠 때, 프로젝트 폴더 밖을 가리키는 패턴은 저장 때 거부할지). 저장 위치는 `$BIVE_HOME/projects/<id>/`(ADR-005). 파일인지 DB 표인지는 수용 기준 문장과 기존 저장 방식(프로젝트 DB)을 보고 정한다(변경 이력 · 무결성 감시를 생각한다. 파일이면 변조 감시가 어떻게 되는지 ADR에 적는다). RPC `blocks.get` · `blocks.set`이 왕복한다.
2. **누가 블록 선언을 쓰는가.** `blocks.set`은 사람 주체만 받는다(에이전트 · 오케스트레이터 주체는 `-32020`). 에이전트 역할에게 블록 선언을 쓰는 도구를 주지 않는다(에이전트가 선언을 고쳐 구조 검사를 우회하는 길, ADR-005). 구조 시험으로 "에이전트 경로에서 블록 선언 쓰기가 없다"를 고정한다. 블록 선언을 사람이 바꾼 기록을 어디에 남기는지(승인 기록의 새 행동 값이 필요하면 스키마를 넓히기만 한다) 가장 작은 방법으로 정해 ADR에 적는다.
3. **규칙의 대상 블록과 위험도.** 규칙에 대상 블록 1개 이상과 위험도(`low` · `medium` · `high`)를 둔다. `propose_rule`(과 새 규칙을 만드는 `supersede_rule`)에 둘이 없으면 도구 오류다. 사람의 규칙 편집 RPC에서도 둘을 고칠 수 있게 할지는 이슈 범위를 보고 정한다(작으면 넣고, 아니면 M3-19 몫으로 넘기고 보고에 적는다).
   - **이미 있는 규칙 행**(대상 블록 · 위험도가 없는 옛 행)은 이행에서 지어내지 않는다. 읽기 스키마는 옛 행의 빈 값을 받아야 한다(조이면 옛 행이 깨진다). "필수"는 새로 만드는 경로에서 강제한다. DB 제약을 둔다면 새 쓰기만 막는 방식이어야 한다.
   - **블록 선언이 없는 프로젝트.** 지금 모든 픽스처 · 파이프라인 e2e · 완료 기준 흐름은 블록 선언 없이 돈다. 여기서 정해야 한다. 조율자의 기본 방침은 **가장 작은 쪽**이다: 대상 블록과 위험도는 도구 수준에서 늘 필수. 블록 선언이 **있으면** 대상 블록 이름이 모두 선언에 있어야 한다(없는 이름은 도구 오류). 블록 선언이 **없으면** 이름을 선언과 대조할 수 없으므로 받은 이름을 그대로 저장한다(그 사실이 조회 결과에서 드러나야 한다. 예: 선언 없음 표시). 이 방침이 뒤 이슈(M3-03 구조 검사는 선언이 있을 때만 판정한다)와 맞는지 확인하고 ADR-122에 적는다. **"선언이 없으면 규칙을 만들 수 없다"(모든 흐름에 `blocks set` 단계가 필요해진다)로 가야 한다고 판단되면 구현하지 말고 멈춰서 근거와 영향 범위(고쳐야 할 시나리오 · e2e · 흐름 수)를 보고한다.** 제품 흐름을 바꾸는 결정이라 조율자가 사람 결정 이슈로 올린다.
   - 가짜 어댑터 시나리오의 `propose_rule` 호출 전부에 대상 블록과 위험도를 더한다. 파이프라인 e2e의 기준값(기록 순서 · 실행 수)이 바뀌면 안 된다.
4. **세션의 읽기 전용 사본.** 세션 작업 디렉터리에 블록 선언 사본을 놓는다(역할마다 필요한지 정한다: 규칙 작성 역할은 대상 블록을 고르려면 필요하다. 테스트 작성 · 구현 역할은 블록 경계를 알려면 필요하다). 쓰기 시도는 경로 가드가 거부한다(기존 가드에 경로를 더하는 방식. 가드를 빼면 빨강인 시험). 사본이 원본과 달라지는 경우(세션 도중 사람이 `blocks.set`)를 어떻게 다루는지 한 줄. 선언이 없으면 사본도 없다. 사본의 글은 사람이 쓴 것이지만 세션 입력이므로 기존 규범 자료의 표시 값 처리(`displayText`)와 길이 상한을 따를지 확인한다.
5. **확인할 것의 위험도 칸.** `confirmation.list` 항목에 규칙의 위험도 칸(선택 칸. 값이 없으면 없음)을 더하고, 확인할 것 화면의 위험도 칩이 그 값으로 살아나는지는 **범위 밖**이다(M3-19 · M3-35 몫). 응답 칸만 더하고 shared 스키마 · 시험을 맞춘다. 과하면 하지 않고 보고에 적는다.
6. **CLI와 픽스처.** `pnpm --filter @bive/app cli blocks set <dir> <json>`이 `blocks.set`을 부른다(CLI의 조회 전용 제한과 어떻게 어울리는지: 쓰기 명령은 사람 주체로만. 기존 CLI에 쓰기 명령이 있는지 보고 같은 방식으로). 예제 `fixtures/blocks/sample-next-app.json`(블록 `auth` 위험도 high, `lib` 위험도 low)이 픽스처의 실제 폴더 구조와 맞음을 `app/test/cli-blocks.test.ts`가 단언한다(include 패턴이 실제 파일을 가리키는지까지).
