## 해야 할 것
1. **선언** (수용 기준 1). `propose_rule`이 규칙마다 "새 동작" 또는 "기존 동작 유지"의 선언을 **필수**로 받는다(칸 이름과 값은 네가 정한다. 예: `behavior: 'new' | 'existing'`). 빠지거나 모르는 값이면 `invalid_args`(기존 인자 검증과 같은 갈래). 선언은 그 규칙의 생성 기록(규범 변경 기록 `created`)에 남는다(상세 칸의 스키마를 넓힌다. 옛 기록(선언 없음)은 읽을 때 "모름"이고 아래 3의 규칙으로 다룬다). 규칙 작성 역할의 작업 지시(프롬프트)에 선언의 뜻과 고르는 기준(이미 구현돼 지금 코드가 이 진술을 지키는가)을 고정 문장으로 더한다. 규칙 작성 세션은 프로젝트 코드를 볼 수 있는가(역할의 접근 범위): 볼 수 없으면 선언은 추정이고 그래서 3(어긋남의 처리)이 중요하다는 것을 ADR에 사실대로 적는다.
   - 대체 도구(`supersede_rule`, M7-09)가 만드는 새 규칙에도 같은 선언이 필요한가(ADR-110이 이 이슈에 넘긴 질문): **조율자 권고는 "필요하다"**(대체로 생긴 규칙도 자동 시작의 대상이라 유형을 정해야 한다). 코드를 보고 대체로 생긴 규칙이 실제로 자동 시작되는지 확인해 결정하고 ADR에 적는다. 필수로 하면 기존 시험 · 시나리오의 `supersede_rule` 호출을 모두 고친다.
   - 사람이 직접 만든 · 고친 규칙(M7-03, ADR-109: 진술 편집 뒤 자동 시작)의 유형: 사람의 편집에는 선언이 없다. 지금 동작(유형 A로 자동 시작)을 **그대로 둔다**(이 이슈의 범위는 규칙 작성 역할의 선언이다. "진술 편집 뒤 자동 시작"은 로드맵 "남은 결정"의 사람 몫이다). ADR 한계에 적는다.
2. **유형 고르기** (수용 기준 2). 자동 시작(`runs/auto-start.ts`)이 규칙의 선언으로 유형을 고른다: 새 동작 → 유형 A, 기존 동작 → 유형 C(M3-06의 유형 C 그대로: Green 확인, 구현 생략). 실행마다 대상 규칙 1개(M7-19 그대로). 시작 근거 · 하루 한도 · 프로젝트당 실행 1개 · 효력 확인 · 설정 확인의 기존 문은 그대로다. 선언을 읽는 자리는 생성 기록 하나다(다른 곳에 복사해 두지 않는다). 다시 시작(M7-12) · 자동 보강(M3-54, 이미 유형 C 보강) · 요구사항 재판단으로 생긴 규칙의 자동 시작도 같은 규칙을 타는지 길마다 확인하고 시험한다(보강 실행의 유형과 연결은 그대로여야 한다).
   - 유형 C로 자동 시작한 "기존 동작" 실행은 **보강 실행이 아니다**(`isReinforcementRun` 거짓: 변이 주입 단계는 `skipped`(`run_type`), "더하기만" 없음). ADR-136 한계 (b)("유형 C는 통과하는 테스트면 병합된다")가 이 실행에 그대로 남는다는 것을 ADR에 적는다: 기존 동작이라고 선언된 규칙의 인수 테스트가 아무것도 검사하지 않아도 Green이면 병합된다. 그 뒤 유형 A가 아니므로 변이 주입도 돌지 않는다. 이것이 사람 결정(ADR-110)이 받아들인 범위인지, 줄일 가장 작은 장치(예: 기존 동작 실행의 병합 뒤에도 변이 주입 대상에 넣기)가 이 이슈의 범위 안인지 판단한다. **범위 밖이면 고치지 말고 한계와 후속 후보로 보고한다.**
3. **선언이 실제와 다른 경우** (수용 기준 3, ADR-110이 이 이슈에 넘긴 질문). 조율자 결정(ADR-151에 "조율자 결정"으로 적는다. 코드에서 성립하지 않으면 멈추고 보고):
   - (가) "새 동작"이라 했는데 Red 확인에서 대상 규칙의 인수 테스트가 이미 통과: **지금 동작 그대로 실패**(테스트 작성 재시도 상한 뒤 `test_retry_limit` 등 기존 종료). 유형을 실행 도중에 바꾸지 않는다. 대상 규칙을 빼지 않는다.
   - (나) "기존 동작"이라 했는데 Green 확인에서 실패: **지금 유형 C의 동작 그대로 실패**(M3-06이 정한 Green 확인 실패의 길: 테스트 작성 회귀 · 상한 뒤 실패). 유형을 도중에 A로 바꾸지 않는다.
   - 두 경우 모두 **자동으로 반대 유형의 새 실행을 만들지 않는다**(선언이 틀렸다는 사실만으로 오케스트레이터가 판단을 뒤집으면 Red 확인의 뜻이 약해진다: "실패해야 한다"가 "실패하지 않으면 다른 길로"가 된다). 실패한 실행의 종료 사유 · 기록에서 사람이 "선언과 실제가 달랐다"를 알 수 있게 하는 가장 작은 표시(기존 종료 사유의 상세에 선언 값을 싣는 정도)를 둔다. 그 뒤의 길은 사람의 규칙 편집 · [실행] · 규칙 작성 역할의 다음 판단(다시 시작 M7-12가 이 실패를 원인으로 삼는가: 지금 규칙대로 두고 무엇이 일어나는지 ADR에 적는다. 다시 시작이 같은 선언으로 같은 실패를 되풀이하지 않는지 확인: 되풀이하면 그 고리를 막는 것까지가 이 이슈다).
   - 어느 경우에도 실행의 대상 규칙 수가 줄지 않는다(이미 통과하는 테스트의 규칙을 대상에서 빼고 진행하는 코드 경로가 없음을 `engine.test.ts`가 단언하고, 구조 시험이 필요하면 더한다).
4. **옛 기록과 시나리오**: 선언이 없는 옛 생성 기록의 규칙이 자동 시작될 일이 있는가(대기 중이던 원인 · 재기동 복구 · 다시 시작). 있으면 유형 A로 본다(지금 동작과 같음)를 ADR에 적고 시험한다. 가짜 어댑터 시나리오(`scenarios/*.yaml`)와 시험의 `propose_rule` 호출 전부에 선언을 더한다. `happy-path`의 둘째 규칙(이미 통과하는 동작)은 "기존 동작"으로 선언해 유형 C로 병합되게 하고(ADR-110 맥락의 그 문제가 풀렸음을 파이프라인 e2e가 보인다), 기존 e2e 단언 가운데 그 실행이 실패한다고 고정한 것이 있으면 이 이슈가 바꾸는 동작이므로 고친다(고친 단언 목록을 보고).
5. **ADR-151**: 선언의 칸 · 값 · 저장 자리, 대체 도구의 선언, 사람 편집 규칙의 유형, 유형 고르기와 길마다의 적용, 어긋남의 처리 (가) (나)와 근거, 다시 시작과의 관계, 옛 기록, 한계(유형 C의 검출력 · 선언이 추정이라는 점 · 그 밖), 다시 정하는 조건(ADR-110 "다시 볼 조건"). `docs/architecture.md`(도구 표 · 자동 시작 문단)를 사실에 맞게 고친다. ADR-110의 본문은 고치지 않는다.
