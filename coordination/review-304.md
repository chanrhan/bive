## 구현자가 정한 것 (네가 타당성을 판정한다)
- 정의는 오케스트레이터 `verification/summary.ts` 한 곳. 새 메서드 없이 응답을 넓혔다: `rule.list` 결과에 `traceability`(선택 칸), `verification.summary`에 `traceability` · `unrulable{count,total}`(**필수 칸**).
- 결함 정의: 효력 있는 자식 규칙이 없는 요구사항(자식이 모두 폐기 · 잠정뿐 포함, 규칙 작성 세션 진행 중 포함) = 규칙 없는 요구사항. 효력 있는 비내장 규칙의 부모가 `null`이거나 삭제됨 = 부모 없는 규칙. 뺌: 규칙화 불가 · 삭제된 요구사항, 내장 규칙(구조 · 계약 검사), 폐기 · 잠정 · 삭제 규칙.
- `requirement.markUnrulable(id, reason)`: 사람만(에이전트 -32020), 공백만인 사유 -32001, 4000자 초과 -32001, 없는 요구사항 -32004, 삭제됨 · 이미 표시됨 · **효력 있는 자식 규칙 있음** -32009(`data.reason`으로 구분). 낙관적 잠금 없음. **승인 기록을 남기지 않는다**(근거: ADR-100의 문장과, 행동 값을 더하려면 마이그레이션 필요). 같은 트랜잭션에서 확인됨(근거 `requirement_record`). 규칙 작성 세션 · 재판단을 띄우지 않는다. 풀기 없음.
- 화면은 서버의 `rule.list.traceability`만 쓰고 결함을 다시 세지 않는다. 요구사항 화면은 규칙 작성 알림에도 `rule.list`를 한 번 읽는다. 규칙화 불가가 결함 표시보다 앞선다.
- 비율 카드는 백분율 대신 "N / M" 표기, 분모(삭제되지 않은 요구사항 전부)가 0이면 '없음'. 추적성 결함 카드 수에 부모 없는 규칙 포함, 카드 이동은 SCR-02만.
- 남긴 한계: 표시 뒤에도 규칙 작성 세션이 뜰 수 있어 "규칙화 불가이면서 규칙 있음"이 될 수 있다, 검증 화면이 규칙 작성 알림 · 요구사항 변경에 다시 읽지 않는다.
