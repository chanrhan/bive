## 해야 할 것
1. **규칙마다 실행 1개.** `runs/auto-start.ts`가 세션이 만든 규칙 N개에 대해 실행 N개를 생성 기록(`created`) 순서대로 만든다. 실행마다 대상 규칙 1개, `auto_start` 항목 1건(원인은 그 규칙의 `created` 순번 1건). N개의 실행 저장과 항목 쓰기는 트랜잭션 1개다(일부만 생기는 경우가 없다). 원자성 시험은 "k번째 `auto_start` 항목 쓰기만 실패"시켜 아무것도 남지 않음을 단언한다(첫 쓰기부터 막는 시험만으로는 부족하다).
   - 멱등: 같은 세션을 두 번 처리해도 실행 수가 늘지 않는다. 지금의 "같은 원인 순번을 쓰는 `auto_start`가 있으면 `duplicate`" 검사를 N개에 맞춘다. 일부 원인만 이미 쓰인 상태(저장소 밖 변조)의 처리를 정해 시험한다.
   - 생략: 하루 한도가 비었거나 닿았으면 N개 모두 만들지 않고 생략 기록은 세션마다 1건이다(지금과 같다).
   - 첫 실행만 바로 판정 · 시작하고 나머지는 실행 대기에 들어간다(`engine.onRunCreated`를 실행마다 부를 때의 순서와 동시 1개 트리거를 확인한다).
2. **시작 근거 대조.** 오케스트레이터가 시작한 실행은 대상 규칙이 정확히 1개이고 원인이 그 규칙의 `created` 1건이어야 한다. 아니면 `run_without_log`. 0016의 `started_by` CHECK(원인 순번 배열)는 그대로 두고(길이 1을 DB에서 강제할지는 ADR에 적는다. 표 재구성은 피한다), 읽기 스키마와 엔진 대조에서 막는다. 사람의 [실행]은 지금처럼 규칙 여러 개를 한 실행으로 받는다.
3. **대기 실행의 시작 때 하루 한도 재확인(조율자 결정, ADR-110).** 대기 중인 자동 시작 실행이 시작할 차례가 되면 프로젝트 하루 한도를 다시 본다(`validateSettingsForAutoStart` + `projectDailyBudget` + `dailyBudgetReached`). 비었거나 닿았으면 작업 폴더와 브랜치를 만들지 않고 끝내며 다음 대기로 넘어간다. 사람이 시작한 대기 실행은 지금처럼 시작한다.
   - 정할 것(ADR-111): 끝나는 상태와 사유의 이름. 종료 상태는 반드시 `runEnding()`을 거친다(엔진 실행 패치에 `status` 리터럴 금지 구조 시험이 있다). 기존 상태 · 사유 enum 안에서 고르는 쪽이 작다(예: `budget_exceeded`). 새 값을 더하면 shared enum · DB CHECK · 화면 표시명 · 검증 화면이 함께 바뀌므로 근거를 적는다. 한도가 비어서 끝난 것과 닿아서 끝난 것을 실행 기록에서 구분할 수 있어야 한다(수용 기준 "그 종료 사유가 실행 기록에 남고").
   - 줄 선 자동 시작 실행이 여러 개일 때 한 번에 모두 끝나는지, 차례가 올 때마다 하나씩 판정하는지 정한다. 자리를 비우고 다음 대기를 깨우는 것이 재귀 · 무한 반복이 되지 않음을 시험한다.
   - 기동 때(`startQueuedRuns`)와 실행이 끝났을 때(`#advanceQueue`) 두 경로 모두에 적용됨을 시험한다.
   - 한도를 다시 채운 뒤 이미 끝난 실행을 되살리지 않는다(되살리기는 범위 밖. ADR에 한계로 적는다).
4. **파이프라인 e2e.** `orchestrator/e2e/pipeline/auto-start-per-rule.test.ts`: 규칙 2개(둘째는 이미 통과하는 동작)를 만드는 시나리오(`happy-path`가 그렇다)로 요구사항을 저장하면 EXE-001 `merged`, EXE-002 `failed`(종료 사유 `test_retry_limit`), 두 실행이 함께 `running`인 조회 결과가 없음을 단언한다. 새 파일은 `scripts/check-pipeline-groups.py`가 보는 두 묶음 가운데 하나에 넣는다(시간이 긴 시험이다. 묶음의 시간 여유를 확인한다). 기존 e2e와 `harness.saveRequirement`의 자동 시작 기대(실행 수)를 새 흐름에 맞게 고친다.
