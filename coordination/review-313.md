1. **범위와 기존 동작.** `git diff 08bf069...HEAD --stat`. `docs/spec/*` · `docs/roadmap.md` · `CLAUDE.md` · 워크플로가 바뀌지 않았는가. 기존 시험 파일의 `-` 줄을 전부 읽는다. 특히 **`mutation.test.ts`의 -329**: 하네스를 옮긴 것뿐인가, 기존 단언(M3-07의 것: 검증됨 · 생존 저장, 거부 13종, 판정 불가 각각, 순서, 예산, 세션 폴더, 변이가 ref에 남지 않음)이 **하나도 빠지거나 약해지지 않았는가**(main의 파일과 시험 이름 목록을 대조: `grep -n "it(\|describe(" `로 양쪽 목록을 뽑아 빠진 이름을 찾는다). `engine.test` · `judge-runner` · `integrity.test` · `test-writer.test` · `auto-start.test`의 고친 단언이 이 이슈가 바꾸는 동작인가. **기존 파이프라인 e2e**(17개 파일)의 단언이 고쳐지지 않았는가: 블록 선언이 없는 픽스처에서는 유형 A의 변이 단계가 여전히 `skipped`(사유만 바뀜)라는 설명이 사실인가, 블록 선언이 있는 e2e(`run-type-b` 등)에서는.
   - 유형 B · D · 보강 아닌 유형 C의 동작이 그대로인가(변이 단계가 돌지 않음을 코드에서 확인하고, 네가 "유형 B · D에서 변이 단계 돌리기" 변이를 넣을 방법을 찾는다).
   - `judge/runner.ts`의 `requireServerAlive`가 주어지지 않으면 판정 러너의 동작이 글자까지 같은가(검사 · Red · Green · 병합 재검사).
2. **무결성: 자동 보강이 기존 자동 시작의 문을 건너뛰지 않는가 (가장 중요, NFR-01 · ADR-100).** `runs/auto-start.ts`(+139)와 `engine/start-basis.ts`(+57)를 끝까지 읽는다.
   - 보강 실행이 만들어지는 **모든 길**을 찾는다(`observe`의 `merged` 이벤트 말고 다른 호출 자리가 있는가). 각 길에서 설정 확인 · 하루 한도 · 프로젝트당 실행 1개(대기) · 승인 단계 자리의 효력 확인 · 시작 근거 대조가 **기존 자동 시작과 같은 함수**로 도는가(복사한 다른 구현이 아닌가). 문에 걸려 생략되면 **로그만 남는다**: 기존 자동 시작이 생략을 어떻게 남기는지(M3-34 #262가 다룰 "자동 시작 생략의 기록")와 같은 수준인가, 사람이 "변이 생존인데 보강이 안 생겼다"를 알 길이 있는가(규칙의 변이 상태는 '생존'으로 남는다: 그것으로 충분한지 판정. 비차단 가능).
   - **위조 원인**: `reinforcementMismatch`가 막는 것과 못 막는 것. 원인 변이 결과가 (가) 다른 규칙의 것 (나) '검증됨' · '미검증' (다) 병합되지 않은 · 실패한 실행의 것 (라) 유형 C(재주입)의 생존 기록 (마) 이미 다른 보강에 쓰인 것 (바) 없는 ID일 때 각각 거부되는가. DB 트리거와 대조 함수의 **두 겹**인지, 한쪽만인지. 누가 이 길을 부를 수 있는가(에이전트 도구 · RPC에서 닿는 경로가 있는가: 없어야 한다. `integrity.test.ts`의 "연결 쓰기는 `auto-start.ts` 한 곳" 구조 시험 확인).
   - **고리와 중복**: 보강 실행(유형 C)의 재주입 결과가 '생존'으로 기록될 때 그것이 새 보강의 원인이 되지 않는가(트리거 "원인 = 유형 A의 생존"과 코드의 조건). 같은 규칙에 열린(대기 · 진행 · 중단) 보강 실행이 있으면 또 만들지 않는가, **실패로 끝난 뒤** 같은 변이 결과로 다시 만들지 않는가(`mutation_result_id UNIQUE`). 같은 규칙의 **다른** 유형 A 실행이 또 생존을 내면 새 보강이 생기는가(생겨야 하는가: 문서로 판단. 무한히 반복되는 길: 유형 A 실행 → 생존 → 보강 실패 → 사람이 규칙을 다시 [실행] → 생존 → 보강 … 은 사람이 낀 고리라 괜찮다. 사람 없이 도는 고리가 있는지만 본다: 자동 시작된 유형 A 실행(규칙 작성 세션의 새 규칙)이 생존 → 보강 → 보강 실패 뒤 무엇이 또 자동으로 시작되는가).
   - **기동 복구 한계**: "병합 저장 뒤 · 생성 전에 재기동하면 그 보강은 만들지 않는다". 그 창이 얼마나 넓은가(같은 트랜잭션이 아닌가, 이벤트 처리가 비동기인가). 놓친 보강은 규칙이 '변이 생존'으로 남을 뿐 조용히 사라진다: ADR-100 B④("자동")와 A17("실패하면 검토 대기열")의 뜻에서 받아들일 수 있는 한계인지, 기동 때 "연결 없는 생존 기록"을 다시 보는 것이 이 이슈의 필수인지 판정한다(기존 자동 시작이 같은 창에서 어떻게 하는지 선례를 본다. 선례가 "놓친다"면 일관된 한계, "복구한다"면 차단 후보).
3. **보강 실행 자체의 무결성.**
   - 보강 실행(유형 C)이 판정 없이 병합되지 않는가: Green 확인 · 검사 · **재주입** · 병합 재검사 · 소스 변경 거부 세 겹이 그대로 도는가. 재주입이 **검사 뒤 · 병합 앞**인가. 재주입에서 '변이 검증됨'이 아니면(생존 · 판정 불가) 병합으로 가는 길이 없는가.
   - **재주입이 정말 같은 변이인가**: 연결된 변이 결과의 경로 · 바꿀 글 · 바꾼 글을 어디서 읽는가(저장된 원문). 보강의 테스트 작성 세션이 그 저장 값을 바꿀 길이 없는가. 재주입 대상 커밋은 보강 실행의 판정 커밋(새 테스트 포함)인가. 기준 브랜치가 그 사이 바뀌어 변이가 적용되지 않으면(바꿀 글이 없음 · 여러 번) `judge_runner_error`로 닫히는가. 재주입 변이가 어떤 ref · 작업 트리에도 남지 않는가(시험 단언 + 네가 예외 경로를 한 번 만들어 확인).
   - **보강의 테스트 작성이 대상 규칙 폴더를 통째로 바꾼다(구현자 한계)**: 세션이 기존 테스트를 다시 쓰지 않으면 **기존 인수 테스트가 지워진 채 병합될 수 있다**. 유형 C의 Green 확인은 "새 테스트 전부 통과"만 본다 → 기존 테스트를 지우고 변이만 잡는 테스트 하나로 바꿔도 Green · 재주입 통과 · 병합. 이것은 그 규칙의 **검증 범위가 줄어드는 병합**이다(무결성 NFR-01: 인수 테스트는 규칙의 채점 기준). 유형 C 일반(ADR-136)에서도 같은가(테스트 작성 세션은 원래 대상 규칙 폴더를 쓸 수 있다: 유형 A의 다시 쓰기와 같은 수준인가), 보강에서 새로 생긴 위험인가를 가르고, 보강은 "더한다"가 뜻이므로(B④ "테스트 보강") 기존 케이스가 사라지지 않음을 지키는 장치(예: 보강 전 케이스 이름이 보강 뒤에도 있어야 함)가 이 이슈의 필수인지 판정한다. 필수로 보면 차단(재현: 가짜 에이전트가 기존 테스트를 지우고 변이만 잡는 테스트로 바꾸는 대본 → 병합되는지). 한계로 둘 수 있다고 보면 근거와 함께 비차단.
   - **"잡는 척" 테스트**: 테스트 작성 세션이 변이 자료(바꾼 글)를 받아, 서버 응답이 아니라 소스 파일의 글자를 읽어 단언하는 테스트를 쓰는 길. 정적 검사가 `fs` · `child_process` 가져오기만 막는다고 한다: `node:fs` · `fs/promises` · 동적 `import('fs')` · `require` · `process.binding` · `Bun` · `fetch('file://…')` · vitest의 `import.meta.glob` 등으로 우회되는가(지금 정적 검사의 범위를 읽는다). #117 계열의 기존 한계이면 그 사실이 ADR-143 한계에 적혔는지만 보고, 이 PR이 그 위험을 **키웠는지**(변이 자료가 정확한 글자를 알려 준다) 한 줄로 판단한다.
