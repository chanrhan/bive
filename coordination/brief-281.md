## 배경
Red 확인은 테스트 작성 커밋을 실제로 돌려 "대상 규칙의 케이스가 전부 실패"인지 본다. 통과한 케이스가 있거나 수집 오류가 나면 테스트 작성으로 회귀하고, 다음 테스트 작성 세션은 "앞 시도의 사유"를 받는다(`steps/test-writing.ts`의 `describeUnmet`). 그 사유에는 Red 확인의 **통과 케이스 이름**(`notFailedCases`)과 **수집 오류 메시지**(`problems`)가 거르지 않고 실린다. 인수 테스트가 앱 코드를 import하면 이미 병합된 **구현 코드**가 실행 중에 케이스 이름과 오류 메시지를 지어낼 수 있다. 그러면 구현 역할의 글이 테스트 작성 역할(채점 기준을 쓰는 역할)의 입력으로 들어간다(역할 분리 약화, ADR-100). M3-37은 규범 자료 · 인용 출처의 케이스 이름만 걸렀다.

## 해야 할 것 (수용 기준 순서)
1. **통과 케이스 이름의 대조.** 앞 시도 사유에 실리는 Red 확인의 통과(실패하지 않은) 케이스 이름이 `norms/case-names.ts`의 대조 기준을 지나게 한다. 모르는 이름은 같은 표기("알 수 없는 케이스 N건")로 바뀌고 원문은 세션 입력에 들어가지 않는다.
   - **기준 글의 출처를 정한다.** M3-37은 "규칙마다 최근 판정 커밋의 인수 테스트 파일"을 썼다. 여기서는 판정 대상이 **방금 Red 확인을 돈 테스트 작성 커밋의 대상 규칙 폴더 파일**이다(테스트 작성 역할 자신이 쓴 파일). 그 커밋의 git 객체에서 읽어(작업 트리 아님, `--no-replace-objects`, 커밋 형식 검사, 일반 파일만: 기존 함수를 그대로 쓴다) 리터럴과 대조한다. 커밋을 읽지 못하면 전부 모르는 이름(닫힌 쪽). 어느 커밋 값을 쓰는지(Red 확인 단계 결과에 남은 커밋)와 그 값이 변조될 수 없는 곳에서 오는지 확인해 ADR에 적는다.
   - 사유가 **저장되는 곳**(단계 시도의 종료 상세 등)에 원문이 남는가를 확인한다. 저장된 원문이 다음 세션 입력 말고 다른 길(화면, 다른 역할의 규범 자료)로 흐르는지 보고, 흐르면 그 자리도 같은 기준을 지나게 하거나 한계로 적는다. 저장 형식을 바꾸지 않는 것이 기본이다(옛 행을 깨지 않는다).
   - `orchestrator/test/test-writer.test.ts`가 단언한다: 구현 코드가 지어낸 이름(파일에 없는 이름)이 통과 케이스로 보고되면 세션 작업 지시에 그 원문이 없고 "알 수 없는 케이스 N건"이 있다. 파일에 리터럴로 있는 이름은 그대로 실린다. 대조를 빼는 변이가 빨강.
2. **수집 오류 메시지.** `collect_error`의 `problems`(파일을 모으다 난 오류의 메시지 · 위치)는 판정 러너와 구현 코드의 출력이 섞일 수 있는 글이다. 싣는 방식을 정해 ADR-128에 근거와 함께 적는다. 고를 것: (가) 메시지를 빼고 "수집 오류 N건"과 **파일 위치**(테스트 작성 역할 자신의 파일 경로 · 줄. 경로가 대상 규칙 폴더 안의 것인지 확인하고 밖의 경로는 싣지 않는다)만 싣는다, (나) 메시지를 싣되 길이 상한 · 표시 값 변환 · 고정 틀 안에 둔다. **기본 방침은 (가)다**(무결성을 더 지키는 쪽). 다만 테스트 작성 역할이 자기 테스트의 문법 오류 · 잘못된 import를 고치려면 무엇이 틀렸는지 알아야 한다: (가)로 가면 고칠 단서가 위치뿐이라 회귀가 헛돌 수 있다. 판정 러너가 주는 오류에서 **구현 코드가 지어낼 수 없는 부분**(오류 종류, 파일 · 줄, 러너가 고정 문구로 만드는 부분)을 가려낼 수 있으면 그것까지 싣고, 가려낼 수 없으면 (가)로 간다. 실제 러너 출력(문법 오류, 없는 모듈 import, 금지된 import, 최상위에서 던지는 앱 코드)을 시험으로 만들어 보고 정한다. `test-writer.test.ts`가 정한 방식을 그대로 단언한다(구현 코드가 최상위에서 던진 메시지 원문이 세션 입력에 없다).
3. **구조 시험.** `integrity.test.ts`의 M3-37 단언(판정 결과를 읽어 세션 입력에 싣는 파일 목록, 필터 자리)에 이 사유 경로를 넣는다: Red 확인 결과의 케이스 이름 · 오류 글을 세션 입력에 싣는 새 자리가 대조 기준을 거치지 않으면 빨강이 된다. 기존 단언을 지우거나 느슨하게 하지 않는다(더하기만).
4. **ADR.** ADR-128에 닫은 길 · 남는 길 · 근거를 적는다. ADR-121의 남는 길 ⓒ 문장을 "ADR-128로 닫음"으로 갱신한다(ADR-121의 다른 문장은 건드리지 않는다). 그리고 **테스트 작성 역할이 받는 구현 산출 입력**을 코드로 전부 확인해 같은 ADR에 적는다: `test-writer/inputs.ts`가 주는 `prisma/schema.prisma` 사본(구현 역할이 쓴 파일), `routes.md`(구현 역할이 만든 라우트 폴더 이름에서 나온 글), 다른 규칙의 기존 `*.acc.ts`(테스트 작성 역할이 쓴 것). 각각 지금 어떻게 다루는지(상한, 표시 값, 형식 검사)와 남는 한계를 사실대로 적는다. **이 입력들의 처리 방식은 이 이슈에서 바꾸지 않는다**(수용 기준은 "처리가 ADR에 적힌다"다. 바꿔야 할 결함을 찾으면 고치지 말고 보고한다).
