## 꼭 판정할 것
1. **범위와 "아직 켜지지 않음".** `git diff e5e3a09...HEAD --stat`. `docs/spec/*` · `docs/roadmap.md` · `CLAUDE.md` · `.github/workflows`가 바뀌지 않았는가. 변이 주입 실행기(`steps/mutation.ts`의 `createMutationExecutor`)가 제품의 기본 실행기 목록에 없고, 제품 오케스트레이터에서 변이 단계가 지금처럼 `skipped`로 기록되는지 코드와 시험(기존 파이프라인 e2e의 기대)으로 확인한다. `steps/judging.ts`(+15)의 `applyMutant`가 주어지지 않으면 `judgeCommit`의 동작이 글자까지 같은가(검사 · Red · Green · 병합 재검사 경로). `engine/types.ts` · `tools/executor.ts`(+50 -9) · `tools/definitions.ts` · `path-guard.ts`의 변경이 기존 역할(테스트 작성 · 구현 · 규칙 작성 · 판단)의 도구 · 경로 판정을 바꾸지 않는가(기존 시험의 `-` 줄 전부).
2. **고친 기존 단언.** 기존 시험 파일의 `-` 줄을 전부 읽고 PR 본문의 "고친 기존 단언 목록"과 대조한다. 각 변경이 이 이슈가 바꾸는 동작(역할 추가 · 설정 필수 칸 · 스냅샷 역할 · 유형 B의 변이 단계 사유)인가. **유형 B의 변이 단계 사유가 `not_in_scope` → `run_type`으로 바뀌는 것**이 ADR-020 · ADR-136과 맞는가, 방금 병합된 M3-06의 시험 · 화면(생략 표시)에 영향이 없는가. integrity 구조 시험의 목록을 넓힌 것(`steps/mutation.ts`의 블록 선언 `.current` 읽기 · `effective.js` 가져오기, 도구 표)이 그 시험이 지키던 것을 헐겁게 하지 않는가.
3. **역할 분리와 격리 (가장 중요, NFR-01 · NFR-02 · ADR-100).**
   - 변이 주입 세션이 인수 테스트를 볼 수 있는 길: 세션 폴더의 사본 목록(대상 블록 include에 `bive-acceptance/`가 걸리는 선언이면? include 패턴이 `**`인 블록), 경로 가드, `search_files`가 세션 폴더 밖을 뒤지는가, 규칙 진술 파일에 케이스 이름이 들어가는가, 오류 메시지 · 도구 결과에 테스트 내용이 새는가(예: `propose_mutant`의 거부 메시지). 다른 역할의 산출물(구현 세션 기록, 판정 출력)을 보는가.
   - 사본을 git 객체에서 읽는 방식: `--no-replace-objects` · `--` 구분 · 심볼릭 링크 · 하위 모듈 · 큰 파일 · 이진 파일 · 경로의 특수 글자(줄 바꿈 · 따옴표)에서 안전한가(M3-04 · M3-50의 선례와 같은 방어인가). 200개 · 4 MiB 상한을 넘을 때 무엇이 빠지고 세션에 어떻게 알리는가.
   - `propose_mutant`의 검증을 빠져나가는 입력을 찾는다: 경로 정규화(`a/../b`, `./`, 중복 슬래시, 대소문자, 유니코드 정규화, 끝의 공백 · 점, NUL), include 패턴 판정에 쓰는 매처가 블록 선언의 매처와 같은가(다른 매처면 블록 밖 파일을 블록 안으로 판정할 수 있다), 거부 목록이 **이름 패턴**(예: `*.config.*`)이라 놓치는 판정 영향 파일(`next.config.mjs`는 걸리는가, `middleware.ts` · `instrumentation.ts` · `.npmrc` · `vitest.setup.*` · 환경 파일)과 그것이 블록 include 안에 있을 수 있는가. 대상 블록 안의 파일이면 무엇이든 한 군데 고칠 수 있다는 것이 뜻이므로, "블록 안 소스 한 군데" 밖으로 나가는 경우만 결함이다. `search`가 여러 번 나오면 거부: 겹치는 일치 · 줄 끝 문자(CRLF) · 유니코드에서의 세기가 맞는가. `replace`에 실리는 글이 **어디로 흐르는가**(저장 · 세션 기록 · 화면 · 다른 역할의 입력): 지금은 저장뿐인지, 화면(실행 추적 · 도구 호출 기록)에 보이면 표시 값 변환을 거치는지.
   - 판정: 변이를 적용한 체크아웃이 **실행 워크트리 · 기준 브랜치 · 저장소의 어떤 ref에도** 남지 않는가(커밋하지 않음, 체크아웃 삭제. 실패 · 중단 · 시간 초과 경로에서 폴더가 남는가: 실제로 중단시켜 본다). 변이 적용이 해시 대조 **뒤**라 인수 테스트 해시 보호를 우회하는 길은 없는가(변이가 `bive-acceptance/`를 못 건드리는 것은 도구 검증뿐인가, `applyMutant`에서도 다시 보는가: 두 겹인지). 설치 **전**에 적용하므로 변이가 `package.json` · 설치 스크립트를 건드리면 판정 환경에서 임의 코드가 돈다: 도구가 그 파일들을 거부하는지와 `applyMutant` 쪽의 재확인.
   - **검출력의 과장**: 구현자 한계("서버를 요청 중에 죽이는 변이는 케이스 실패 = 검증됨"). 변이 주입 역할은 이득이 없지만(자기 채점 아님), 결과 '변이 검증됨'은 테스트 품질의 지표로 화면에 나간다. 판정 결과에서 "테스트가 단언으로 잡음"과 "서버가 죽어 요청이 실패함"을 가를 수 있는 정보가 판정 러너 출력에 있는가(서버 프로세스 종료 감지, 연결 거부). 가를 수 있는데 안 갈랐으면 비차단 이상으로 적고, 가를 수 없으면 한계 문장이 사실대로인지만 본다. 케이스가 **일부만** 실패해도 검증됨인 것은 타당한가(대상 규칙의 케이스 가운데 하나라도 잡으면 된다).
   - 변이 결과 저장: 추가 전용 트리거 · CHECK가 "판정 불가를 검증됨으로 저장"하는 조합을 DB 수준에서 막는가(마이그레이션 0026을 줄 단위로 읽는다: 색인 · 외래 키 · 트리거 · 기본값. 0025 뒤에 오는 번호가 맞는가. `migrate.test`가 0025 상태 DB에서 올라오는 길을 보는가). 저장하는 주체가 판정 실행기 한 곳인가(구조 시험이 있는가). 변이 주입 세션(에이전트)이 결과를 직접 쓸 도구가 없는가.
4. **대상과 순서 · 예산.** 순서 비교 함수(위험도 → 표시 ID 길이 → 글자)가 맞는가, `null` 자리, 같은 위험도. "대상 아님"의 네 경우가 기록 없이 미검증으로 남는 것이 화면 · 지표에서 '변이 생존'이나 '검증됨'으로 잘못 보이지 않는가(지금 화면은 변이 상태를 안 그린다: 값의 기본이 미검증인지만). 예산: 변이 세션의 비용 · 턴이 실행 예산과 역할 예산에 어떻게 잡히는가(스냅샷 역할, `usage`의 단계 · 역할 목록), 하루 한도에 드는가. 예산 소진 때 이미 남긴 변이 기록과 실행의 끝(`budget_exceeded`, 병합 없음)이 기존 규칙과 같은가.
