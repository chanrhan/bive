## 해야 할 것
1. **폐기 상태.** 규칙에 "폐기됨"을 둔다(삭제와 다르다. 판정 이력은 지워지지 않는다). 저장 모양을 정한다: 기존 `normState`에 값을 더할지, 폐기 시각 · 대체한 규칙 ID 칸을 따로 둘지. 마이그레이션 0019로 넣고(`rules` 표에 UPDATE · 식별 정보를 지키는 트리거가 있는지 먼저 읽는다. 표 재구성이 필요하면 트리거 · 색인을 빠짐없이 다시 만들고 이행 전 데이터가 그대로임을 `store/test/migrate.test.ts`로 단언한다), 폐기는 되돌릴 수 없게(폐기 → 효력으로 돌아가는 UPDATE를 DB에서 막을지) 정해 ADR-112에 적는다. 사람이 폐기를 되돌리는 길은 M5-08(이의)의 몫이다.
2. **도구 `retire_rule` · `supersede_rule`.** 규칙 작성 역할에만 준다(`NORM_TOOL_NAMES`). 다른 역할 도구 목록 · MCP 목록에 없음을 `integrity.test.ts`가 단언한다.
   - `retire_rule`: 대상 규칙을 폐기하고 규범 변경 기록 `retired` 1건.
   - `supersede_rule`: 대상 규칙 폐기 + 새 규칙 생성 + 규범 변경 기록(`superseded`, 새 규칙의 `created`, 모순 판단 `judgment`를 어떻게 남길지 정한다)을 **트랜잭션 1개**로. 중간 실패 때 아무것도 바뀌지 않아 모순된 두 규칙이 함께 효력을 갖는 시점이 없어야 한다(ADR-100 D6). 원자성 시험은 "k번째 쓰기만 실패"시키는 트리거로 쓰기마다 본다(첫 쓰기부터 막는 시험만으로는 부족하다. PR #240 · #241 검토에서 걸렸다).
   - 근거 필수(NRM-07). 근거가 대상 규칙의 진술이나 인수 테스트 케이스 이름 가운데 하나 이상을 **글자 그대로** 인용하지 않으면 `invalid_args`(형식 검사, A6). 인용 대조를 원문으로 할지 표시 값으로 할지, 최소 인용 길이(한두 글자 인용으로 통과하지 못하게), 공백 · 정규화 처리를 정해 ADR에 적고 경계 시험을 둔다. 에이전트는 규범 입력에서 표시 값을 본다는 점(ADR-106 · ADR-108)을 고려한다.
   - 대상 검증: 없는 규칙, 이미 폐기 · 삭제된 규칙, 잠정 규칙, 같은 호출이 만드는 규칙, 다른 프로젝트의 규칙. 표시 ID와 ID 둘 다 받는지는 `propose_rule.contradiction`의 방식을 따른다.
   - **내장 구조 규칙**(부모 없는 내장 종류)을 폐기 · 대체하려 하면 `denied`(사람 결정 B⑨). 시험용 내장 규칙 행으로 단언한다. 내장 규칙을 가려내는 기준이 ADR-106의 "없음 (내장 구조 규칙)" 표기와 같은지 확인한다.
   - 대체로 생기는 새 규칙의 `contradiction` 판단: `propose_rule`은 `contradiction`이 필수다. `supersede_rule`은 그 자체가 "대상과 모순이라 대체한다"는 판단이므로 판단 기록(`judgment`)의 `subject` · `verdict`를 어떻게 남길지 정한다(`NormJudgmentSubject` · `NormJudgmentVerdict`는 넓히기만 한다). 새 규칙이 대상 말고 다른 효력 규칙과 모순인지의 판단도 받을지 정한다.
   - 도구 인자의 글(근거 · 새 규칙의 제목 · 진술)은 에이전트가 쓴 글이다. 저장은 원문, 내보낼 때는 표시 값이라는 기존 방침을 따른다. `normChange.list`가 `detail` · `reason`을 표시 값으로 내보내는지 확인한다.
3. **폐기 규칙이 빠지는 곳.** 수용 기준 3의 다섯 곳: `rule.list` 기본 결과(폐기 포함 옵션을 둘지 정한다. 화면은 M7-15), 검사 단계와 병합 재검사의 대상, 지금의 준수 분모, 모든 역할 세션의 규범 입력. 효력 판정이 지금 세 곳에 따로 있다(`runs/run-service.ts`의 `unapprovedTargets`, `steps/check.ts`의 `approvedRules`, `norms/norm-input.ts`의 `effectiveRules`). 셋을 함께 바꾸고, 가능하면 한 함수로 모아 셋이 그것을 쓰게 한다(모으면 구조 시험으로 "효력 판정은 이 함수만"을 묶는다. 범위가 커지면 모으지 않고 셋을 고친 뒤 [후속]으로 보고한다). 판정 이력(`judgments`)은 지우지 않는다.
   - 정해서 ADR에 적을 것: 폐기 규칙의 인수 테스트 파일 처리(작업 트리에 남은 `tests/acceptance/<RULE>/…`을 누가 언제 지우는지. 지우지 않으면 검사 단계가 폴더가 있는 규칙을 판정하려 들 수 있다. 폐기 규칙의 테스트가 남아 새 구현을 깨는 경우가 바로 모순 상황이다), 폐기 규칙만 자식으로 남은 요구사항의 처리(상태 표시 · 준수 집계에서 어떻게 보이는지).
4. **대체 뒤 자동 시작.** 대체로 생긴 새 규칙은 M7-05 · M7-19의 자동 시작으로 실행 1개가 생긴다(규칙마다 실행 1개 · 원인 1건, ADR-110 · ADR-111). 폐기만 있으면 실행이 생기지 않는다. 자동 시작의 원인은 지금 규칙 작성 역할의 `created` 기록뿐이고 엔진 대조(`engine/start-basis.ts`)도 `kind === 'created'`만 받는다. 대체가 새 규칙의 `created`를 남기면 기존 경로를 그대로 탄다(가장 작은 변경). 그렇게 할지, `superseded`를 원인으로 받을지 정하고 `creationsOf`와 대조를 함께 맞춘다. 한 세션이 `propose_rule`과 `supersede_rule`을 섞어 부른 경우의 실행 수와 순서를 시험한다.
   - 대체 뒤 새 실행이 병합되기 전까지 작업 트리에는 옛 규칙의 구현과 테스트가 남아 있다. 새 실행의 검사 단계가 옛 규칙의 테스트를 대상에서 빼는지(3의 결정)와 맞물린다. `contradiction` 시나리오로 끝까지 `merged`가 되는지 확인한다.
5. **병합 직전의 재검사.** 실행의 대상 규칙이 병합 직전에 폐기됐으면 병합하지 않고 사유를 기록한다(ADR-100 A3 · A4). 종료는 `runEnding()`을 거친다. 승인 단계 자리의 효력 확인(`target_rule_unavailable`)과 대기 실행의 시작 때 재검사도 폐기를 효력 없음으로 본다. 진행 중인 실행의 대상 규칙이 도중에 폐기되는 경우(단계 사이)의 처리를 정한다: 지금 단계 감시(`verifyNormWatch`)가 규범 변경을 어떻게 다루는지 읽고, 에이전트의 정당한 폐기가 다른 진행 중 실행을 `guard` 위반으로 죽이지 않는지 확인한다.
6. **시나리오 `contradiction`.** 두 번째 요구사항에서 규칙 작성 역할이 RULE-001을 대체한다(요구사항마다 규칙 1개, 로드맵 M7 흐름 7의 전제). 기존 `contradiction-noted`(기록만)는 그대로 둔다. 파이프라인 e2e `contradiction.test.ts`는 M7-17의 몫이다. 여기서는 시나리오 파일과 단위 · 통합 시험까지다(시나리오가 `scripted-adapter.test.ts`의 필수 목록에 들어가는지 본다).

## 반드시 지킬 것
- 폐기 · 대체는 규칙 작성 역할의 도구로만 일어난다. 테스트 작성 · 구현 역할, 실행 안의 어떤 세션도 규칙을 폐기할 수 없다(구현자가 자기 채점 기준을 바꾸지 못한다, ADR-100 D4). `.rules.` 쓰기 호출과 `.normChanges.append(`의 허용 목록을 넓히면 이유를 PR 본문에 적고, 폐기 쓰기를 부를 수 있는 파일을 묶는 구조 시험을 둔다.
- 확인 상태(`confirmations`)는 이 이슈에서 건드리지 않는다. 확인됨 규칙을 에이전트가 폐기 · 대체할 때 확인이 풀리는 것은 M7-13이다. 다만 그 이슈가 같은 트랜잭션에 끼워 넣을 수 있게 폐기 · 대체의 쓰기를 한 함수에 모아 둔다. `/confirm/i` 금지 대상 파일에 그 글자를 넣지 않는다(주석 포함).
- 검사 단계에서 기존 규칙이 깨졌을 때의 모순 판단(M7-12), 구현 역할의 이의 제기(M7-11), 폐기 표시 화면과 [폐기 포함](M7-15), 확인할 것 목록(M7-14), 준수 지표의 사람 확인 기준 분리(M7-16)는 범위 밖이다.
- 사람의 승인 기록(`approval_log`)에 에이전트 행동을 쓰지 않는다(C2).
- 작업 지시에 새 글을 넣으면 `taskHeaderText` · `indentedText`를 쓴다(ADR-108). 규칙 작성 역할의 시스템 프롬프트에 두 도구의 쓰임을 고정 문장으로 더하고 스냅샷으로 단언한다. 실제 CLI 계약 시험(`real-cli.test.ts`)이 도구 스키마를 보는지 확인한다.
- `docs/spec/*` · `docs/roadmap.md` · `CLAUDE.md`를 고치지 않는다.
- 검토에서 반복해서 걸린 것을 스스로 점검한다: ⓐ 보이는지만 단언하는 시험 ⓑ 방어 코드는 있는데 시험이 없는 곳(원자성, 멱등, 경계값, 거부 사유별) ⓒ ADR · `docs/architecture.md` 문장이 코드와 다른 것 ⓓ 새 실패 사유 · 상태 값이 shared enum · DB CHECK · 화면 표시명에서 빠진 곳.
- 토큰을 아낀다. 전체 `pnpm test`는 PR을 올리기 전 한 번만(제한 시간 25분 이상), 그 밖에는 바뀐 시험 파일만 돌린다. 이슈가 크다. 변경 파일이 30개를 크게 넘거나 한 PR로 끝내기 어렵다고 판단되면 멈추고 어디서 나눌지 보고한다(나누는 것은 조율자가 정한다).
