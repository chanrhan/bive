## 해야 할 것 (수용 기준 순서)
1. **유형별 단계 계획과 상태 기계.** `RUN_STEP_PLANS`에 B · C · D를 더하고 엔진이 유형별 계획대로 간다. 문서가 정한 순서(ADR-020, architecture.md 4장 유형 표)를 그대로 따른다:
   - B: 승인 → 구현 → 검사 → 변이 → 병합 → 화면 갱신. 테스트 작성 · Red 확인은 `skipped`.
   - C: 승인 → 테스트 작성 → Green 확인 → 검사 → (테스트 보강이면 변이 재주입) → 병합 → 화면 갱신. 구현은 `skipped`.
   - D: 승인 → 기준 검사(Green) → 구현 → 검사(Green) → 병합 → 화면 갱신. 테스트 작성 · Red 확인은 `skipped`.
   - **생략 단계를 어떻게 저장하는가**: 수용 기준은 "생략 단계의 `skipped` 저장"이다. 유형 A에서 변이가 `skipped`로 저장되는 기존 방식(ADR-076)과 같게 한다(계획에 넣고 `skipped`로 기록하는지, 계획에서 빼는지: 화면의 파이프라인 표시가 단계 목록을 어떻게 읽는지 확인하고 기존 방식에 맞춘다). 변이 단계는 지금 모든 유형에서 `skipped`다(변이 주입은 M3-07). "테스트 보강이면 변이 재주입"은 M3-07 뒤의 일이므로 여기서는 계획의 자리만 두고 `skipped`로 기록하며 ADR에 넘긴다고 적는다.
   - D의 "기준 검사"를 어느 단계 종류로 저장할지: `StepKind`를 새로 만들지 않는 쪽이 작다(이미 있는 `green_check`를 쓸 수 있는지 본다. C의 Green 확인과 D의 기준 검사가 같은 종류로 저장될 때 뜻이 섞이지 않는지 판단해 ADR에 적는다). 새 종류가 꼭 필요하면 shared · store CHECK(마이그레이션) · 앱 표시명 표를 함께 고쳐야 하므로 **멈추고 보고한다**.
   - 회귀 상한 2회(`MAX_REGRESSION_COUNT`)는 모든 유형 공통: 유형별로 "어디로 회귀하는가"를 정한다(B · D: 검사 실패 → 구현. C: Green 확인 실패 → 테스트 작성, 검사 실패 → 구현이 없으므로 어디로? 문서에 없으면 가장 보수적으로: C의 검사 실패는 회귀 없이 실패로 끝내거나 테스트 작성으로 회귀. 근거와 함께 ADR에).
   - `engine.test.ts`가 유형마다 단언한다: 단계 순서(저장된 단계의 종류 · 상태 열), 생략 단계의 `skipped`, 회귀 상한 2회에서 `failed`(`regression_limit`), 재기동 복구(중간 단계에서 다시 띄워도 유형의 계획대로 이어감), 예산 복사가 유형이 쓰는 역할만 담는지(ADR-061: 유형 A의 역할 목록을 유형별로).
2. **유형 C: Green 확인과 소스 파일 쓰기 거부.**
   - Green 확인: 테스트 작성 세션이 쓴 **새 테스트가 전부 통과**해야 한다. 하나라도 실패면 테스트 작성이 끝나지 않는다(Red 확인의 거울: Red 확인이 "통과하는 테스트가 있으면 미종료"로 테스트 작성에 돌아가는 기존 방식(ADR-068 · ADR-128)과 같은 길로 돌아간다. 사유 글 · 앞 시도 자료의 전달도 같은 방식). 새 테스트가 0건 · 수집 오류 · 러너 오류는 통과가 아니다(닫힌 쪽). 판정은 기존 `judgeCommit`을 쓴다(새 판정 경로를 만들지 않는다).
   - 소스 파일 쓰기 거부: 유형 C의 실행에서 인수 테스트 폴더 밖의 파일이 바뀌지 않는다. 테스트 작성 세션의 경로 가드(ADR-052)가 이미 막는 것과, **세션 뒤 실행기가 커밋 · 대조할 때** 막는 것(가드를 지나친 변경이 있어도 Green 확인 · 검사 · 병합으로 가지 않는다)을 둘 다 확인하고 없으면 더한다. 구현 단계가 `skipped`라 구현 세션은 뜨지 않는다. 병합되는 변경이 인수 테스트 파일뿐인지 병합 전에 다시 본다(닫힌 쪽).
   - 시험: 새 테스트 전부 통과 → 진행, 하나 실패 → 테스트 작성으로 돌아감(시도 번호 · 사유), 상한 뒤 실패, 0건 · 수집 오류, 소스 파일을 건드린 세션(가짜 에이전트가 시도) → 거부와 그 뒤 상태, 병합 결과에 소스 변경 없음.
3. **유형 D: 시작 전 Green 전제와 검사 단계의 기존 검사 전부 통과.**
   - "시작 전 기존 검사 전부 통과가 아니면 시작을 거부": 무엇으로 "기존 검사 전부 통과"를 아는지 정한다. 선택지: (가) `run.create` 때 저장된 최신 판정으로 거부, (나) 실행의 첫 일로 기준 브랜치 커밋을 새로 판정(기준 검사 단계)하고 Green이 아니면 구현 세션을 띄우지 않고 끝냄, (다) 둘 다. 문서는 유형 표에 "기준 검사(Green)" 단계를 두고 "시작 전 기존 검사 전부 통과가 전제"라고 한다. 저장된 판정은 낡았을 수 있으므로 **새로 판정한 결과가 기준**이어야 한다고 본다((나) 또는 (다)). 결정과 근거를 ADR에 적는다. 거부 · 끝냄일 때 작업 트리 · 브랜치 · 병합에 아무것도 남지 않는다.
   - "기존 검사 전부" = 효력 있는 모든 규칙의 판정(인수 테스트 · 구조 · 계약). **판정 없음**(실행기 없는 계약 종류, 계약 안 요청 0건 등 ADR-132의 판정 없음, 미판정 규칙)을 어떻게 셀지 정한다: 통과로 세지 않되, 구현이 고를 수 없는 판정 없음이 D를 영영 막지 않게 한다(준수 지표의 "판정 가능 분모" 정의와 M3-47의 "막지 않음"을 따른다). 실패가 하나라도 있으면 Green이 아니다.
   - 검사 단계: 구현 뒤 **기존 검사 전부 통과**(Green → Green)를 요구한다. 유형 A의 검사 단계가 이미 효력 있는 규칙을 모두 판정하는지 확인하고(대상 규칙만 보는 자리가 있으면 D에서는 전부), 실패면 구현 회귀 · 상한 뒤 실패. D는 인수 테스트를 새로 쓰지 않으므로 대상 규칙의 "새 테스트" 개념이 없다: 구현 세션이 인수 테스트 파일을 고치지 못하는 기존 대조(해시)가 D에서도 듣는지 확인한다.
   - 시험: 기준이 Green이 아니면(실패 1건 · 구조 실패 · 계약 실패 각각) 시작 거부 · 구현 세션 0회 · 병합 0건, 판정 없음만 있는 경우, Green이면 진행, 검사 단계에서 대상 아닌 규칙이 깨지면 회귀, 상한 뒤 실패.
4. **`run.create`의 유형 기록과 유형 B가 받는 규칙.**
   - `run.create`가 유형을 기록한다. 인자 모양을 정한다(응답 형식 · 기존 호출은 넓히기만): 선택 인자 `type`을 더하고, **주지 않으면** 대상 규칙으로 정한다 — 대상이 모두 인수 테스트 검사 규칙이면 A(지금 그대로), 대상이 모두 정적 검사 규칙(`structure` 또는 `contract`)이면 B. 섞이면 거부(-32009, 아무것도 남지 않음). C · D는 명시할 때만. 이 방식이면 화면의 [실행]은 요청을 바꾸지 않아도 내장 규칙에서 유형 B 실행을 만든다. 다른 모양이 더 맞다고 보면 근거와 함께 ADR에 적고 그렇게 한다.
   - 유형 B는 검사 종류가 `structure` 또는 `contract`인 규칙만 받는다(명시 · 유도 둘 다). 유형 A · C는 정적 검사 규칙을 받지 않는다(지금의 내장 규칙 거부가 A · C에 남는다). 유형 D가 받는 대상은 문서로 정한다(리팩터링 · 되돌리기의 "대상 규칙"이 무엇인지: 문서에 없으면 가장 보수적으로 인수 테스트 검사 규칙만 받거나 기존 `ruleIds` 검증을 그대로 쓰고 ADR에 적는다).
   - `assertNoBuiltinTarget`을 유형별 대상 검증으로 바꾼다(ADR-127 ③ · ⑧ · "넘길 사실"). 내장 규칙을 대상으로 한 유형 B 실행에서 구현 판정(구현 단계의 "대상 규칙만 판정")이 내장 · 계약 규칙을 어떻게 다루는지 정한다: 구현 단계는 대상 규칙의 인수 테스트가 없으므로, 구현 커밋에서 그 규칙의 정적 검사(구조 · 계약)로 판정하거나 구현 단계의 판정을 건너뛰고 검사 단계에 맡긴다(가장 작은 쪽, ADR에 근거). **실행기가 없는 계약 종류의 규칙만 대상인 유형 B 실행**(판정 없음): 통과로 병합되는가, 거부하는가 — 통과로 세지 않는다는 M3-47의 원칙과 "판정할 수 없는 대상으로 구현 세션을 돌려 병합"하는 위험을 함께 보고 닫힌 쪽으로 정한다(예: 판정할 실행기가 없는 규칙만 대상이면 `run.create` 거부).
   - 자동 시작(`runs/auto-start.ts`) · 다시 시작 경로는 지금 유형 A만 만든다: 이 이슈에서 **바꾸지 않는다**(유형 C 자동 시작은 M3-30). 다만 그 경로들이 `createRun`의 새 검증을 지나며 동작이 달라지지 않는지 기존 시험으로 지킨다.
   - 사람 주체만(에이전트 -32020) · 프로젝트당 실행 1개 · 예산 검사 등 기존 `run.create` 규칙은 그대로다.
   - 시험(`run.test.ts`): 유형 기록(A · B · C · D), 유도(A · B · 섞임 거부), B에 인수 테스트 규칙 → 거부, A · C에 정적 검사 규칙 → 거부, 내장 구조 규칙 [실행] → 유형 B 실행 생성(승인 기록 포함), 계약 검사 규칙 → B, 실행기 없는 종류, 형식이 틀린 `type`, 거부 때 아무것도 남지 않음.
5. **유형 B의 끝까지 가는 흐름.** 파이프라인 e2e(`orchestrator/e2e/pipeline/`)에 유형 B 시나리오를 하나 이상 둔다(가짜 에이전트): 구조 위반 변형에서 `structure.declared-direction` [실행] → 구현 세션이 고침 → 검사 통과 → 병합, 그리고 `contract-mismatch` 변형에서 계약 검사 규칙 [실행] → 통과. 기존 구조 · 계약 시나리오의 기준값이 바뀌면 왜인지 보고한다. CI의 두 묶음 대조(`scripts/check-pipeline-groups.py`)에 새 파일이 들어가게 한다. **CI 시간**: `pipeline-e2e` 묶음과 `checks` 잡(제한 20분, 지금 약 14분 30초)에 여유가 적다. 무거운 시험(실제 `next build`)은 꼭 필요한 만큼만 더하고 늘어난 시간을 보고에 적는다.

## 화면
- 앱 코드는 고치지 않는 것이 기본이다. 확인만 한다: (1) 내장 규칙의 [실행]이 클라이언트에서 막혀 있지 않은지(막혀 있지 않고 서버 거부로 "실행 시작 실패"가 보였던 것: `screens/rules/runStartView.ts`). (2) 실행 유형 · 새 단계 구성(`green_check` · `skipped` 단계)이 화면의 파이프라인 표시 · 실행 목록 · 표시명 표에서 날값이나 깨진 모양으로 보이지 않는지(표시명 표에 `green_check`와 유형 B · C · D가 있는지). 빠진 표시명이 있으면 shared · app의 표에 더하고(이 경우 화면 e2e · 스모크 필수) ADR에 적는다. 화면 정의서에 없는 새 표시 · 새 문구는 만들지 않는다.

## ADR-136
유형별 단계 계획과 생략 단계의 저장, D의 기준 검사 단계 종류, 유형별 회귀의 목적지, C의 Green 확인 판정과 소스 변경 거부의 자리, D의 "기존 검사 전부 통과"의 정의(판정 없음의 처리 포함)와 시작 거부의 방식, `run.create`의 유형 인자와 유도 규칙, 유형별로 받는 대상, 내장 · 계약 규칙 대상 실행의 구현 판정, 실행기 없는 종류, 자동 시작 · 다시 시작을 바꾸지 않은 사실, ADR-127 ③ · ⑧ · 한계 가운데 닫은 문장, 남는 한계(변이 재주입, 유형 C 자동 시작 M3-30, 유형 D를 만드는 화면 경로 없음 등). 앞 ADR 본문은 고치지 않는다. `docs/architecture.md` 4장의 유형 표 · `run.create` 행 · C-18은 사실만 맞춘다("보수적 초안" 문구를 구현된 사실로).

## 반드시 지킬 것
- 유형 A의 동작은 글자까지 그대로다: 기존 `engine.test.ts` · `run.test.ts` · 파이프라인 e2e의 단언을 고치지 않는다(고쳐야 하면 왜인지 보고). `M1_RUN_TYPE`을 쓰는 자리는 필요한 만큼만 바꾼다.
- 무결성(NFR-01 · NFR-02)과 역할 분리(ADR-100): 어떤 유형도 판정 없이 병합하지 않는다. 생략한 단계 때문에 기존 방어(인수 테스트 해시 대조, 규범 대조, 구조 · 계약 검사, 병합 재검사)가 빠지지 않는다 — 유형별로 "이 방어가 여전히 도는가"를 표로 확인해 ADR과 보고에 적는다.
- 방어 · 거부 조건마다 "빼면 빨강"인 시험과 변이 결과 표: 유형 B의 대상 종류 검증 빼기, 섞임 거부 빼기, C의 Green 확인을 늘 통과로, C의 소스 변경 거부 빼기, D의 기준 검사 빼기 · 판정 없음을 통과로 세기 · 실패를 무시하기, D의 검사 단계가 대상 규칙만 보게, 유형별 회귀 상한 빼기, 생략 단계를 `skipped` 대신 `done`으로, 재기동 복구가 유형 A 계획으로 이어가게, 실행기 없는 종류의 대상 처리.
- 새 종료 사유 · 새 `StepKind` · 새 역할 · 새 도구 · 마이그레이션이 필요해 보이면 **멈추고 보고한다**(조율자가 정한다). 이미 있는 값으로 표현할 수 있으면 그것을 쓴다.
- `docs/spec/*` · `docs/roadmap.md` · `CLAUDE.md`를 고치지 않는다. 의미 있는 단위마다 로컬 커밋을 남긴다(서명 설정을 끄지 않는다).
- 이 이슈는 크다. 바뀐 파일이 35개를 넘을 것 같거나, C · D 가운데 하나가 위 "멈추고 보고" 조건에 걸리면: **끝낸 부분까지 커밋 · 푸시하고 PR은 만들지 않은 채** 남은 부분의 설계(선택지와 권고)를 보고한다(조율자가 쪼갠다).
- 완료 조건 명령: 설치 · 린트 · 타입 · 빌드 · 형식 · 단위 테스트(격리 `TMPDIR`, 알려진 두 시험만 실패 허용) · 픽스처 설치 뒤 `pnpm e2e:pipeline`(`TMPDIR` 격리, 오래 걸린다: 약 50분). 앱 코드를 고쳤으면 화면 e2e(`--trace off`) · Electron 스모크. 시험을 돌린 뒤 `ps`로 네 작업 공간 · 네 `TMPDIR` 경로의 프로세스(vitest · next · prism)가 남지 않았는지 확인한다(PID · cmdline · cwd를 확인한 네 PID만 끝낸다).
