## 해야 할 것
1. **확인 풀림.** 확인됨 규칙을 에이전트가 폐기 · 대체하면 **그 변경과 같은 트랜잭션에서** 확인 상태가 미확인이 되고, 규범 변경 기록에 `unconfirmed` 항목(주체 오케스트레이터, 풀린 시각, 원인 규범 변경 기록의 순번)이 남는다. 끼울 자리는 `norms/agent-rule.ts`의 `writeRetirement`다.
   - `.confirmations` 접근은 `confirmations/confirmation-service.ts`에서만 한다는 구조 시험이 있다. 풀기 함수를 그 서비스에 두고 `agent-rule.ts`가 부르게 한다(확인 서비스를 가져오는 곳 목록에 `norms/agent-rule.ts`를 의도적으로 더한다. PR 본문에 적는다). `.normChanges.append(`는 `agent-rule.ts`가 이미 허용 목록에 있다.
   - 확인 행을 어떻게 "미확인"으로 만드는지 정한다. 지금 확인 표의 모양과 트리거(추가 전용인지, 갱신을 받는지, 삭제를 막는지)를 먼저 읽는다. 사람의 확인 이력(누가 언제 무엇을 근거로 확인했는지)은 승인 기록에 남아 있다. 확인 행을 지우는 것이 DB에서 막혀 있으면 마이그레이션 0019로 "풀림" 표시를 받을 수 있게 넓힌다(풀 수 있는 주체는 오케스트레이터뿐이고 원인 순번이 있을 때만, 확인됨으로 되돌리는 것은 사람 RPC뿐이라는 것을 DB 제약으로 지킬 수 있는 만큼 지킨다). 원자성 시험은 "풀림 쓰기만 실패" · "`unconfirmed` 기록 쓰기만 실패"시켜 폐기 · 대체 전체가 남지 않음을 본다(k번째 쓰기만 실패시키는 방식. 첫 쓰기부터 막는 시험만으로는 부족하다).
   - 미확인 규칙의 폐기 · 대체에는 `unconfirmed` 항목이 생기지 않는다. 대체로 생긴 새 규칙은 미확인이다(에이전트가 만든 것).
   - 풀린 뒤 사람이 폐기된 규칙을 다시 [확인]할 수 있는지 정한다(`confirmation.set`은 지금 삭제만 본다). 폐기된 규칙의 확인이 뜻이 있는지("이 폐기를 봤다"로 쓸지, 거부할지)를 정해 ADR-113에 적고 시험한다. M7-14의 화면이 폐기 · 대체 카드에 [확인]을 둘 것이므로(B⑦: 맨 위에 두는 목적은 사람이 보고 넘기는 것이다) 그 행동이 무엇을 저장하는지가 여기서 정해져야 한다.
   - 요구사항의 확인 풀림: 에이전트가 요구사항을 고치는 도구는 M7에 없다(A11). 요구사항 쪽에는 풀림 경로가 없음을 구조 시험으로 보인다.
2. **확인됨을 만드는 경로는 사람 RPC뿐.** 확인 · 사람의 작성과 편집(`confirmation.set`, `requirement.*`, `rule.update`, 옛 제안 승인)만 확인됨을 만들고, 오케스트레이터와 에이전트 경로에는 없으며, 규칙 작성 역할에 요구사항 쓰기 도구가 없음을 `integrity.test.ts`가 단언한다. 네가 `agent-rule.ts`에 확인 서비스 가져오기를 더하므로, 그 모듈이 부를 수 있는 것은 "풀기"뿐이고 "확인"은 부를 수 없음을 구조 시험으로 묶는다(함수 이름 단위의 허용 목록).
3. **`confirmation.list`.** 지금 응답 모양을 읽고, 수용 기준 3대로 넓힌다: 확인 풀림 항목과 에이전트의 폐기 · 대체(확인 여부와 무관)를 시각 최신순으로 **맨 앞**에 두고, 항목마다 변경 전후 내용 · 사유 · 근거를 돌려준다. 그 뒤에 지금의 항목(미확인 규범 등)이 온다.
   - 항목의 종류를 구분하는 값(확인 풀림 / 폐기 / 대체 / 테스트 변경 / 미확인 규범)과 각 종류가 싣는 칸을 shared 스키마로 정한다. 같은 폐기가 "확인 풀림"과 "폐기" 두 항목으로 겹쳐 나오지 않게 한다(확인됨 규칙의 폐기는 한 항목에 풀림 사실을 함께 싣는 식).
   - 에이전트가 쓴 글(사유, 새 규칙의 제목 · 진술, 변경 전 내용)은 표시 값으로 내보낸다(`normChange.list`의 방식). 길이 상한을 둔다.
   - 맨 위 항목이 언제 목록에서 내려가는지 정한다: 사람이 그 항목을 [확인]하면(1의 결정) 내려가는지, 계속 남는지. "항상 맨 위"(B⑦)는 사람이 보기 전까지로 읽는 것이 보통이지만, 근거를 ADR에 적는다. 개수 상한과 잘림 표시를 둔다.
   - 알림 배지 수(지금 `confirmation.list`나 다른 RPC가 세는 값이 있으면)가 새 항목을 어떻게 세는지 정한다. 화면 변경은 M7-14다.
4. **테스트 변경 알림(G).** 확인됨 규칙을 대상으로 한 실행의 테스트 작성 단계가 그 규칙의 **기존** 인수 테스트 파일을 바꾸면(내용이 달라짐 · 지움. 처음 쓰는 것은 아님) 확인 상태는 그대로 두고 규범 변경 기록에 `test_changed` 항목(규칙, 바뀐 파일, 실행)을 남기며 `confirmation.list`가 그것을 돌려준다.
   - 누가 쓰는가: 테스트 작성 세션의 결과를 반영하는 오케스트레이터 코드(`applyTestWriterOutputs` 근처)다. 에이전트 도구가 아니다. `.normChanges.append(` 허용 목록에 그 파일을 더해야 하면 이유를 PR 본문에 적는다. 주체는 오케스트레이터로 하고 세션 · 실행 ID를 싣는다.
   - "바뀜"의 기준(파일 내용 해시 비교, 이름만 바뀜, 재시도마다 다시 쓰는 경우의 중복 항목)을 정한다. 한 실행에서 같은 규칙에 여러 번 쓰지 않게 한다. 실행이 병합되지 않고 실패하면(테스트가 main에 들어가지 않음) 알림을 어떻게 다루는지 정한다(가장 단순한 것은 병합 시점에 쓰는 것이다. 테스트 작성 단계에서 쓸지 병합 때 쓸지 근거와 함께 고른다. 수용 기준은 "테스트 작성 단계가 … 바꾸면 … 남으며"다).
   - 미확인 규칙의 테스트 변경에는 항목을 남기지 않는다(수용 기준은 확인됨 규칙만). 사람의 진술 편집으로 시작된 실행(ADR-109)이 테스트를 다시 쓰는 것도 대상인지 정한다(그 규칙은 편집으로 확인됨이고, 사람이 고친 진술에 맞춰 테스트가 바뀐 것이다. 알림을 남기는 쪽이 사람 결정 G의 글자와 맞다).
   - 종료 상태나 단계 진행에 영향을 주지 않는다. 확인 상태는 실행 생성 · 단계 진행 · 판정 · 병합의 어느 조건에도 쓰이지 않는다. `integrity.test.ts`의 `/confirm/i` 금지 대상 파일(엔진 · 단계 · 에이전트 · 도구 · 역할 · 판정 · 실행. `steps/`와 `test-writer/`가 들어 있다)에 그 글자를 넣지 않는다(주석 포함). 그러면 "이 규칙이 확인됨인가"를 테스트 작성 단계 코드가 직접 물을 수 없다. 금지 목록을 느슨하게 하지 말고, 단계는 "기존 인수 테스트가 바뀐 규칙과 파일"이라는 사실만 내놓고, 금지 대상 밖의 모듈(예: `norms/` 아래)이 확인 서비스에 물어 기록을 쓰게 배선한다. 배선 모양을 ADR에 적는다.

## 반드시 지킬 것
- 에이전트가 확인 표시를 만들 수 없다(NFR-01). 풀기는 오케스트레이터만 하고, 에이전트 세션에 풀기 · 확인 도구가 없다.
- 사람의 승인 기록(`approval_log`)에 오케스트레이터 · 에이전트 행동을 쓰지 않는다(C2). 풀림 · 테스트 변경은 규범 변경 기록에만 남는다.
- 규범 변경 기록의 `detail` 스키마는 넓히기만 한다. 원인 기록은 정수 `seq`로 싣는다. JSON 왕복이 되는 값만 쓴다.
- 폐기 · 대체의 쓰기 순서와 트리거(0018: 폐기 행에는 짝 기록이 있어야 한다)를 깨지 않는다. `unconfirmed` 항목을 어디에 끼워도 해시 체인 검증이 통과함을 시험한다.
- `docs/spec/*` · `docs/roadmap.md` · `CLAUDE.md`를 고치지 않는다. 확인할 것 화면(M7-14), 확인 상태 표시(M7-15), 준수 지표의 사람 확인 기준(M7-16), 이의(M5-08)는 범위 밖이다.
- 숨은 글자: 시험 파일에 날 숨은 글자를 넣지 않는다(이스케이프 표기, U+2028 · U+2029는 `String.fromCodePoint`). 스크립트로 파일을 고치면 `\u` 표기가 실제 글자로 풀릴 수 있다. `pnpm format:check` **뒤에** 바뀐 파일 전부를 `node /tmp/claude-0/-home-user-bive/6333409f-cbf4-55aa-b491-463fe23e95e5/scratchpad/r187-scan/r187b-hidden.mjs <파일들>`로 훑는다.
- 검토에서 반복해서 걸린 것을 스스로 점검한다: ⓐ 보이는지만 단언하는 시험 ⓑ 방어 코드는 있는데 시험이 없는 곳(원자성 k별, 경계값, 거부 사유별, 순서) ⓒ ADR · `docs/architecture.md` 문장이 코드와 다른 것 ⓓ 새 값이 shared enum · DB CHECK · 앱의 가짜 응답에서 빠진 곳.
- 토큰을 아낀다. 전체 `pnpm test`는 PR을 올리기 전 한 번만(제한 시간 25분 이상), 그 밖에는 바뀐 시험 파일만 돌린다.
