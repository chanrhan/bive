## 해야 할 것 (수용 기준 순서)
1. **규칙 상세에 대상 블록과 위험도.** 화면 정의서가 정한 자리(속성 줄 등)에 대상 블록(여러 개)과 위험도를 보인다. 위험도 값(`low` · `medium` · `high`)의 한국어 표시명은 화면 정의서의 낱말을 쓰고, 표는 shared에 두어 app이 대조 시험과 함께 쓴다(판단 주제 · 실행 종료 사유 표와 같은 방식). 영어 식별자를 화면에 내지 않는다. 블록 이름은 사람이 선언에 적은 식별자(소문자 · 숫자 · `-`)라 그대로 보인다. 다음을 정해 ADR-126에 적고 시험으로 고정한다:
   - 옛 규칙 · 내장 규칙처럼 두 칸이 비어 있을 때(빈 목록, `null`): 화면 정의서의 "값 없음" 표기(기존 화면이 쓰는 낱말)를 쓴다. 0이나 빈칸으로 두지 않는다.
   - 대상 블록 이름이 **지금 블록 선언에 없을 때**(선언 없이 받은 이름, 사람이 선언을 바꿔 이름이 사라진 경우): 이름을 그대로 보이되 선언에 없음을 드러낸다(문구는 1.1 원칙. 색에만 기대지 않는다). 선언 자체가 없는 프로젝트에서는 모든 이름이 그렇게 보이는 것이 맞는지, "선언 없음"을 한 번만 알릴지 정한다. 판단 근거는 `blocks.get`의 지금 선언이고, 화면이 지어내지 않는다(NFR-03).
   - 블록이 많을 때(10개)의 배치: 창 폭 820 · 1100 · 1280 · 1440px에서 가로 스크롤 · 넘침 · 겹침이 없다.
2. **요구사항 상세의 구현 위치.** 자식 규칙의 대상 블록만 모아 중복을 없애 보인다. 정해야 할 것: 폐기된 자식 규칙 · 효력 없는 자식 규칙의 블록을 넣는가(화면 정의서 · NRM-09 문장으로 판정. 문장이 없으면 "효력 있는 자식 규칙만"이 가장 작은 쪽), 정렬 순서(선언 순서가 있으면 선언 순서, 선언에 없는 이름은 뒤), 자식 규칙이 없거나 블록이 하나도 없을 때의 표기. 계산을 어디서 하는가: 응답에 이미 필요한 값이 있으면 app에서 모으고, 없으면 오케스트레이터 응답에 값을 더한다(아래 "응답 형식"). 화면이 규칙을 따로 여러 번 읽어 모으지 않게 한다.
3. **필터 칩.** SCR-03 규칙 목록 · SCR-02 요구사항 목록 · SCR-17 확인할 것의 블록 칩과 위험도 칩이 **값 개수와 함께** 활성화된다(1.4의 칩 규칙: 값마다 건수, 여러 값 선택, 해제. 기존 칩과 같은 동작 · 같은 컴포넌트). 정해야 할 것:
   - 한 규칙이 블록 여러 개를 가질 때의 건수(블록마다 한 번씩 센다)와 거르기(선택한 블록 가운데 하나라도 가진 항목).
   - 요구사항 목록의 블록 · 위험도는 무엇에서 오는가(자식 규칙의 블록 합집합 = 구현 위치, 위험도는 자식 규칙 가운데 가장 높은 값? 화면 정의서 문장으로 판정. 문장이 없으면 ADR에 근거와 함께 가장 작은 쪽).
   - 값이 없는 항목(빈 블록, `null` 위험도)을 거르는 칩 값("없음")을 둘지: 기존 칩(확인 상태 등)의 방식과 같게.
   - 선언에 없는 블록 이름도 칩 값으로 나오는가(나온다. 화면의 값은 응답에서 온다).
   - 확인할 것의 위험도 칩은 ADR-119에서 비활성으로 두었다. 이번에 활성화하고 ADR-126에 ADR-119의 그 문장을 대체한다고 적는다. 확인할 것 항목 가운데 규칙이 아닌 종류(테스트 변경 등)는 어떻게 세는가.
   - 대상 링크로 넘어올 때 필터를 비우는 기존 동작(ADR-114 · ADR-123)에 새 칩도 포함된다. 프로젝트 전환 때 초기화도.
4. **응답 형식(필요할 때만, 가장 작게).** 화면에 필요한 값이 지금 응답에 없으면 shared 프로토콜과 오케스트레이터 처리기에 **선택 칸을 더하는 것만** 한다(예: `confirmation.list` 항목의 대상 블록, `requirement.list` 항목의 구현 위치 · 위험도). 기존 칸의 뜻 · 필수 여부를 바꾸지 않는다. 저장 스키마 · 마이그레이션 · 엔진 · 규칙 작성 도구를 건드리지 않는다. 값은 저장된 규칙에서 그대로 읽어 싣는다(계산해 지어내지 않는다). 더한 칸마다 오케스트레이터 시험을 둔다. 더한 것이 5개 파일을 넘거나 기존 칸을 바꿔야 하면 멈추고 보고한다.

## 하지 않을 것 (보고에 후속으로만 적는다)
- 사람이 규칙 편집에서 대상 블록 · 위험도를 고치는 일(`rule.update`).
- 블록 선언을 화면에서 보거나 고치는 일, 블록 선언 변경 알림.
- 내장 구조 규칙(M3-03), 위험도에 따른 정렬 · 변이(M3-07).

## 반드시 지킬 것
- 화면 데이터는 RPC 응답에서만 만든다(NFR-03). 목 데이터는 시험 코드 안에서만. 가짜 응답은 shared 스키마를 통과해야 한다.
- UI 문구는 화면 정의서 1.1(명사형, 이모지 없음, 코드 표기 없음). 문서 기호를 넣지 않는다. 설명 글이 필요하면 `title` 속성이 아니라 공통 툴팁을 쓴다.
- 새 화면 시험에 `waitForTimeout`을 쓰지 않는다. 글꼴 폭에 따라 달라지는 줄바꿈 · 잘림을 고정 값으로 단언하지 않는다(순서 규칙 · 조건 규칙으로). 시험 소스에 숨은 글자를 글자 그대로 적지 않는다.
- 규칙마다 "빼면 빨강"인 시험을 두고 변이 결과 표를 PR 본문에 낸다(값 없음 표기, 선언에 없는 이름 표시, 구현 위치 중복 제거 · 폐기 규칙 제외, 칩 건수, 여러 블록 거르기, 표시명 표 대조, 필터 초기화).
- 구조 시험을 느슨하게 만들지 않는다. `docs/spec/*` · `docs/roadmap.md` · `CLAUDE.md`를 고치지 않는다.
- 의미 있는 단위마다 로컬 커밋을 남긴다(컨테이너 재시작 대비).
- 바뀐 파일이 40개를 넘을 것 같으면 멈추고 보고한다. 쪼갤 경계는 "(1 · 2) 상세 표시" / "(3) 필터 칩".
- 완료 조건 명령: 설치 · 린트 · 타입 · 빌드 · 형식 · 단위 테스트(격리 `TMPDIR`, 알려진 두 시험만 실패 허용) · 화면 e2e · Electron 스모크. 오케스트레이터 처리기를 고쳤으면 파이프라인 e2e도 한 번(픽스처 설치 뒤, 격리 `TMPDIR`). 고치지 않았으면 CI에 맡긴다.
