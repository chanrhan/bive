## 해야 할 것
1. **변이 주입 단계 켜기** (수용 기준 1).
   - 제품의 기본 실행기 목록에서 변이 주입 단계가 `createMutationExecutor`로 돈다. 유형 A와 유형 C **보강** 실행에서 돈다(ADR-020: 변이 주입 단계는 A · C(보강)만). 유형 B · D와 보강이 아닌 유형 C는 지금처럼 생략(`skipped`, 사유는 기존 방식).
   - 변이 생존은 그 실행을 실패로 만들지 않는다(유형 A: 단계 통과 → 병합). 변이 단계가 끝나야 병합으로 간다.
   - **변이를 내지 않는 세션**: 대본에 변이 주입 역할이 없는 기존 가짜 시나리오에서 ScriptedAdapter가 세션을 오류로 끝낸다고 한다. 그때의 결과(변이 없음 = `no_mutant`, 판정 · 설치 없음, 단계 통과)가 **기존 파이프라인 e2e의 단언을 고치지 않고** 지나가는지 실측한다. 단언이 변이 단계의 상태(`skipped`)를 고정하고 있어 고쳐야 하면(이 이슈가 바꾸는 동작이다) 고친 단언의 목록과 이유를 보고한다. 세션 오류가 "변이 없음"으로 조용히 넘어가는 것이 실제 에이전트의 오류(SDK 오류 · 한도)까지 삼키지 않는지 구분한다: 세션이 **정상 종료했는데 변이를 내지 않음**만 `no_mutant`이고, 세션 오류는 기존 다른 역할의 세션 오류와 같은 길(단계 실패 또는 문서가 정한 처리)로 간다. 가짜 어댑터의 "대본 없음"이 어느 쪽으로 분류되는지 정하고(기존 시나리오에 변이 주입 대본을 한 줄씩 더하는 쪽이 더 정직하면 그렇게 한다) ADR에 적는다.
   - **세션 끝내기(#308 검토 지적)**: 변이를 받은 뒤에도 도구를 계속 부르는 모델은 `error_max_turns` · 한도에 걸려 실행 전체가 `budget_exceeded`가 되고 받은 변이는 판정되지 않는다. `propose_mutant`가 받아들여지면 세션을 끝내는 장치를 둔다(이의 제기의 `closedCalls` · `objection_raised`와 같은 방식을 `mutant_proposed`에). 시험: 받은 뒤 도구를 계속 부르는 대본에서 세션이 끝나고 변이가 판정된다.
   - **검출력 과장 방지(#308 검토 지적)**: 서버 프로세스를 죽이는 변이가 "케이스 실패 = 변이 검증됨"으로 세어진다. 판정 러너는 서버 자식 프로세스를 쥐고 있다: 판정 중에(`server.stop()` 전에) 서버가 이미 죽었으면 그 판정을 러너 오류(판정 불가 = 변이 미검증)로 본다. 이 변경이 **변이 판정에만** 걸리게 할지 모든 판정에 걸리게 할지 정한다(모든 판정에 걸면 검사 · Red · Green의 기존 결과가 달라질 수 있다: 서버가 죽은 판정을 실패로 세던 것이 러너 오류가 된다. 가장 작은 쪽은 변이 판정에만). 처리 함수 안의 예외(서버는 살아 있음)는 테스트가 잡은 검출로 둔다. ADR-139 ⑩의 "가를 정보가 없다"는 문장은 네 ADR-143에서 바로잡는다(ADR-139 본문은 고치지 않는다).
   - **세션 폴더의 이름 겹침(#308 검토 지적)**: 블록 include가 `rules/**`를 덮는 프로젝트에서 소스 사본 `rules/<ID>.md`가 규칙 글 파일을 덮어쓴다. 규칙 글 · 변이 자료 등 BIVE가 쓰는 파일을 소스 사본과 겹치지 않는 자리(소스 사본을 하위 폴더에 두거나 BIVE 파일의 이름을 사본이 올 수 없는 이름으로)로 옮기고 시험을 더한다.
   - **빠진 시험(#308 검토 지적)**: include가 `**`인 블록에서 인수 테스트 사본이 세션 폴더에 없음, 변이 결과를 저장하는 곳이 한 곳뿐임(integrity 구조 시험), `prisma` 거부가 루트 폴더만 보는 것은 지금 프로파일(스키마가 `prisma/schema.prisma`)에서 맞는지 확인하고 스키마 경로가 다른 프로젝트면 놓친다는 사실을 한계에 적는다(넓히지 않는다).
2. **자동 보강** (수용 기준 1 · 2, ADR-141 ② · ③ · ⑦).
   - 유형 A 실행이 병합으로 끝났고 그 실행의 변이 결과에 '변이 생존'이 있으면, 그 규칙마다 유형 C **보강 실행**이 사람 확인 없이 생긴다. 만드는 길은 기존 자동 시작 모듈(`runs/auto-start.ts`)이다: 시작 근거 대조 · 하루 한도 · 프로젝트당 실행 1개(대기) · 승인 단계 자리의 효력 확인 · 설정 확인을 **그대로** 거친다. 새 시작 경로를 따로 만들지 않는다.
   - **시작 근거**: 변이 결과 기록(생존)을 원인으로 하는 새 원인 종류를 규범 변경 기록 `auto_start`의 상세에 둔다(지금은 `causeSeqs` 또는 `ruleEditSeqs` 가운데 정확히 하나: 셋 가운데 정확히 하나가 되게 넓힌다. 이름 · 모양은 네가 정한다). shared 스키마 · store CHECK(0027) · `start-basis` 대조 · 구조 시험(`integrity.test.ts`의 관련 목록)을 함께 넓힌다. 원인이 가리키는 변이 결과가 실제로 그 규칙의 '생존' 기록이고 병합된 실행의 것인지 대조한다(위조된 원인으로 실행을 만들 수 없게: 기존 원인 대조와 같은 엄격함).
   - **보강 표시**: 실행 표를 다시 만들지 않는다. 실행과 원인 변이 결과를 잇는 새 표(0027)를 둔다(실행 ID · 변이 결과 ID, 추가 전용, 실행마다 하나). 엔진은 이 연결이 있는 유형 C 실행을 "보강"으로 본다(변이 단계를 돌고 재주입이 종료 조건).
   - **언제 만드는가**: 실행이 병합으로 끝난 직후. 그 시점에 오케스트레이터가 죽었다 살아나면(기동 복구) 놓친 보강을 만드는가, 만들지 않는가를 정한다(기존 자동 시작이 기동 때 놓친 원인을 다시 보는 방식이 있으면 그것을 따른다. 없으면 가장 작은 쪽으로 정하고 한계에 적는다). 중복 방지와 함께 멱등이어야 한다(같은 변이 결과로 보강 실행이 둘 생기지 않는다: 새 표의 유일 제약).
   - **고리 · 중복 방지**: 보강 실행의 재주입 결과는 새 자동 시작의 원인이 아니다. 같은 규칙에 대기 · 진행 중인 보강 실행이 있으면 또 만들지 않는다. 보강 실행이 실패로 끝난 뒤 같은 변이 결과로 다시 만들지 않는다(실패 뒤의 처리는 M3-08: 검토 대기열. 이 이슈는 '변이 생존' 상태 유지와 실행 실패 기록까지).
   - 규칙이 그 사이 폐기 · 삭제 · 효력 없음이 되면 만들지 않는다(기존 효력 확인).
   - 시험(`orchestrator/test/auto-start.test.ts` · `mutation.test.ts` · `store/test/mutation-results.test.ts`): 생존 → 보강 실행 1개(유형 C, 대상 = 그 규칙, 시작 주체 = 자동, 시작 근거 = 그 변이 결과), 검증됨 · 미검증은 만들지 않음, 하루 한도 초과 · 실행 진행 중(대기) · 설정 미비 · 효력 없음의 기존 문이 그대로 적용됨, 위조 원인 거부, 중복 · 고리 · 실패 뒤 재생성 없음, 여러 규칙이 생존이면 규칙마다 하나, 새 표의 제약(SQL 직접 쓰기 포함).
3. **보강 실행: 변이 자료와 재주입** (수용 기준 3, ADR-141 ④ · ⑥).
   - 보강의 테스트 작성 세션이 살아남은 변이를 받는다: 파일 경로 · 바꿀 글 · 바꾼 글을 ADR-128의 앞 시도 자료와 같은 방식(틀 · 상한 · 표시 값 변환 · 들여쓰기)으로. 작업 지시에 "이 변이를 잡는 테스트를 더한다"는 고정 문장. 변이 글은 다른 역할(변이 주입)이 쓴 글이다: 자료 틀 밖으로 새지 않게 하고, 길이 상한을 넘으면 자르고 잘렸음을 적는다. **보강이 아닌 세션에는 이 자료가 글자 하나 실리지 않는다**(기존 테스트 작성 작업 지시의 글자 단언이 그대로 통과).
   - 유형 C의 기존 흐름(ADR-136): 테스트 작성 → Green 확인 → (구현 생략) → 검사 → **변이 주입 단계 = 재주입** → 병합. 재주입은 새 변이 세션을 열지 않고 **살아남았던 같은 변이**(연결된 변이 결과의 경로 · 바꿀 글 · 바꾼 글)를 판정 커밋의 격리 체크아웃에 다시 적용해 대상 규칙의 인수 테스트를 돌린다. 검출(케이스 실패) = 그 규칙 '변이 검증됨' 기록 + 단계 통과 → 병합. 생존 = 테스트 작성으로 회귀(회귀 상한은 기존 카운터: ADR-136 ④의 유형 C 두 카운터가 재주입 회귀에서 어떻게 세는지 정하고 최악 세션 수를 ADR에 적는다) → 상한 뒤 실행 실패(기존 종료 사유 가운데 맞는 것. 새 종료 사유가 꼭 필요하면 멈추고 보고). 재주입이 판정 불가(변이가 더는 적용되지 않음: 보강 세션은 소스를 못 고치므로 생기지 않아야 하지만 기준 브랜치가 그 사이 바뀐 경우 · 러너 오류)면 닫힌 쪽(검증됨으로 세지 않고 실행 실패 또는 미충족)으로.
   - 재주입의 결과도 변이 결과 표에 기록한다(어느 실행의 재주입인지 구분되게: 0026의 칸으로 표현되는지 보고, 안 되면 0027에서 넓힌다). 규칙의 최신 변이 상태는 가장 나중 기록을 따른다.
   - 보강 세션이 받은 변이를 "잡는 척"하는 길: 테스트 작성 세션이 변이의 바꾼 글 자체를 문자열로 단언하는 테스트(소스 파일을 읽어 글자를 비교)를 쓰면 재주입에서 검출된다. 인수 테스트는 HTTP로 서버를 검사하게 돼 있고 앱 코드 import를 정적 검사(`judge/acceptance-lint.ts`)가 막는다: 파일 시스템을 읽는 테스트를 그 검사가 막는지 확인하고, 못 막으면 한계에 사실대로 적는다(#117 계열. 여기서 고치지 않는다).
   - 시험(`orchestrator/test/test-writer.test.ts` · `mutation.test.ts`): 보강 세션의 작업 지시에 변이 자료가 틀 안에만 있음(표시 값 변환 · 상한 · 잘림 표기), 보강이 아닌 세션에는 없음, 재주입이 같은 변이를 적용함(새 변이 세션 0회), 검출 → 검증됨 → 병합, 생존 → 회귀 → 상한 뒤 실패(규칙은 '변이 생존' 그대로), 판정 불가의 처리, 재주입 변이가 어떤 ref · 작업 트리에도 남지 않음.
4. **시나리오와 파이프라인 e2e** (수용 기준 1). `scenarios/mutant-survives.yaml`: 유형 A 실행에서 변이 주입 세션이 낸 변이가 생존 → 자동으로 유형 C 보강 실행 → 테스트 작성 세션이 그 변이를 잡는 테스트를 더함 → 재주입에서 검출 → '변이 검증됨'. `orchestrator/e2e/pipeline/mutant-survives.test.ts`(실제 판정 러너)가 끝까지 단언한다: 첫 실행 병합 · 규칙 '변이 생존' · 사람 조작 없이 보강 실행(유형 C, 구현 생략, Green 확인, 변이 주입 단계가 생략 아님) · 끝나면 '변이 검증됨' · 변이가 main에 없음. 로드맵 M3 완료 기준 흐름 3번의 문장과 맞춘다(카드 예외 표시는 M3-15의 몫이라 여기서는 RPC로 상태를 본다).
   - **CI 시간**: `checks` 제한 30분(지금 15 ~ 22분), `pipeline-e2e-group` 제한 40분(지금 13 ~ 21분). 새 e2e는 실행 둘(유형 A + 유형 C)과 변이 판정 둘(설치 · 빌드가 각각)을 돈다: 로컬 소요 시간을 재고, 묶음 1 · 2 가운데 어디에 둘지(`PIPELINE_E2E_GROUP1` 목록) 시간으로 정한다. **기존 e2e 전체가 변이 단계를 켠 뒤 얼마나 느려지는지** 전 · 후를 잰다(변이를 내지 않으면 판정 · 설치를 돌지 않으니 세션 1개만큼이어야 한다). 한 묶음이 30분을 넘길 것 같으면 멈추고 보고한다.
5. **ADR-143**: 단계 켜기와 유형별 변이 단계, 변이를 내지 않는 세션과 세션 오류의 구분, 세션 끝내기, 서버 종료의 판정, 세션 폴더 배치, 시작 근거의 모양과 대조, 보강 연결 표, 만드는 시점과 기동 복구, 고리 · 중복 · 실패 뒤, 변이 자료의 틀, 재주입과 회귀 카운터 · 최악 세션 수, 재주입 결과의 기록, 기존 e2e에 미친 영향과 시간, ADR-139 ⑩의 바로잡음, ADR-136 한계 (b)를 닫음, M3-08로 넘기는 사실(보강 실행이 실패로 끝난 변이 생존 항목을 무엇으로 찾는가), 남는 한계. `docs/architecture.md` 4장(단계표 · 유형 표 · 역할 접근 제한)과 자동 시작 서술을 사실대로.
6. **화면(한 줄만)**: 설정 화면의 "변이 주입" 행 머리가 고정폭 글꼴이라 글자 사이가 벌어져 보인다(#308 검토 지적). 한국어 표시명을 쓰는 행 머리의 글꼴만 본문 글꼴로 바꾸는 CSS 한두 줄이면 고치고(화면 e2e `scr-21*.spec.ts`와 스모크를 돌린다), 다른 행의 모양이 바뀌거나 그보다 크면 **하지 말고 보고에 적는다**.

## 반드시 지킬 것
- **무결성 (NFR-01 · NFR-02 · ADR-100)**: 변이(첫 주입 · 재주입)는 어떤 경로로도 병합 브랜치 · 실행 브랜치 · ref · 작업 트리에 남지 않는다. 판정할 수 없는 결과를 '변이 검증됨'으로 세지 않는다. 자동 보강은 기존 자동 시작의 문을 하나도 건너뛰지 않는다. 보강 실행도 판정 없이 병합되지 않는다(Green 확인 · 검사 · 재주입 · 병합 재검사 · 소스 변경 거부 세 겹이 그대로).
- 유형 A의 변이 단계 말고는 유형 A · B · D의 동작이 그대로다. 보강이 아닌 유형 C도 그대로다. 기존 시험의 단언을 고칠 때는 이 이슈가 바꾸는 동작(유형 A 변이 단계의 상태, 자동 시작 원인의 종류)에 한하고 목록을 보고한다.
- 방어 · 거부 조건마다 "빼면 빨강"인 시험과 변이 결과 표(시험용 변경): 유형 B · D에서도 변이 단계 돌리기, 생존을 실행 실패로, 세션 오류를 `no_mutant`로 삼키기, 받은 뒤 세션을 끝내지 않기, 서버 종료를 검증됨으로, 검증됨 · 미검증에도 보강 만들기, 하루 한도 · 실행 1개 문 건너뛰기, 위조 원인 받기, 보강 중복 · 고리 · 실패 뒤 재생성, 보강 실행을 유형 A로, 보강 아닌 세션에 변이 자료 싣기, 변이 자료의 표시 값 변환 빼기, 재주입에서 새 세션 열기 / 다른 변이 적용, 재주입 없이 보강 끝내기, 재주입 생존을 통과로, 재주입 변이를 워크트리에 남기기.
- 새 종료 사유 · 새 `StepKind` · 새 역할 · 새 화면은 만들지 않는다. 꼭 필요하면 멈추고 보고.
- `docs/spec/*` · `docs/roadmap.md` · `CLAUDE.md`를 고치지 않는다. 의미 있는 단위마다 로컬 커밋(서명 설정을 끄지 않는다). 권한 · 격리 검사가 거부한 일을 다른 길(스크립트로 감싸기, 옵션이나 도구를 바꿔 같은 일 하기)로 하지 않는다. 프록시 환경 변수 값을 출력하지 않는다. 판정 격리를 돌아가는 대처를 하지 않는다. 실제 API 키를 쓰지 않는다.
- **멈춤 조건**: 순서는 1(단계 켜기와 #308 지적) → 2(자동 보강) → 3(변이 자료 · 재주입) → 4(시나리오 · e2e) → 5 · 6. **1과 2를 끝낸 시점에 바뀐 파일이 25개를 넘으면**: 그때까지를 커밋 · 푸시하되, 단계를 켠 채 자동 보강만 있고 재주입이 없는 상태는 제품으로 내보낼 수 없다(보강 실행이 끝나는 조건이 없다) → 보강 실행을 만드는 호출을 엔진에 **잇지 않은 채**(함수와 시험만) 두고 PR 없이 멈춰, 남은 부분의 설계와 파일 수를 보고한다(조율자가 다시 쪼갠다). 전체가 40개를 넘을 것 같으면 그때도 멈추고 보고한다.
