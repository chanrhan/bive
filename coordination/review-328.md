## 구현자가 정한 것 (네가 타당성을 판정한다)
- 시작 단계 = 원 실행의 `currentStep`(`runs/run-continuation.ts`의 `continuationStartOf`, `createRun`의 `RunContinuationSeed.inherited`). 계획에서 그 앞 단계마다 원 실행의 **마지막 시도**를 보고: 통과 · 실행기의 생략 → 이어받음 / 이어받은 시도(원 실행도 이어받는 실행) → 그 시도가 가리키는 실제 시도를 그대로 가리킴(사슬 2단) / 유형 생략(`run_type`) → 이어받지 않고 대기로 두어 엔진이 다시 유형 생략으로 기록 / 없음 · 끝나지 않음 · 실패 → 거기서 멈추고 그 단계부터 다시 돎(닫힌 쪽).
- 이어받은 시도의 기록: 새 실행의 `skipped` 행 + shared `InheritedStepDetail = {reason: 'inherited', fromRunId, fromStepId, fromStatus}`. `passed` 행을 만들지 않는다.
- 작업 가지: `continuationWorktreeStart`가 원 실행의 `headCommit`(없으면 기준 커밋)을 돌려준다. 엔진은 워크트리를 만들 때 새 실행의 `headCommit`도 그 값으로 저장하고 **저장한 레코드로 첫 단계를 돈다**(처음 구현에서 `#drive`가 `#prepare` 저장 전의 레코드로 돌아 `headCommit`이 비던 결함을 고쳤다고 함). 원 브랜치를 지운 경우는 `start_commit_unavailable` → `worktree_error`.
- 판정 근거 `basisSteps`: 자기 단계의 이어받은 시도가 가리키는 시도 + 자기 단계. 원 실행의 시작 단계 이후 시도는 들지 않는다. 단계 실행기 6개(check · green-check · implementation · merge · mutation 두 자리 · red-check)가 쓴다. 이어받은 시도가 없으면 저장소를 읽지 않고 자기 단계 그대로. `integrity.test.ts`에 구조 시험.
- 회귀 상한 `lineageCounts`(엔진 `#unmet`): 구현 · 검사 회귀는 사슬의 `regressionCount` 합 + 자기 회귀. 테스트 작성 재시도는 원 실행들의 시도에서 재기동 중단 · 이어받은 시도 · 멈춘 테스트 작성 시도를 빼고 센다(멈춘 시도는 이어받는 실행의 첫 시도가 다시 한다).
- 보강 실행을 이어받은 실행: 재주입은 이어받은 테스트 작성 커밋과 Green 확인 해시로 돌고, "더하기만" 대조는 기준 커밋과 원 실행의 테스트 작성 커밋 사이에서 본다.
- 표시명: 앱은 단계 `exitDetail`을 보이지 않아 더하지 않음(한계).
- 구현자 한계: 이어받는 실행의 첫 구현 세션은 원 실행의 앞 시도 사유(검사 실패 등)를 받지 않는다. Green · Red 확인 실행기와 유형 A 새 변이 주입의 `basisSteps`는 행동 시험 없이 구조 시험으로만 묶였다(유형별 계획상 이어받은 단계 뒤에서 다시 도는 경로가 없다는 주장). 기준 4의 재주입 시험은 시험 실행기로 예산 초과 자리를 만들었다(제품 경로에는 그 단계에서 예산 초과가 날 세션이 없다).

2. **이어받는 단계의 정의 (가장 중요, NFR-01).** `continuationStartOf`를 줄마다 읽고 유형별 단계 계획(A · B · C 보강 · C 보강 아님 · D)과 멈춘 자리별로 표를 만든다: 원 실행이 [승인 전 / 테스트 작성 1회차 / 테스트 작성 회귀 중 / Red 확인 / 구현 1회차 / 구현 회귀 중(검사 실패 뒤) / Green 확인 / 검사 / 변이 주입 / 병합]에서 예산 초과가 됐을 때 새 실행의 시작 단계 · `skipped` 행 · 다시 도는 단계. 각 칸에서 다음을 확인한다.
   - **이어받은 단계가 "실제로 통과했고 그 뒤에 무효가 되지 않은" 단계뿐인가.** "그 앞 단계의 마지막 시도가 통과"라는 조건만으로 충분한가: 예 ⓐ 유형 A에서 검사 실패 → 테스트 작성으로 회귀하는 정책이 있는가(있으면 테스트 작성 2회차 중 예산 초과: 앞 단계 없음 → 처음부터). ⓑ 구현으로 회귀한 뒤 예산 초과: 테스트 작성 · Red 확인의 마지막 시도는 통과(이어받음), 그런데 **회귀로 작업 가지가 되감겼는가**(회귀 때 `headCommit`이 어디로 돌아가는가: ADR-066). 새 실행의 시작 커밋(원 실행의 `headCommit`)이 "이어받은 마지막 단계의 산출 커밋"과 같은가, 아니면 실패한 구현 시도의 커밋이 섞이는가. 구현 역할이 원 실행의 멈춘 시도에서 커밋까지 한 상태(커밋은 됐고 단계는 안 끝남)가 있을 수 있는가: 있으면 그 커밋이 새 실행의 시작점에 들어가고 Red 해시 보호는 그것을 보는가.
   - **`currentStep`의 신뢰성**: 예산 초과가 단계 사이(한 단계가 끝나고 다음 단계가 열리기 전)에 판정되면 `currentStep`은 무엇인가(`budget_aggregate_exceeded`는 세션 뒤에 난다: 그 단계는 끝난 것인가 안 끝난 것인가. 끝난 단계를 다시 도는 것은 안전(닫힌 쪽), 안 끝난 단계를 이어받는 것은 구멍). 원 실행이 `queued` · `waiting_approval`에서 예산 초과가 된 경우.
   - "실행기의 생략"(통과가 아닌 `skipped`인데 `run_type`이 아닌 것: 예 변이 주입의 `no_mutation_targets`)을 이어받는 것이 맞는가: 그 생략의 조건이 새 실행에서도 같은가(대상 규칙 · 블록 선언이 그 사이 바뀌었으면?).
   - 사슬 2단: 이어받은 시도가 가리키는 "실제 시도"가 늘 그 단계를 실제로 돌아 통과한 시도인가(1차가 이어받은 단계를 2차가 다시 이어받는 경우와, 1차가 직접 돈 단계를 2차가 이어받는 경우가 섞일 때).
   - 요청으로 `inherited`를 바꿔 넣을 수 있는가(RPC 스키마 · `createRun`의 인자가 사람의 `run.create`로 닿지 않는가). DB에 직접 `skipped` · `inherited` 행을 위조하면 `basisSteps`가 그 행이 가리키는 **아무 실행의 아무 단계**를 근거로 읽는가: `fromRunId`가 연결 사슬(`run_continuations`)의 조상인지, `fromStepId`가 그 실행의 그 종류 단계인지 **읽을 때** 확인하는가(확인하지 않으면 위조된 한 행으로 Red 해시 · 검사 통과 커밋을 바꿔치기할 수 있다: #117 계열의 한계인지 이 PR이 새로 연 길인지 판정).
3. **`basisSteps`와 단계 실행기 6개.** 각 실행기가 근거로 무엇을 읽는지(Red 해시 · Green 해시 · 앞 단계 산출 커밋 · 검사 통과 커밋) 표로 만들고, 이어받는 실행에서 그 값이 원 실행의 어느 시도에서 오는지 확인한다. **원 실행의 시작 단계 이후 `passed` 시도가 근거에 들지 않는가**(예: 원 실행에서 통과했던 검사 시도를 새 실행의 병합 대조가 쓰면 새 실행이 검사를 다시 돌지 않고 병합할 수 있다. 구현자의 변이 "`basisSteps`가 원 실행들의 단계 전부를 읽음"이 빨강이라는 것을 다시 확인하고, 병합 단계에서 직접 시도한다: 새 실행이 검사를 통과하지 않은 상태에서 병합 실행기가 원 실행의 검사 통과를 근거로 받아들이는가).

   - "행동 시험 없이 구조 시험으로만 묶은 자리"(green-check · red-check · 유형 A 새 변이 주입)의 주장 "유형별 계획상 이어받은 단계 뒤에서 다시 도는 경로가 없다"가 맞는가(표로 확인: Red 확인이 이어받은 테스트 작성 뒤에서 도는 경우 = 원 실행이 Red 확인에서 예산 초과? Red 확인은 세션이 없어 예산 초과가 안 난다는 뜻인가. 판정 러너 시간 초과 등 다른 길로 `budget_exceeded`가 되는가). 틀리면 시험이 없는 것이 차단이다.
4. **작업 가지와 `headCommit`.** 새 실행의 시작 커밋 = 원 실행의 `headCommit`. 원 실행의 브랜치가 그 뒤 움직일 수 없는가(종료 상태의 실행 브랜치를 건드리는 코드가 없는가). 기준 커밋은 원 실행과 같은데 **main이 그 사이 나아갔으면** 병합 단계(병합 재검사)가 기존 실행처럼 처리하는가. 원 실행의 멈춘 시도가 남긴 커밋되지 않은 변경이 새 워크트리에 없는가(새 워크트리는 커밋에서 만든다). `#drive`가 저장된 레코드를 쓰게 한 고침의 범위.
5. **회귀 상한 `lineageCounts`.** 상한의 뜻(구현 회귀 N회 · 테스트 작성 재시도 M회)을 코드에서 확인하고, 사슬 합이 상한에 닿는 경계(원 2 + 이 실행 1 = 상한)에서 한 번 더가 막히는지, **이어받기로 상한이 늘어나는 길**(멈춘 시도를 빼는 규칙을 이용해 매번 시도 중에 예산 초과 → 이어받기를 되풀이하면 시도 수가 세어지지 않는가: 예산이 상한이라 무한은 아니지만 "회귀 상한을 넘길 수 없다"는 수용 기준과 맞는가)과 **부당하게 줄어드는 길**을 따진다. 재기동 중단 시도를 빼는 것이 기존 규칙과 같은가.
6. **보강 실행을 이어받은 실행.** 재주입이 이어받은 테스트 작성 커밋과 Green 해시로 도는가, "더하기만"(세 자리: 테스트 작성 결과 받기 · Green 확인 전 · 병합 직전) 대조가 기준 커밋과 원 실행의 테스트 작성 커밋 사이에서 성립하는가(시작 단계가 테스트 작성보다 뒤일 때 첫째 자리는 돌지 않는다: 나머지 둘이 지키는가). 기준 4의 시험이 "시험 실행기로 예산 초과 자리를 만들었다"는 것이 제품에서 생기지 않는 상태를 시험한 것인가(생기지 않으면 그 시험의 값은 무엇인가. 보강 실행이 예산 초과가 되는 제품 경로 = 테스트 작성 세션: 그 경우의 시험이 있는가).
7. **한계의 판정.** "이어받는 실행의 첫 구현 세션은 원 실행의 앞 시도 사유(검사 실패 등)를 받지 않는다"(ADR-128): 회귀 중 예산 초과 → 이어받은 구현 세션이 왜 다시 하는지 모르고 같은 구현을 되풀이할 수 있다. 무결성은 아니고 비용(사슬 누적 한도 안)이다: 비차단인지, 작은 고침(원 실행의 마지막 미충족 사유를 `basisSteps`처럼 읽어 넘기기)이 이 PR의 범위인지 의견.
8. **구조 시험과 ADR.** `integrity.test.ts`의 새 구조 시험(단계 폴더에 `lastPassed` · `acceptanceBaselineOf`에 `context.steps`를 넘기는 자리가 없고 `basisSteps(context)`를 쓰는 파일은 여섯)이 정규식인가 구문 트리인가, 빠져나가는 꼴(별칭 · 구조 분해)이 있는가. ADR-152의 문장마다 코드와 맞는가. ADR 머리줄: 이 브랜치는 150 다음 152다(151은 열린 PR #327의 것). `grep -c 'udb40' docs/decisions.md`는 2. `docs/architecture.md`.
9. **변이.** 구현자의 것(PR 본문 표: 13행)과 겹치지 않게 8 ~ 10종. 후보: ⓐ `continuationStartOf`가 마지막 시도 대신 "통과한 시도가 하나라도 있으면" 이어받기(회귀로 무효가 된 단계를 이어받음), ⓑ 시작 단계를 `currentStep`의 **다음** 단계로(멈춘 단계를 건너뜀), ⓒ `fromStatus`가 `failed`인 시도도 이어받기, ⓓ `basisSteps`가 이어받은 시도를 자기 단계 **뒤**에 두기(`lastPassed`가 원 실행 것을 고름), ⓔ 병합 실행기만 `context.steps`로(구현자는 "각 해당 시험"이라 했다: 병합은 어느 시험인가), ⓕ `lineageCounts`가 바로 앞 실행만 세기(사슬 2단), ⓖ 테스트 작성 재시도에서 이어받은 시도를 세기, ⓗ 유형 C에서 Green 해시 대신 Red 해시를 읽기, ⓘ `#drive`가 저장 전 레코드로 돌게(구현자 것과 같으면 생략), ⓙ 사슬의 조상이 아닌 실행을 가리키는 `inherited` 행을 근거로 받아들이는지(위조 행을 DB에 넣는 탐침 시험: 지금 코드가 무엇을 하는지 보고). 변이마다 어느 시험이 빨강이 됐는지 표로 낸다. 빨강이 안 된 변이는 차단 후보다(제품에서 생기지 않는 상태면 근거와 함께 비차단).
