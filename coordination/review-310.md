## 구현자가 정한 것 (네가 타당성을 판정한다)
- `norms/norm-input.ts`에 `blockScopeOf`. `collectNormInput`의 넷째 선택 인자 `{ blockBasisRuleIds }`. 고르는 때: 블록 선언이 있고 **기준 규칙이 모두** 대상 블록을 가질 때뿐. 기준 규칙이 없거나, 하나라도 대상 블록이 비었거나, 없는 규칙 ID면 전체.
- 세션별 기준: 규칙 작성(새 요구사항 · 다시 시도) = 기준 없음 → 전체. 요구사항 재판단 = 효력 있는 자식 규칙. 테스트 작성 · 구현 = 실행의 대상 규칙. 이의 판단 = 이의 대상 + 실행의 대상 규칙. 검사 실패 판단 = 실행의 대상 규칙 + 실패한 규칙.
- 겹침 = 대상 블록 이름의 교집합이 비어 있지 않음(이름 그대로, `dependsOn`으로 넓히지 않음). 대상 블록 없는 규칙(내장 구조 규칙 · 계약 검사 규칙 · 옛 규칙)은 늘 넣는다.
- 요구사항: 초점 요구사항 + 고른 규칙의 부모 + **효력 있는 자식 규칙이 없는 요구사항**. 계약: 검사 규칙이 고른 규칙인 계약 + 부모 요구사항이 고른 요구사항인 계약 + 검사 규칙도 부모도 없는 계약(지금은 계약 검사 규칙의 대상 블록이 늘 비어 사실상 전부 실린다).
- 먼저 고르고 그다음 기존 A15 줄이기. 세션 기록 `SessionNormInput`에 선택 칸: 종류별 `outOfBlock`, `summary.blocks`. 고른 세션에만 자료 첫 줄에 고정 문장(`normInputScopeLine`)과 머리말의 수.
- K1의 "규범이 많아지면"을 수용 기준대로 "블록 선언이 있으면"으로 읽었다(수 문턱 없음).

2. **K1 · A15의 해석.** ADR-100의 K1 원문이 무엇을 정했는지(고르는 조건이 "블록 선언이 있으면"인가 "규범이 많아지면"인가, 무엇을 고르라고 했는가) 읽고 구현 · 수용 기준 · ADR-140의 해석이 그 범위 안인지 판정한다. ADR-100은 사람 결정이고 그 명세 변경 목록의 항목은 명세보다 우선한다: K1이 수 문턱을 요구하는데 구현이 문턱 없이 늘 고르면 차단 후보(수용 기준 문장은 "대상 블록이 선언된 프로젝트에서"다: 수용 기준과 K1이 어긋나면 그 사실을 적는다). A15의 줄이는 규칙을 **그대로** 쓰는가(줄이는 코드의 `-` 줄이 로직을 바꿨는가, 고른 범위를 입력으로만 넣는가).
3. **고르는 규칙의 안전성 (NFR-02 · 역할 분리).**
   - 고르기는 세션이 받는 자료를 **줄이는** 변경이다. 새로 들어가는 자료가 있는가(예: "효력 있는 자식 규칙이 없는 요구사항"을 넣는 것은 전에도 들어갔던 것인가. 전체일 때의 부분집합인지 확인: 고른 결과 ⊆ 전체 결과여야 한다. 시험이 그 성질을 단언하는가).
   - 세션별 기준 표가 타당한가. 특히 (가) 규칙 작성 세션을 전체로 둔 것(모순 판단에 필요한 규범을 빼지 않는다: K1이 규칙 작성 세션도 고르라고 했는지 원문 확인), (나) 요구사항 재판단의 기준 = 효력 있는 자식 규칙: 자식 규칙이 여러 블록에 걸치거나 하나라도 대상 블록이 없으면 전체로 가는가, (다) 검사 실패 판단: 실패한 **기존 규칙**이 블록 밖이어도 판단 입력에 초점으로 들어가는가(시험 `check-regression.test.ts`의 M3-29 절을 읽고, "판단 입력에서 블록 밖 실패 규칙 빼기" 변이를 네가 다시 넣어 본다), (라) 이의 판단에서 "기준에 더한 대상 규칙은 초점이 아니어서 상한을 넘으면 빠질 수 있다"는 한계가 판단을 그르칠 수 있는가.
   - 겹침 판정: 대상 블록 이름 비교가 선언의 이름과 같은 정규화(대소문자 · 공백)를 쓰는가. 선언 외 이름을 가진 규칙끼리 같은 이름이면 겹친다고 보는 것이 맞는가. 대상 블록이 여러 개인 규칙. **폐기 · 삭제 · 잠정 규칙**이 기준이나 결과에 섞이지 않는가(효력 모듈을 그대로 쓰는가).
   - "기준 규칙 중 하나라도 대상 블록이 비면 전체"가 보수적인 쪽인지, 반대로 **기준에 내장 규칙이 섞인 실행**(유형 B: 대상이 내장 구조 규칙 · 계약 검사 규칙, 대상 블록이 빈 목록)에서 어떻게 되는가(전체로 간다: 맞는가). 방금 병합된 M3-06(유형 B · C · D)의 세션들이 이 함수를 어떻게 부르는지 main의 호출 자리로 확인한다(이 PR의 기준 main `e5e3a09`는 M3-06을 포함한다).
   - 고른 세션에 넣는 고정 문장(`normInputScopeLine`)이 길고 블록 이름을 싣는다: 블록 이름은 사람이 선언한 글이다. 표시 값 변환 · 길이 상한을 거치는가(블록 이름에 줄 바꿈 · 제어 글자 · 아주 긴 이름을 선언 스키마가 막는가). 문장의 사실성("검사 단계는 효력 있는 규칙 전체를 판정한다")이 유형 B · C · D에서도 맞는가.
