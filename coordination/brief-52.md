## 해야 할 것 (수용 기준 순서)
1. **변이 주입 세션 · 고정 도구 `propose_mutant` · 판정** (`orchestrator/test/mutation.test.ts`).
   - 새 역할(변이 주입). 세션은 기존 역할과 같은 틀(SDK 내장 도구 없음, BIVE MCP 고정 도구만, 경로 가드, 규범 입력, 예산, 세션 기록)로 띄운다. 이 역할이 **읽을 수 있는 것**: 대상 규칙의 진술과 대상 블록의 소스 파일(읽기 전용). **볼 수 없는 것**: 인수 테스트(대상 규칙의 인수 테스트를 보여 주면 그 테스트만 피하는 변이를 고를 수 있다 → 역할 분리. 문서가 달리 정하면 문서대로, 없으면 보지 못하게 하고 ADR에 근거). **쓸 수 있는 것**: 없음(작업 트리를 고치지 않는다). 유일한 출력은 `propose_mutant`다.
   - `propose_mutant`: 대상 블록 파일 **안**의 **단일 패치**(파일 하나, 한 군데). 인자의 모양과 검증을 정한다(파일 경로가 그 규칙의 대상 블록의 `include`에 드는가, 인수 테스트 · 설정 · 계약 원본 · 잠금 파일 · `.bive` 계열이 아닌가, 패치가 그 파일에 깨끗이 적용되는가, 크기 상한, 한 세션이 낼 수 있는 변이 수(규칙마다 1개가 기본)). 검증에 걸리면 도구 오류로 돌려주고 판정하지 않는다. 변이의 내용(패치)은 에이전트가 쓴 글이다: 저장 · 표시 때 기존 방식(표시 값 변환 · 상한)을 따른다.
   - 판정: 오케스트레이터가 **격리 워크트리**(실행 워크트리 · 기준 브랜치를 건드리지 않는 새 체크아웃. `judgeCommit`의 깨끗한 체크아웃 방식을 쓴다)에 패치를 적용하고 **대상 규칙의 인수 테스트**를 판정 러너로 돌린다. 실패하면(= 테스트가 변이를 잡음) '변이 검증됨'(`verified`), 통과하면 '변이 생존'(`survived`)을 그 규칙에 저장한다. 판정할 수 없는 경우(패치가 적용되지 않음, 빌드 · 설치 실패, 수집 오류, 러너 오류, 시간 초과)를 무엇으로 볼지 정한다: 빌드가 깨지는 변이를 '검증됨'으로 세면 검출력을 과장한다 — **닫힌 쪽(검증됨으로 세지 않는다: 미검증으로 남기거나 단계 미충족)**으로 정하고 ADR에 적는다. 변이는 어떤 경우에도 병합 대상 브랜치 · 실행 브랜치에 남지 않는다(시험이 단언).
   - 변이 결과의 저장: shared `MutationResult`와 store의 기존 표가 있으면 그것을, 없으면 마이그레이션 0026으로. 규칙별 최신 변이 상태와 기록(실행 · 시각 · 패치 요약 · 판정 결과)을 남긴다. 기본값은 '변이 미검증'(`unverified`).
   - 시험: 검증됨(대상 인수 테스트 실패) · 생존(통과) 저장, 도구 인자 검증의 거부 각각(블록 밖 파일 · 인수 테스트 파일 · 여러 파일 · 적용 안 되는 패치 · 상한), 판정 불가 각각, 변이가 실행 브랜치 · 기준 브랜치에 남지 않음, 세션이 인수 테스트를 읽지 못함 · 쓰기 도구가 없음, 예산 기록.
2. **대상 순서와 예산** (같은 시험 파일). 변이 대상 규칙의 순서는 위험도 high → medium → low, 같으면 규칙 ID(표시 ID 순: 자리수 넘김 주의). **위험도 `null`인 규칙의 자리**와 **인수 테스트가 없는 내장 규칙(구조 · 계약 검사)의 처리**를 ADR-139에 정한다(이슈 댓글의 몫). 기본 방침: 내장 규칙은 인수 테스트로 판정하지 않으므로 변이 대상이 아니다(상태는 미검증으로 남고 화면에서 "변이 생존"으로 보이지 않게). 위험도 `null`은 low 뒤(가장 보수적: 값이 있는 것을 먼저). 무엇이 "변이 대상"인가: 그 실행의 대상 규칙만인가, 효력 있는 모든 규칙인가 — 수용 기준 문장과 RUN-02(단계는 실행의 것) · COST-01(예산은 실행의 것)로 정한다(실행의 대상 규칙이 기본). 예산이 중간에 바닥나면 남은 규칙은 '변이 미검증'으로 남는다: 이때 **실행은 어떻게 끝나는가**(예산 초과로 실패인가, 변이 단계만 부분 완료로 병합까지 가는가)를 기존 예산 초과 규칙(COST-01 · ADR-057 · ADR-061)과 병합 순서(변이 단계는 병합 **앞**이다)로 정한다. 시험: 순서(세 위험도 · `null` · 같은 위험도의 ID 순 · EXE/RULE 자리수), 예산 소진 뒤 남은 규칙 미검증, 그때 실행의 끝.
3. **유형 A의 변이 단계가 `skipped`가 아니게 · 변이 생존의 자동 보강** (`mutant-survives` 시나리오).
   - 유형 A(와 문서가 정한 유형: ADR-020 "변이 주입 단계는 A · C(보강)만". 유형 B · D는 그대로 `skipped`)의 변이 주입 단계가 실제로 돈다. 단계의 통과 조건을 정한다: 변이 **생존은 그 실행을 실패로 만들지 않는다**(완료 기준 흐름 3: 실행 '통과', 규칙 카드 예외 '변이 생존', 그 뒤 자동 보강). 변이 단계가 끝나야 병합으로 간다.
   - 변이 생존이면 그 규칙의 **유형 C 테스트 보강 실행**이 사람 확인 없이 자동으로 생긴다(ADR-100 B④, M7-05의 자동 시작 규칙: 규칙마다 실행 1개 · 시작 근거 기록 · 하루 한도 · 프로젝트당 실행 1개 대기 · 승인 단계 자리의 효력 확인. 기존 자동 시작 모듈(`runs/auto-start.ts`)의 길을 그대로 쓴다. 새 시작 경로를 따로 만들지 않는다). 시작 근거(무엇 때문에 생긴 실행인지)를 규범 변경 기록 · 승인 기록의 기존 방식으로 남긴다(새 행동 값이 DB CHECK를 넓혀야 하면 0026에 함께 넣는다).

"변이 재주입"의 뜻을 plan.md · ADR에서 확인). 재주입에서도 생존이면: 테스트 작성으로 회귀(상한) 뒤 실패 — 그때 ADR-100 A17("자동 보강 실행이 실패로 끝나면 그때만 검토 대기열에")의 검토 대기열 등록은 **M3-08의 몫**이다. 이 이슈는 상태('변이 생존' 유지)와 실행 실패 기록까지만 하고 넘길 사실을 ADR에 적는다.
   - 보강의 **무한 고리 방지**: 보강 실행의 재주입 결과가 또 자동 보강을 낳지 않는다(보강 실행 안에서는 재주입이 종료 조건이지 새 실행의 원인이 아니다). 같은 규칙에 보강 실행이 이미 진행 · 대기 중이면 또 만들지 않는다. 시험이 단언한다.
   - 가짜 에이전트 시나리오 `scenarios/mutant-survives.yaml`: 첫 실행(유형 A)에서 변이 주입 세션이 낸 변이가 생존 → 자동으로 유형 C 보강 실행 → 테스트 작성 세션이 그 변이를 잡는 테스트를 더함 → 재주입에서 검출 → '변이 검증됨'. 오케스트레이터 시험과 파이프라인 e2e(`orchestrator/e2e/pipeline/mutant-survives.test.ts`, 실제 판정 러너)가 그 흐름을 끝까지 단언한다. **기존 파이프라인 e2e**: 변이 단계가 실제로 돌게 되면 기존 시나리오(가짜 에이전트가 변이 주입 세션의 대본을 모른다)가 어떻게 되는가 — 대본에 변이 세션이 없을 때의 기본 동작(변이를 내지 않고 끝난 세션 = 그 규칙 '변이 미검증'으로 단계 완료)을 정해 기존 e2e의 **단언을 고치지 않고** 지나가게 한다. 기존 e2e의 기준값(단계 상태 열에 `mutation: skipped`를 단언하는 것 등)을 고쳐야 하면 어느 단언을 왜 고치는지 보고한다(이 이슈가 바꾸는 동작이다: 유형 A의 변이 단계는 `skipped`가 아니게 된다).
   - **CI 시간**: `pipeline-e2e` 묶음 제한 40분(지금 12 ~ 21분), `checks` 제한 30분(지금 약 15분). 변이 판정은 규칙마다 설치 · 빌드를 한 번 더 돌 수 있다: 기존 e2e 전체가 변이 단계 때문에 얼마나 느려지는지 로컬에서 재고(전 · 후), 변이를 내지 않는 대본에서는 판정(설치 · 빌드)을 **돌지 않게** 한다. 새 e2e 파일은 묶음 2에 든다: 늘어난 시간을 보고에 적는다.
4. **설정 화면(SCR-21)의 변이 주입 역할** (`e2e/scr-21-mutation-role.spec.ts`). 설정에 변이 주입 역할의 모델과 한도 입력 칸. 비어 있으면 `validateForRun`이 `SETTINGS_INCOMPLETE`. 기존 역할(테스트 작성 · 구현 · 규칙 작성 등)의 칸과 같은 컴포넌트 · 저장 방식 · 검증을 쓴다. **기존 프로젝트**(변이 역할 설정이 없는 저장된 설정)가 이 변경 뒤 실행을 시작하면 어떻게 되는가: `SETTINGS_INCOMPLETE`로 막히는 것이 수용 기준의 문장이지만, 기존 e2e · 파이프라인 e2e · 픽스처 초기화(`scripts/reset-fixture.sh`) · 시험 도우미의 설정이 모두 그 칸을 채워야 한다. 기본값을 두는지(다른 역할의 선례), 이행(옛 설정을 읽을 때)의 방식을 정해 ADR에 적는다. 변이 단계가 `skipped`인 유형(B · D)도 그 설정을 요구하는가(예산 스냅샷은 유형이 쓰는 역할만 담는다, ADR-136).
5. **화면의 변이 상태**: 규칙 카드 예외 '변이 생존'(SCR-03)과 규칙 상세의 변이 상태가 이미 그려지는지 확인한다(M1에서 미노출로 둔 것, ADR-035). 수용 기준은 화면에서 SCR-21만 요구한다: 카드 예외는 로드맵 "완료 기준 흐름 3"이 기대한다. 이미 그리는 코드가 있어 값만 흐르면 되는 경우는 값이 흐르게 하고 e2e 한 줄을 더한다. 새로 그려야 하는 양이 크면 **하지 말고 보고에 적는다**(조율자가 후속 행으로 뺀다). 검증 화면의 '변이 검증됨' 카드는 이 이슈가 아니다.
6. **ADR-139**: 역할의 입력과 도구(인수 테스트를 보지 못함), `propose_mutant`의 인자와 검증, 격리 워크트리와 판정, 판정 불가의 처리, 저장 모양, 대상과 순서(`null` · 내장 규칙), 예산 소진 때 실행의 끝, 유형별 변이 단계, 변이 생존이 실행 결과에 미치는 영향, 자동 보강의 시작 근거와 중복 · 고리 방지, 보강 세션이 받는 변이 자료, 재주입의 뜻, 재주입 실패 뒤(M3-08로 넘김), 설정의 기본값 · 이행, 기존 e2e에 미치는 영향, ADR-136 한계 가운데 닫은 문장, 남는 한계. `docs/architecture.md` 4장(단계표 · 역할표 · 유형 표)과 IPC · 도구 표를 사실대로 맞춘다.

## 반드시 지킬 것
- **무결성 (NFR-01 · NFR-02 · ADR-100 역할 분리)**: 변이는 판정을 위한 임시 변경이다. 어떤 경로로도 병합 브랜치에 들어가지 않는다. 변이 주입 역할은 작업 트리 · 인수 테스트 · 규범 · 설정을 바꿀 수 없다. 변이 주입 역할이 '변이 검증됨'을 스스로 만들 수 있는 길(빌드를 깨는 패치, 테스트와 무관하게 서버를 죽이는 패치)이 "검증됨"으로 세어져 검출력을 과장하는지 따져 ADR 한계에 사실대로 적는다(서버가 죽어 실패한 것과 테스트가 잡은 것을 가를 수 있으면 가른다: 판정 결과의 케이스 실패 · 수집 오류 구분).
- 유형 B · D와 유형 C(보강 아님)의 동작은 그대로다. 유형 A는 변이 단계 말고는 그대로다. 기존 시험의 단언을 고칠 때는 이 이슈가 바꾸는 동작(유형 A 변이 단계의 상태)에 한하고 목록을 보고한다.
- 자동 시작의 기존 규칙(하루 한도 · 실행 1개 · 효력 확인 · 규칙마다 실행 1개)을 우회하는 새 길을 만들지 않는다. 보강 실행도 사람 주체가 아니다: 승인 기록 · 시작 근거의 주체를 기존 자동 시작과 같게 한다.
- 화면 데이터는 저장된 기록에서만(NFR-03). 목 데이터는 시험 코드 안에만. UI 문구는 화면 정의서의 낱말('변이 검증됨' · '변이 미검증' · '변이 생존' · '변이 주입') 그대로.
- 방어 · 거부 조건마다 "빼면 빨강"인 시험과 변이 결과 표(여기서 "변이"는 네가 제품 코드에 넣어 보는 시험용 변경이다): 블록 밖 파일 허용, 인수 테스트 파일 허용, 여러 군데 패치 허용, 판정 불가를 검증됨으로, 생존을 검증됨으로 뒤집기, 순서 뒤집기 · `null`을 앞에, 내장 규칙을 대상으로, 예산 소진 뒤에도 계속, 변이를 실행 브랜치에 남기기, 자동 보강 중복 · 고리, 재주입 없이 보강 끝내기, 보강 실행을 유형 A로 만들기, 설정 빈 칸을 통과로, 변이 세션에 인수 테스트 보이기.
- 새 종료 사유 · 새 `StepKind`는 만들지 않는 쪽이 기본이다(`mutation` 단계 종류는 이미 있다). 꼭 필요하면 shared · store CHECK(0026) · 앱 표시명 표를 함께 고치고 ADR에 근거.
- `docs/spec/*` · `docs/roadmap.md` · `CLAUDE.md`를 고치지 않는다. 의미 있는 단위마다 로컬 커밋을 남긴다(서명 설정을 끄지 않는다). 권한 · 격리 검사가 거부한 일을 다른 길로 하지 않는다. 프록시 환경 변수 값을 출력하지 않는다. 판정 격리를 돌아가는 대처를 하지 않는다. 실제 API 키를 쓰지 않는다.
- **이 이슈는 PR 하나로 끝내기에 크다고 본다.** 순서대로 한다: ①(세션 · 도구 · 판정 · 저장) → ②(순서 · 예산) → ④(설정) → ③(단계를 실제로 켜기 · 자동 보강 · 재주입 · 시나리오 · e2e) → ⑤. ③을 시작하기 전에 바뀐 파일 수를 센다. **①②④까지 끝낸 시점에 25개를 넘었거나 ③의 설계에 위 "문서로 정한다" 항목 가운데 문서로 풀리지 않는 것이 둘 이상이면**: 변이 단계는 계속 `skipped`인 채(①②④는 시험으로만 도는 상태)로 커밋 · 푸시하고 PR은 만들지 않은 채 멈춰, ③의 설계(선택지와 권고, 풀리지 않은 질문)를 보고한다(조율자가 이슈를 쪼갠다). 그렇지 않으면 끝까지 가서 PR을 만든다. 전체가 45개를 넘을 것 같으면 그때도 멈추고 보고한다.
- 완료 조건 명령: 설치 · 린트 · 타입 · 빌드 · 형식 · 단위 테스트(격리 `TMPDIR`, 알려진 두 시험만 실패 허용) · 화면 e2e(`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=$(ls -d /opt/pw-browsers/chromium-*/chrome-linux*/chrome) pnpm e2e`, `--trace off`) · Electron 스모크(`xvfb-run -a pnpm smoke`) · 픽스처 설치 뒤 `pnpm e2e:pipeline`(`TMPDIR` 격리, 한 시간쯤 걸린다. 출력이 끝에만 나온다: 중간에 멈추지 않는다). 시험 뒤 `ps`로 네 작업 공간 · 네 `TMPDIR` 경로의 프로세스가 남지 않았는지 확인한다(PID · cmdline · cwd를 확인한 네 PID만 끝낸다).
- PR을 만들었으면 **`ci` 성공까지 확인한 뒤** 보고한다.
