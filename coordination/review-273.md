## 꼭 판정할 것
1. **범위.** `git diff 3169273...HEAD --stat`. 오케스트레이터 · store · parser · 시나리오 · `docs/spec/*` · `CLAUDE.md` · 구조 시험이 바뀌지 않았는가. shared 변경이 표시명 표 · 값 목록 추가뿐인가(저장 스키마 · 프로토콜 형식을 바꾸지 않았는가).
2. **[문제만] 토글을 감춘 결정.** 구현자의 근거: 화면 정의서 1.4가 문제 항목을 "2줄째 예외가 있는 항목"으로 정하고 확인할 것 항목은 모두 예외를 가지므로 토글이 아무것도 거르지 않는다. 이 근거가 명세 문장 · ADR-119와 맞는가(확인할 것 항목에 예외가 없는 종류가 지금 정말 없는가를 `confirmation.list` 응답 형식과 화면 코드로 확인). 감춘 것이 다른 화면(규칙 · 요구사항 목록)의 토글을 건드리지 않았는가. ADR-123에 다시 두는 조건이 적혔는가.
3. **대상 링크의 카드 선택.** `navigation/pendingSelection.ts`는 모듈 수준 상태다. 다음을 따진다: 링크를 누른 뒤 목록을 읽기 전에 다른 화면으로 가면 남은 값이 나중에 엉뚱한 화면에서 쓰이는가, 프로젝트를 바꾸면 지워지는가, 같은 대상을 두 번 누르면 두 번째도 동작하는가, 사용자가 걸어 둔 필터 · 검색어 때문에 대상 카드가 목록에 없을 때 어떻게 되는가(필터를 조용히 바꾸는가, 안 고르는가. 어느 쪽이든 ADR에 적혔고 시험이 있는가), 폐기된 규칙에서 [폐기 포함]을 켠 것이 그 뒤 화면 상태로 남는 것이 의도인가. 없는 대상일 때 "선택 항목 없음"이 문구 원칙에 맞는가.
4. **죽은 코드 삭제.** `unread` · `decision` 관련 코드가 정말 쓰이지 않았는가(삭제 전 main에서 grep). CSS 삭제(`.card-unread` · `.card-end`)가 다른 카드 배치를 깨지 않는가(화면 시험 · 넘침 검사 결과로). `card-line.spec.ts` · `support/overflow.ts`에 남았다는 안 읽음 점 선택자가 "늘 빈 결과"로 통과하는 죽은 단언이 됐는가. 그렇다면 비차단으로 적되 무엇을 지워야 하는지 적는다.
5. **실행 종료 사유 표시.**
   - 자리 결정(규칙 상세 "실행 이력" 줄)이 화면 정의서와 맞는가. 구현자는 ADR-073의 "판정 기록 1건마다 한 줄"을 "실행당 한 줄"로 바꿨다. ADR-123이 ADR-073의 어느 문장을 대체하는지 분명히 적었는가, 명세 문장과 부딪치지 않는가(부딪치면 PRD > 화면 정의서 > 기획서 순).
   - `RunFailureReason` 42개 값: 오케스트레이터가 실행을 끝낼 때 실제로 남기는 값과 같은가를 네가 직접 센다(`runEnding(` 호출과 `failureReason` 대입을 grep. 구현자의 시험은 "소스 글을 읽어 모은다"고 했다. 그 시험이 app 패키지에서 오케스트레이터 소스 파일을 읽는 방식이 패키지 의존 방향(`docs/architecture.md` 2장)과 빌드 · CI에서 문제가 없는가, 변수로 넘기는 경로를 놓치는 한계가 ADR 또는 시험 주석에 적혔는가). 병합 관리자 결과 값(`vetoed` · `base_changed` 등)이 정말 `Run.failureReason`으로 저장되는 값인가, 다른 칸(`exitDetail`)의 값을 섞은 것은 아닌가.
   - 표시명 42개를 전부 읽는다: 화면 정의서 1.1(명사형, 이모지 없음, 코드 표기 없음), 문서 기호 없음, 영어 낱말(`git 오류` 같은 것)이 기존 화면 문구의 쓰임과 맞는가, 서로 구별되는가, 사용자가 뜻을 알 수 있는가. app이 "같은 표를 다시 적고 시험이 대조"한다는 방식이 기존 판단 주제 표와 같은 방식인가.
   - 모르는 값은 "알 수 없는 사유"로만 보이는가(원문 식별자가 툴팁 · title 속성 · 접근성 이름 · 데이터 속성으로 새지 않는가). 사유가 붙는 조건(실패 · 예산 초과로 끝난 실행만)이 맞는가. `interrupted` · `merged` 실행 줄은 어떻게 보이는가.
   - `exitDetail`을 보이지 않는다는 결정이 코드와 맞는가(상세 글이 다른 길로 화면에 나오지 않는가).
6. **실행 이력의 새 데이터 길.** 규칙 상세가 `run.list`를 읽어 판정 기록과 합친다.
   - 합치는 열쇠가 무엇인가(실행 ID). 다른 규칙만 대상인 실행이 섞이지 않는가, 한 실행이 여러 규칙을 다루는 경우(검사 단계가 모든 규칙을 판정) 대상 규칙이 아닌 규칙의 상세에 그 실행이 어떻게 보이는가. 정렬 순서가 정해져 있는가.
   - `run.list` 실패 시 "실행 상태 불러오기 실패"를 보이고 판정 기록만으로 그린다는 동작이 시험으로 고정됐는가. 화면이 값을 지어내지 않는가(NFR-03).
   - 다시 읽기: `event.run.updated`마다 상한 없는 `run.list`를 다시 읽는다. 실행이 도는 동안 알림 빈도와 겹쳐 요청이 쌓이지 않는가(진행 중 요청이 있을 때 겹침 처리, 늦게 온 응답이 새 응답을 덮는 경쟁). 수용 기준의 "알림 한 번에 한 번"이 `normChange.list`에 대해 지켜지고, 새로 더한 `run.list` 읽기도 같은 원칙인가.
7. **수용 기준 4의 시험들.** 각 단언이 실제로 그 성질을 고정하는가: 다시 읽기 횟수 시험이 호출 수를 정확히 세는가(구현자가 "처음 변이를 못 잡아 목록 응답을 늦추도록 고쳤다"고 했다. 고친 시험이 시간에 기대 불안정하지 않은가. 고정 대기 · `waitForTimeout`이 있는가), `replace` 뒤 다시 읽기, U+2028 · U+2029, SCR-05 '없음' 빈 목록.
