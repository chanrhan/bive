## 사실 (조율자가 확인한 것 · 구현자 보고)
- #52의 브랜치가 끝낸 것: 역할 `mutator`(표시명 "변이 주입"), 도구 `propose_mutant {path, search, replace}`(세션마다 1개), 격리 체크아웃에서의 판정(`judgeCommit`의 `applyMutant`), 저장 표 `project/0026_mutation_results`, 대상 = 실행의 대상 규칙 · 순서 위험도 high → medium → low → 없음 · 같으면 표시 ID 순, 내장 규칙 · 대상 블록 없음 · 인수 테스트 없음은 대상 아님, 예산 소진이면 실행 `budget_exceeded`, SCR-21의 "변이 주입" 행과 `RUN_REQUIRED_ROLES`(기본값 없음: 옛 설정은 사람이 채울 때까지 `SETTINGS_INCOMPLETE`). 제품의 변이 주입 단계는 그대로 `skipped`다(실행기는 기본 목록에 없다).
- 남은 것(새 행 M3-54의 몫): 유형 A(와 유형 C 보강)의 변이 주입 단계를 실제로 켜기, 변이 생존이면 그 규칙의 유형 C 테스트 보강 실행을 사람 없이 자동으로 만들기, 보강 실행의 종료 조건인 변이 재주입, `mutant-survives` 시나리오와 파이프라인 e2e, 규칙 카드 예외 '변이 생존'(로드맵 완료 기준 흐름 3번이 기대한다. `rule.list`에 변이 상태 칸이 아직 없다).
- 문서로 풀리지 않은 질문과 **조율자 결정**(ADR-141에 "결정"으로 적고, M3-54의 수용 기준에 검증 가능한 문장으로 넣는다. 세부 모양은 M3-54의 ADR이 정한다):
  1. 자동 보강의 시작 근거: 지금 자동 시작의 원인은 규범 변경 기록 `created` 순번(또는 승인 기록 순번)뿐이다. **결정**: 변이 결과 기록(생존)을 원인으로 하는 새 원인 종류를 두고(저장 CHECK를 넓히는 마이그레이션 포함), 시작 근거 대조 · 하루 한도 · 프로젝트당 실행 1개 · 효력 확인은 기존 자동 시작의 길을 그대로 쓴다(새 시작 경로를 따로 만들지 않는다).
  2. 보강 실행의 표시: 유형 C 실행이 "보강"인지(재주입이 종료 조건인지)와 어느 변이 결과 때문인지를 저장할 칸이 없다. **결정**: 실행 표를 다시 만들지 않고 실행과 변이 결과를 잇는 저장(새 표)을 둔다.
  3. 변이 글의 전달: 변이 주입 역할이 쓴 글(바꿀 글 · 바꾼 글)을 테스트 작성 역할에 넘겨도 되는가. **결정**: 넘긴다. 다만 ADR-128의 앞 시도 자료와 같은 방식(틀 · 상한 · 표시 값 변환)을 거친 자료로만. 근거: 보강 세션이 무엇을 잡아야 하는지 모르면 보강이 성립하지 않고(ADR-100 B④), 이 흐름은 어느 역할도 자기 산출을 스스로 채점하게 만들지 않는다(판정은 재주입에서 판정 러너가 한다).
  4. 예산 소진 뒤: **결정**: 기존 규칙 그대로(실행 `budget_exceeded`, 병합 없음, 남은 규칙 '변이 미검증'). M3-07의 구현이 이미 그렇게 했다.
  5. 재주입의 뜻: **결정**: 살아남았던 **같은 변이**를 다시 적용한다(새 변이 세션을 열지 않는다. 결정적이다). 재주입에서도 생존이면 테스트 작성으로 회귀하고 상한 뒤 실패로 끝낸다. 그 실패를 검토 대기열에 올리는 것은 M3-08의 몫이다(ADR-100 A17).
  6. 고리 · 중복 방지: **결정**: 보강 실행의 재주입 결과는 새 자동 시작의 원인이 아니다. 같은 규칙에 대기 · 진행 중인 보강 실행이 있으면 또 만들지 않는다.
