# run-milestone

조율자가 직접 따른다. 구현 · 리뷰 · QA는 전부 서브에이전트. 조율자는 브랜치 이름, PR 번호, 판정만 기억한다. 서브에이전트 모델은 구현 · 리뷰 · QA가 `opus`, 기계적 작업(발행, 표 갱신)이 `sonnet`이다.

## 준비

1. `scripts/gh-rest.sh GET "repos/chanrhan/bive/issues?milestone=<번호>&state=open&per_page=100"`로 이슈 목록을 받고, 본문의 `## 의존`과 로드맵 표로 위상 정렬한다. 의존이 다른 마일스톤의 미완료 이슈면 그 이슈를 먼저 처리하거나 needs-human으로 보고.
2. 📍 이슈(#1)에 "Mn 시작: 이슈 k개" 한 줄.
3. 기본 브랜치를 최신으로: `git fetch origin main && git checkout main && git reset --hard origin/main`.

## 조율 규칙 (실제로 사고가 났던 것들)

- **동시 서브에이전트는 최대 3개.** 구현 · 수정 · 검토를 모두 합친 수다. 그보다 많으면 VM 부하로 프로세스 기동 시험이 시간 초과되고 사용량 한도에 걸린다.
- **CI 대기는 15분까지.** PR의 `mergeable_state`가 `dirty`(충돌)면 CI가 아예 생기지 않으므로 기다리지 않는다. main을 병합해 충돌을 풀고 다시 푸시한다.
- **PR을 머지한 직후 열려 있는 다른 PR의 충돌을 확인한다** (`git merge-tree --write-tree --name-only origin/main origin/<브랜치>`). 충돌이 문서뿐이면 조율자가 직접 병합하고, 코드가 걸리면 구현 서브에이전트에게 넘긴다.
- **PR을 닫았다 열거나 빈 커밋을 푸시해 CI를 다시 돌리지 않는다. 강제 푸시 · 리베이스도 하지 않는다.** CI가 돌지 않거나 실패하면 원인을 고친 실제 커밋을 푸시하고, 안 되면 보고하고 멈춘다.
- **구현 서브에이전트의 작업 공간(worktree)은 PR이 머지될 때까지 지우지 않는다.** 지우면 그 서브에이전트를 다시 깨울 수 없다. 검토 서브에이전트의 작업 공간은 보고를 받으면 지운다.
- **임시 파일을 격리한다.** 테스트는 `TMPDIR`을 worktree마다 따로 주고, 공용 scratchpad에 두는 로그 · PR 본문 파일은 이름에 이슈 번호를 넣는다.
- **새 이슈를 만들면 같은 날 로드맵에 행을 더한다** (`docs/roadmap-format.md`). 키는 기존 키와 겹치지 않는지 확인한다.

## 이슈 처리 (의존이 풀린 이슈는 최대 3개까지 병렬, 같은 패키지를 크게 고치는 이슈는 직렬)

### a. 구현 서브에이전트 (모델 opus, `isolation: worktree`)

브리핑에 반드시 넣을 것: 이슈 번호 · 제목 · 본문 전체(수용 기준), 관련 PRD · SCR · ADR 절의 **본문 발췌**, 브랜치 이름 `feat/<번호>-<slug>`(bug면 `fix/`, chore면 `chore/`), CLAUDE.md 4장 규칙, "테스트를 끄지 말 것", "범위 밖 변경 금지", 완료 조건 = CLAUDE.md 5장의 명령(화면을 고치지 않았으면 e2e · 스모크 제외) 통과 후 push + PR 생성(제목 = 이슈 제목, 본문 템플릿 채움, 첫 줄 `Closes #번호`), 위 조율 규칙 중 CI 대기 상한 · 금지 행동 · 임시 파일 격리, 커밋 트레일러(세션이 지정한 값). PR 번호와 실행한 명령 · 결과를 보고하게 한다.

### b. CI

PR 최신 커밋의 체크를 `GET repos/chanrhan/bive/commits/<sha>/check-runs`로 확인. 빨강이면 같은 서브에이전트(SendMessage)에게 로그(`get_job_logs`)를 주고 고치게 한다. 3회 실패하면 이슈에 코멘트를 남기고 needs-human 여부를 판단.

### c. 리뷰

`pr-reviewer` 스킬 절차로 새 서브에이전트에게 검토시킨다. REQUEST_CHANGES면 차단 지적만 구현 서브에이전트에게 넘겨 수정 → CI → 재검토. 최대 2회. 그래도 남으면 PR을 그대로 두고 이슈를 쪼개 로드맵 · GitHub에 반영한다.

### d. 머지

APPROVE + CI 초록이면 `merge_pull_request`(squash, 제목 = 이슈 제목). 머지 후 `git fetch origin main`. 이슈가 `Closes`로 안 닫혔으면 닫는다.

### e. 기록

📍 이슈(#1)에는 이슈나 머지마다 코멘트하지 않는다. 머지 기록은 닫힌 PR 목록에 남는다. 코멘트는 다음 때만 한 줄씩 남긴다: 마일스톤 시작, 마일스톤 끝(회고), 일시 정지, 재개, 운영 방식이 바뀔 때(사람 지시 포함).

## 일시 정지와 재개

사람이 멈추라고 하면 새 서브에이전트를 띄우지 않는다. "진행 중인 작업까지만"이면 돌고 있는 서브에이전트의 보고를 받아 APPROVE + CI 초록인 PR만 머지하고, 수정 요청은 다음 작업으로 남긴다. "지금 멈춰"면 서브에이전트를 중단한다(작업 내용은 브랜치 · 작업 공간에 남는다). 멈출 때 📍 이슈에 한 코멘트로 적는다: 현재 머지 수, 열린 PR마다 상태와 남은 지적, 재개하면 할 일 순서, 열린 needs-human 이슈. 재개할 때는 그 코멘트와 저장소 상태(`git fetch`, 열린 PR, 작업 공간 목록)부터 확인한다.

## 마일스톤 마무리

1. 모든 이슈가 닫혔는지 확인. 남은 이슈는 사유(needs-human · 분할 · 다음 마일스톤 이월)를 이슈 코멘트에 적는다.
2. CLAUDE.md `<!-- KICKOFF -->` 칸의 완료 조건 명령과 `dev-env` 스킬의 명령 표가 현재 저장소에서 실제로 도는지 한 번 실행해 보고 다르면 고친다(PR `chore/kickoff-commands`).
3. QA는 운영 프롬프트 4-b 절차로 **구현에 관여하지 않은 새 서브에이전트**에게 맡긴다. 버그 이슈가 생기면 이 스킬의 "이슈 처리"로 같은 마일스톤에서 처리. 검수 → 수정 반복은 최대 2회.
4. 📍 이슈에 회고 코멘트: 머지된 PR 수 · 검수 판정 · needs-human 목록 · 새 ADR · 로드맵 조정이 필요해 보이는 점.
5. 다음 마일스톤은 사용자 지시를 기다린다. (운영 프롬프트가 "계속"을 대신 지시한 경우 바로 다음 마일스톤으로 간다.)
