## 1. 문제 정의

### 1.1 배경

- 에이전트 코딩 확산으로 **코드 생산 속도 > 사람의 검토 속도**
- 검증은 여전히 사람이 코드를 읽는 방식에 의존

### 1.2 문제

| # | 문제 | 결과 |
|---|---|---|
| 1 | 코드를 직접 읽어야 검증 가능 | 검토가 개발 속도의 병목 |
| 2 | 에이전트가 임의로 추가한 기능 · 설계를 파악할 수단 없음 | 인지 부채 누적, 다음 기획 불가 |
| 3 | 에이전트의 "통과" 보고를 검증할 근거 없음 | 약한 테스트 · 테스트 조작 미검출 |
| 4 | 요구사항과 코드의 불일치(드리프트) 추적 불가 | 무엇이 지켜지고 있는지 모름 |

### 1.3 가설

> 코드 대신 **규범(요구사항 · 규칙 · 계약)과 실행 기반 판정**을 보면, 코드를 읽지 않고도 에이전트 작업 검증 가능

- 검증 방법: 7장 성공 지표(코드 열람 횟수 · 사유)

## 4. 기능 요구사항

> **우선순위 (후보)** · **P0** 첫 슬라이스 필수 · **P1** MVP · **P2** 이후

### 4.1 프로젝트

| ID | 요구사항 | 우선 | 수용 기준 |
|---|---|---|---|
| PRJ-01 | 폴더 열기로 프로젝트 연결 | P0 | 폴더 선택 후 프로젝트 화면 진입. 미연결 폴더면 설정 파일 생성, 이미 연결된 폴더는 생성 없이 진입 |
| PRJ-02 | 기존 프로젝트 동기화 | P1 | 동기화 = 설계 메타(블록 선언 등) 생성. 설정 파일 생성(PRJ-01)과 별개. 동기화 후 블록 · 의존 · ERD 표시 |
| PRJ-03 | 요구사항 자동 생성 (코드 역추출) | P2 | 결과가 승인 대기에만 등록. 승인 전 규범 미반영. 잠정 승인 대상 아님 |

### 4.2 규범

| ID | 요구사항 | 우선 | 수용 기준 |
|---|---|---|---|
| NRM-01 | 요구사항 작성 · 수정 · 삭제 | P0 | 사람의 직접 편집과 지시(DSN-07) 모두 가능. 직접 편집은 승인 불필요. 생성 주체 · 시각 기록 |
| NRM-02 | 요구사항 → 규칙 자동 생성 | P0 | 규칙마다 제목(사람이 읽는 요약, 표현은 작성 규칙 NRM-10) + 진술(EARS, 판정용) + 검사 종류 1개 이상 지정 + 부모 요구사항 연결. 검사 산출물(테스트 파일)은 테스트 작성 단계에서 생성. 생성된 규칙은 승인 대기 등록 (NRM-04) |
| NRM-03 | 계약 등록 (OpenAPI · DB 스키마 · AsyncAPI) | P1 | 표준 포맷 파일 연결 (등록 단위 = 파일). `contract` 검사 규칙 연결. 요구사항과의 연결 단위(파일 / 엔드포인트 · 테이블) `미정` |
| NRM-04 | 에이전트 제안 · 승인 · 거절 | P0 | 제안(요구사항 · 규칙 · 신규 계약)은 승인 대기 등록. 승인 전 규범 미반영 (예외: NRM-05 잠정 승인). 승인 화면에서 사람이 제안 문장을 고친 뒤 승인 가능, 수정 내용과 주체 기록 (확정). 승인된 규칙 · 계약의 변경은 지시(DSN-07)로만. 예외: 규칙 제목 변경은 작성 규칙 적용(NRM-10)으로도 제안 가능, 진술 · 판정 불변. 거절 사유 필수 (확정) |
| NRM-05 | 잠정 승인 | P1 `미정` | 사람 승인 전 효력을 갖는 별도 상태. 도구 정책만 부여, 에이전트 호출 불가 (NFR-01). 잠정 항목 별도 표시, 준수 지표에서 분리 집계 (JDG-03). 거절 시 되돌리는 실행 생성 (RUN-07 유형 D) |
| NRM-06 | 추적성 결함 표시 | P1 | 규칙 없는 요구사항 · 부모 요구사항 없는 규칙의 개수와 목록 표시. 내장 구조 규칙(JDG-05)과 '규칙화 불가' 요구사항(NRM-08)은 결함에서 제외 |
| NRM-07 | 규범 변경 이력 | P1 | 변경 내용 · 시각 · 주체 · 연결 실행 표시 |

### 5.1 제품 형태 · 프로세스 구성

- M1 범위를 가르는 구성 결정만 기록. 세부 구현은 다루지 않음

| 항목 | 결정 | 상태 |
|---|---|---|
| 구성 | 화면 앱, 백그라운드 프로세스(오케스트레이터), 에이전트 프로세스(세션당 1개)의 3층 | 확정 |
| 화면 앱 | Electron. 화면은 React · TypeScript | 확정 (React는 기본값) |
| 오케스트레이터 | Node 프로세스. Claude Agent SDK(TypeScript) 사용. 화면 앱과 분리되어 앱 종료 후에도 유지 (NFR-06). 사용자당 1개, 여러 프로젝트 관리 | 확정 (사용자당 1개는 기본값) |
| 통신 | 로컬 파이프(Windows named pipe, macOS · Linux Unix 소켓). TCP 포트 미개방. 승인 요청은 이 경로로만 수신 (NFR-01). 같은 사용자 권한의 다른 프로세스 접근은 완전 차단 불가, 승인 기록으로 증거 | 확정 |
| 백그라운드 수명 | 앱 실행 또는 실행 시작 시 기동. 진행 중인 실행이 없고 앱이 닫혀 있으면 자동 종료. 꺼져 있던 동안의 코드 변경은 다음 기동 시 커밋 비교로 감지 | 확정 |
| 끊김 복구 | 비정상 종료 후 재기동 시 실행을 '중단'으로 표시. 사람이 재개하면 마지막 완료 단계 다음부터 새 세션으로 시작. 자동 재개 없음 | 확정 |
| 에이전트 세션 설정 | 사용자 · 프로젝트 설정 비로드, 자동 메모리 비활성 (NFR-02) | 기본값 |
| Claude 인증 | 본인 사용은 구독 로그인, 배포 시 API 키 (v5 8.7) | 기본값 |
| 확인 필요 | 패키징된 앱에서 SDK 내장 실행 파일 호출, Windows에서 앱 종료 후 백그라운드 프로세스 유지, 에이전트 프로세스의 메모리 사용량(세션당 약 1GB가 출발점) | `미정` M1에서 실측 |
