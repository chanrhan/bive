# BIVE 결정 기록 (ADR)

> 운영 프롬프트 1단계 규칙에 따라, 문서(docs/spec/plan.md · prd.md · screens.md) 사이에 충돌하거나 구현에 필요한데 빠진 내용에 대해 **가장 보수적인 해석**을 골라 기록한다.
> 모든 항목의 상태는 `제안 (에이전트)`이며, 사람이 확인하면 `채택` 또는 `기각`으로 바꾼다. 기각 시 영향받는 코드 · 로드맵을 함께 고친다.
> 형식: 맥락 → 결정 → 결과. 근거 문서 위치를 ID로 적는다.

## ADR-001 요구사항 · 화면 ID 체계

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: 운영 프롬프트는 FR-001 / NFR-001 / SCR-01 형식을 요구하지만 PRD에는 이미 PRJ · NRM · RUN · JDG · DSN · TODO · COST · MET · COL · NFR 체계가 있고, 기획서 · 화면 정의서가 그 ID를 교차 참조한다.
- 결정: 요구사항 ID는 PRD 원본 ID를 그대로 쓴다 (FR-xxx 재번호 없음). 화면은 SCR-01~21을 부여하고 원본 ID(S-01 · P-01 · D-01 · R-01 · T-01 · X-01)를 병기한다. 매핑은 docs/spec/screens.md 1.3.
- 결과: 로드맵 커버리지 표의 행 키는 PRD ID와 SCR ID. 코드 · 커밋 메시지에서 화면은 SCR ID로, 요구사항은 PRD ID로 부른다.

## ADR-002 화면 정의서의 `PRD 반영 필요` 태그 처리

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: 화면 정의서 v0.5가 `PRD 반영 필요`로 표시한 항목(거절 사유 필수 NRM-04, 회귀 상한 2회 RUN-02, 승인 대기 상한 40건 TODO-04, 검토 대기열 처리 액션 TODO-02, 유형 C 종료 조건 RUN-07, 규칙 제목 NRM-02, 규칙 제목 변경 제안 TODO-01, ERD 블록 강조 제외 DSN-04, 항목 단위 질문 DSN-08, 작성 규칙 NRM-10)은 PRD v0.9에 이미 확정 반영돼 있다. 화면 정의서 미결 #13도 같은 이유로 종결 상태다.
- 결정: PRD v0.9를 기준으로 삼고 위 항목을 **확정**으로 취급한다. 화면 정의서의 태그는 문서 동기화 지연으로 본다.
- 결과: 구현 시 PRD 수용 기준을 따른다. 사람이 화면 정의서 태그를 정리하기 전까지 docs/spec/screens.md 원문은 고치지 않는다.

## ADR-003 설계 화면의 FE 표시 범위

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: 기획서 8장 #6 현재 안은 "서버 · 클라이언트 모두", PRD 2.2 비목표는 "설계 화면은 BE 중심, FE 표시 범위는 화면 정의서 미결 #1", 화면 정의서 미결 #1은 "현재 L0에 웹 · 모바일 앱 노드만 표시 `미정`".
- 결정: 보수적인 쪽인 **BE 중심**을 택한다. L0(SCR-09)에는 웹 · 앱 노드를 계약 연결선의 끝점으로만 표시하고, FE 내부(컴포넌트 · 라우트)는 파싱 · 표시하지 않는다. L1 · 흐름도 · ERD는 서버 코드만 대상으로 한다.
- 결과: 파서의 입력 범위가 BE 코드로 한정된다. FE 확장은 로드맵 밖(M3 이후 후보).

## ADR-004 항목 참조 없는 자유 지시

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: 화면 정의서 1.4 · SCR-20은 "참조 없이는 전송 불가"로 적었고, PRD 2.2 비목표와 PRD 미결 #3은 채팅형 자유 지시 UI 제외 여부를 `미정`으로 둔다.
- 결정: 더 제한적인 해석인 **참조 없는 전송 불가**를 따른다 (PRD DSN-07 · DSN-08 수용 기준과도 일치).
- 결과: 채팅 입력은 참조 칩이 비어 있으면 현재 선택 항목을 자동 참조하고, 선택 항목도 없으면 전송 버튼을 비활성화한다.

## ADR-005 블록 선언 파일의 위치

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: 기획서 2.1은 블록 선언을 "프로젝트 폴더 밖 저장소 (확정)"에 두면서 위치를 `미정`이라 하고, 기획서 3.3 · PRD DSN-01은 "설정 파일 `blocks`"(프로젝트 폴더 안)에서 읽는다고 한다. 기획서 8장 #1 · PRD 미결 #5도 이 점을 남은 쟁점으로 적는다.
- 결정: 무결성(NFR-01) 쪽으로 보수적으로 해석한다. **블록 선언의 원본은 프로젝트 폴더 밖 저장소**에 두고 파서 · 판정기 · 화면은 거기서 읽는다. 프로젝트 폴더 안 설정 파일에는 프로젝트 식별자만 둔다. 역할 에이전트에게 블록 경계를 알려야 할 때는 오케스트레이터가 읽기 전용 사본을 세션 작업 디렉터리에 넣어 준다.
- 결과: 에이전트가 블록 선언을 직접 고쳐 구조 검사를 우회할 수 없다. 사람이 "프로젝트 안 설정 파일"로 결정하면 저장소 경로만 바뀌고 데이터 모델은 유지된다.

## ADR-007 서브 에이전트 허용 여부

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: 기획서 3.2는 허용 여부 `미정`, 8장 #5의 v5 안은 생성 금지(격리 누수). 그런데 기획서 4.5 비용 집계와 SCR-16 수치 줄은 서브 에이전트가 있는 것을 전제로 한다.
- 결정: 보수적으로 **역할 에이전트의 서브 에이전트 생성을 허용하지 않는다** (NFR-02 역할 접근 제한과 일관). SDK 옵션으로 차단한다.
- 결과: SCR-16의 "서브 에이전트별" 열은 비표시. 비용 집계는 세션 → 단계 → 역할 → 실행만. 허용으로 바뀌면 열만 추가한다.

## ADR-008 LLM 작성 텍스트의 생성 주체 표시 범위

- 상태: 제안 (에이전트) · 2026-10-15

## ADR-009 작성 규칙의 역할 명칭

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: SCR-21 작성 규칙은 rule-writer · planner · implementer · test-writer · 채팅을 역할 축으로 쓰는데, 기획서 3.2 · PRD RUN-04의 세션 역할은 테스트 작성 · 구현 · 변이 주입뿐이다. rule-writer · planner는 다른 문서에 정의가 없고 변이 주입은 작성 규칙 목록에 없다.
- 결정: 세션 역할(RUN-04)과 문장 작성 주체(NRM-10)를 분리한다. 매핑: test-writer = 테스트 작성, implementer = 구현, rule-writer = 요구사항 → 규칙 자동 생성(NRM-02)의 수행 주체, planner = 제안 · ADR 작성 주체(DSN-07), 채팅 = 질문 답변 주체(DSN-08). 변이 주입 역할은 사람이 읽는 문장을 만들지 않으므로 작성 규칙 대상에서 제외한다.
- 결과: NRM-10은 P2이므로 M1 · M2에 영향 없음. 화면 문구는 화면 정의서 명칭을 쓴다.

## ADR-010 M1 대상 화면에 설정(예산 · 모델) 포함

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: PRD 6장 M1 대상 화면은 S-01 · P-01 · P-02 · P-04 · P-05 · T-01이지만, COST-01(P0)과 NFR-07(역할별 모델 명시 필수, 예산 한도 없는 실행 금지)을 지키려면 예산 · 모델을 입력할 곳이 필요하다. 화면 우선순위 표도 X-02 예산 · 모델을 P0으로 둔다.
- 결정: **SCR-21의 예산 · 모델 섹션만 M1에 포함**한다. 나머지 섹션(잠정 승인 · 자동 모드 · 대기열 · 작성 규칙)은 원래 우선순위대로.
- 결과: M1 완료 기준 "사람 개입 없이 1회 완주"의 사전 조건으로 설정 저장이 필요하다.

## ADR-015 마일스톤 분할 (PRD 6장 → M0~M6)

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: PRD 6장은 M1 · M1 직후 측정 · M2 MVP(P1 전부) · M3 확장 4단계다. P1은 요구사항 30여 개 · 화면 15개로 마일스톤 하나로는 검수 · 회고 주기가 너무 길고, scaffold 단계가 없다.

- 결과: 로드맵 · GitHub 마일스톤 이름은 M0~M6. PRD 단계와의 대응은 docs/roadmap.md 0절.

## ADR-016 자동 테스트는 가짜 에이전트 어댑터로 수행

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: 이 VM과 CI에는 Claude 인증(API 키 · 구독)이 없다. 실제 Claude Agent SDK 호출은 비결정적이고 비용이 든다.
- 결정: `AgentAdapter` 인터페이스 뒤에 `ClaudeSdkAdapter`(실제)와 `ScriptedAdapter`(시나리오 재생)를 두고, 모든 자동 테스트 · e2e · QA는 ScriptedAdapter로 돈다. 환경 변수 `BIVE_AGENT`로 선택. 실제 SDK 완주는 사람이 1회 수행(needs-human).
- 결과: 판정 로직(JDG-01)은 어댑터와 무관하게 실행기 출력만 보므로 테스트 신뢰성에 영향 없음. 프롬프트 품질은 자동으로 검증되지 않는다.

## ADR-017 병합 시 기준 브랜치가 바뀐 경우

- 상태: 제안 (에이전트) · 2026-10-15

## ADR-030 대기열 유입 상한의 경계와 검토 대기열 건수 상한

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: TODO-04 "승인 대기 · 검토 대기열의 건수 · 체류 기간 상한 초과 시 신규 제안 중단 · 경고. 건수 상한: 승인 대기 40건(확정, 설정에서 변경 가능). 체류 기간 상한 `미정`". SCR-17 "대기 n / 상한 40 (초과 시 빨강)". 검토 대기열의 건수 상한 값은 없고, "초과"가 41번째까지 허용하고 42번째를 막는 것인지 41번째부터 막는 것인지 정해져 있지 않다(로드맵 v1 검토 지적 16 · 25).
- 결정: 대기 건수 n이 상한 N에 이르면(n ≥ N) 다음 제안부터 생성을 거부한다. 즉 승인 대기는 상한을 넘지 않는다(기본값에서 41번째 제안 거부). "초과"는 '상한을 넘게 될 신규 제안'으로 읽는다. 거부 오류는 `-32009` · 사유 `QUEUE_LIMIT_REACHED`이고, 제안 도구를 부른 세션은 도구 오류를 받고 끝나며 자동 재시도는 없다. 경고는 n ≥ N일 때 SCR-17 머리줄 "대기 n / 상한 N" 빨강, 사이드바 알림 배지 빨강, 배지 툴팁 "유입 상한 도달". 상한을 n보다 낮춰도 기존 제안은 지우지 않고 신규만 막는다. 검토 대기열의 건수 상한 기본값도 40(승인 대기와 별도 설정)이고 같은 규칙으로 신규 제안을 막으며 SCR-18 머리줄에 같은 형식으로 표시한다. 실행 생성은 막지 않는다(PRD에 없음). 체류 기간 상한은 `미정` 유지, 설정에 노출하지 않는다.
- 결과: M3-13. M3 완료 기준 흐름 8은 대기 40건 → 41번째 거부 → 상한 50 → 다시 허용.

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: JDG-06 수용 기준은 "요구사항 → 규칙 · 계약 → 코드 연결", SCR-07은 "요구사항 → 규칙 · 계약 → 실행 연결 전체"다. 문서 우선순위는 PRD > 화면 정의서(CLAUDE.md 1장). NFR-03은 근거를 물리적으로 찾을 수 없는 연결(추정 · 예시)을 표시하지 못하게 한다(로드맵 v1 검토 지적 16).

## ADR-037 TypeScript 7과 ESLint 파서용 TypeScript 6 병행

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: architecture.md 6장은 `typescript` 7을 정했다. TypeScript 7.0.2(네이티브 구현)는 설치 · `tsc` 동작이 확인됐지만 기존 컴파일러 JS API를 내보내지 않고(`exports`가 `version.cjs`와 `unstable/*`뿐), `typescript-eslint` 8.71.2의 peer 범위는 `typescript >=4.8.4 <6.1.0`이라 ESLint가 TypeScript 파일을 파싱할 수 없다(M0-01).
- 결정: 타입 검사 · 빌드(`tsc`)는 각 패키지 devDependency `typescript@7.0.2`로 한다. 루트 devDependency에는 ESLint 파서 전용으로 `typescript@6.0.3`(peer 범위 안의 최신)을 둔다. pnpm은 루트의 `typescript-eslint` peer를 루트 `typescript`로, 패키지 스크립트의 `tsc`는 패키지의 `node_modules/.bin`으로 해석한다. 타입 정보가 필요한 lint 규칙(type-aware)은 쓰지 않는다.
- 결과: M0-01. `typescript-eslint`가 TypeScript 7을 지원하면 루트 `typescript`를 7로 올리고 이 ADR을 닫는다. 그 전까지 TypeScript 7에만 있는 문법은 lint 파싱 오류가 날 수 있다. 루트 `node_modules/.bin/tsc` · tsserver는 6.0.3이라 편집기 진단이나 루트 `npx tsc`는 CI(7.0.2)와 다를 수 있다.

## ADR-038 픽스처 헬스 체크 응답 · 자체 테스트 위치

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: M0-08은 `fixtures/sample-next-app`의 `GET /api/health` HTTP 테스트 1개만 요구하고 응답 형태 · 테스트 위치는 정하지 않았다. M1 · M3 완료 기준 흐름이 헬스 응답에 필드를 추가하는 규칙(서버 시각 · 버전 · 호스트 이름 등)을 새로 실행하고 그 규칙은 Red 확인(구현 전 실패, RUN-03 · ADR-026)을 거친다. 픽스처가 처음부터 그런 필드를 돌려주면 해당 규칙의 인수 테스트가 구현 전에 통과해 Red 확인이 끝나지 않는다. ADR-026은 BIVE 인수 테스트를 `bive-acceptance/<RULE-ID>/*.acc.ts`에 두고 판정 러너가 그 아래 전부를 실행한다.
- 결정: 픽스처의 `/api/health`는 데이터베이스를 한 번 읽고(`Item` 개수) `{ ok: true }`만 돌려준다(시각 · 버전 없음). 픽스처 자체 HTTP 테스트는 프로젝트 테스트 경로 `tests/http/*.test.ts`에 두고 `bive-acceptance/`는 비워 둔다(규칙에 매핑되지 않는 인수 테스트를 판정 러너가 줍지 않도록). 프로젝트 vitest 설정은 `bive-acceptance/**`를 명시적으로 제외한다. 서버 기동은 ADR-026과 같은 순서(임시 SQLite `DATABASE_URL`에 `prisma migrate deploy` → `next build` → `next start` 127.0.0.1 빈 포트)를 `tests/support/server.ts`(vitest globalSetup)가 한다.
- 결과: M0-08. M1 · M3 흐름의 헬스 응답 필드 추가 규칙이 Red 확인을 정상으로 거친다. 사람이 응답에 시각을 처음부터 넣기로 하면 M1 흐름의 요구사항 문장을 함께 바꾼다.

## ADR-039 IPC 오류 코드 판단 순서 · 패키지 간 import 해석

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: architecture.md 5장은 "스키마 불일치 = `-32602`"라고만 하고, JSON-RPC 표준의 `-32700`(해석 실패) · `-32600`(형식 위반) · `-32601`(없는 메서드)과의 관계를 정하지 않았다. 또 워크스페이스 패키지의 `exports`가 `dist`만 가리켜 다른 패키지가 shared를 쓰려면 빌드가 먼저 필요했다(M0-03).
- 결정: 받는 쪽은 JSON 해석 `-32700` → 메시지 형식(JSON-RPC 2.0 봉투) `-32600` → 메서드 등록 여부 `-32601` → 메서드별 파라미터 스키마 `-32602` 순으로 판단한다. 요청한 쪽이 받은 응답의 형식 · 결과가 메서드 스키마와 다르면 `-32602`로 처리한다. 봉투는 모르는 필드를 거부하고(strict), 파라미터가 없는 메서드에 `params`를 넣으면 `-32602`다. import 해석은 사용자 정의 조건 `@bive/source`(→ `src`)를 typecheck · vitest에서만 켜고 빌드 · 런타임은 `dist`를 쓴다(architecture.md 2장 끝).
- 결과: M0-03 · M0-04(파이프 서버). 표준 코드를 그대로 따르므로 되돌리기 쉽다. store · parser가 import 대상이 되면 같은 조건을 `exports`에 추가한다.

## ADR-040 프로젝트 등록부와 저장소 마이그레이션 규칙

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: ADR-025는 프로젝트별 저장소 `$BIVE_HOME/projects/<projectId>/`만 정했고, 여러 프로젝트를 나열(`project.list`)할 등록부의 형식과 위치, 스키마 변경 방식은 문서에 없다(M0-04).
- 결정: 등록부는 프로젝트별 DB와 분리한 SQLite 파일 `$BIVE_HOME/registry.db`(`registered_projects`: 프로젝트 ID · 등록 시각)로 둔다. 프로젝트 내용(이름 · 경로 · 기준 브랜치)의 원본은 프로젝트별 `bive.db`의 `projects` 행 하나뿐이다. 등록은 프로젝트별 DB 생성 · 행 저장 뒤 마지막에 등록부 항목을 넣고, 등록 해제는 등록부 항목만 지운다(규범 · 기록 보존). 등록부에 있는데 프로젝트별 DB가 없으면 목록 조회가 오류를 낸다. 스키마는 `packages/store/src/migrations/<project|registry>/<NNNN>_<name>.ts`를 순서대로 적용하고 `schema_migrations`에 SQL 해시를 남긴다. 기록과 코드가 다르거나 DB가 코드보다 새 버전이면 그 DB를 열지 않는다.
- 결과: M0-04. JSON 파일 대신 SQLite를 써서 쓰기가 원자적이고 같은 마이그레이션 러너를 쓴다. 같은 값을 두 곳에 두지 않으므로 경로 변경은 프로젝트별 DB만 고친다. 폴더 경로로 프로젝트를 찾는 색인은 두지 않는다(`.bive.json`의 `projectId`로 찾는다, M1-01). 필요해지면 등록부에 마이그레이션을 추가한다.

## ADR-041 파이프 서버 인증 전 처리 · 프레임 상한 · 유휴 종료 · 단일 인스턴스 잠금

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: architecture.md 5장 · ADR-027은 `system.hello`의 토큰 확인과 "불일치 시 연결 종료"만 정하고, 인증 전 다른 메시지 · 프레임 크기 · 유휴 종료 기준 · 잠금 방식은 정하지 않았다. PRD 5.1은 "진행 중인 실행이 없고 앱이 닫혀 있으면 자동 종료", 사용자당 1개만 정한다. `system.hello`는 5장 표에서 M1이지만 M0-05 수용 기준이 토큰 인증을 요구한다(#8).
- 결정:
  - `system.hello { protocolVersion: 1, token }` → `{ orchestratorVersion }`을 M0-05에서 shared `METHODS`에 등록한다(`PROTOCOL_VERSION = 1`).
  - 인증 전에는 `system.hello` 요청만 받는다. 다른 메서드 · 알림 · 응답 모양 · JSON 아님 · UTF-8 아님은 `-32020`, hello 파라미터 위반(버전 불일치 포함)은 `-32602`, 토큰 불일치는 `-32020`이며 모두 응답 1건 뒤 연결을 닫는다. hello가 10초 안에 오지 않아도 `-32020` 후 닫는다(인증 안 된 연결이 유휴 종료를 막지 못하게). 인증된 연결의 두 번째 hello는 `-32009`. 토큰은 SHA-256 다이제스트를 상수 시간 비교한다.
  - 인증 뒤에는 ADR-039 순서를 따른다. JSON 해석 실패 · UTF-8 아님은 id `null`의 `-32700`이고 연결은 유지한다. 알림(id 없음)에는 어떤 경우에도 응답하지 않는다. 처리기 예외는 `-32603`(내부 메시지 미노출), 처리기 결과가 메서드 결과 스키마와 다르면 내보내지 않고 `-32603`.
  - 프레임 상한은 1 MiB(개행 제외). 넘으면 프레임 경계를 믿을 수 없으므로 id `null`의 `-32600` 후 연결을 닫는다. 줄 끝 `\r`은 떼고 빈 줄은 무시한다.
  - 수명: 연결 수는 인증 여부와 무관한 열린 파이프 연결 수, 실행 수는 `RunTracker.beginRun()` 핸들 수(실행 엔진은 M1). 둘 다 0인 상태가 `BIVE_IDLE_SHUTDOWN_MS`(기본 300000, 양의 정수만, 그 밖의 값은 종료 코드 2) 동안 이어지면 정상 종료한다. 기동 직후 아무도 접속하지 않아도 같은 기준으로 센다.
  - 단일 인스턴스: `$BIVE_HOME/run/orchestrator.pid`를 임시 파일의 hard link로 원자 생성한다. 기존 pid가 살아 있으면(`kill(pid, 0)` 성공 또는 `EPERM`) 아무 파일도 바꾸지 않고 "이미 실행 중"을 출력한 뒤 종료 코드 0. 죽은 pid · 형식이 틀린 파일이면 잠금을 인수하고 남은 소켓 파일을 지운 뒤 기동한다. 정상 종료(유휴 · SIGTERM · SIGINT) 때 소켓 · 토큰 · 잠금 파일을 지운다.
  - 권한: `run` 폴더 0700, 소켓 0600(listen 직후 chmod), 토큰 0600(임시 파일 → rename으로 교체, 기동마다 새 32바이트 난수). Unix 소켓 경로가 OS 제한(Linux 107 · macOS 103바이트)을 넘으면 기동하지 않는다(종료 코드 1).
  - 종료 · 기동 실패 정리는 자기 파일만 지운다: 토큰은 내용이 자기 토큰과 같을 때, 소켓은 자기가 bind한 파일(장치 · inode 일치)일 때, 잠금은 자기 pid일 때. 같은 경로에 다른 인스턴스의 소켓이 있으면 Node가 서버를 닫으며 경로를 지우지 않도록 닫는 동안 잠시 옆으로 옮겼다가 되돌린다.
  - 앱 클라이언트(#9)는 '이미 실행 중' 직후 또는 기동 직후 접속할 때 ENOENT · ECONNREFUSED를 짧게 재시도해야 한다(잠금을 잡은 뒤 소켓을 bind하기 전 틈이 있다).
  - 실행: `pnpm --filter @bive/orchestrator start`는 빌드 없이 tsx로 `src/cli.ts`를 `@bive/source` 조건과 함께 실행한다(ADR-039). 빌드 산출물은 `node packages/orchestrator/dist/cli.js`.
- 결과: M0-05. 앱(#9)은 같은 순서(접속 → hello → 요청)로 붙는다. 알려진 한계: 죽은 pid가 무관한 프로세스에 재사용되면 "이미 실행 중"으로 판단해 기동하지 않는다(보수적 방향, 잠금 파일을 지우면 풀림). 두 기동이 같은 죽은 잠금을 동시에 인수하는 좁은 경합은 인수 직전 재확인으로만 줄였다. Windows named pipe 실동작 · 권한은 실기기 확인이 필요하다(architecture.md 9장).
