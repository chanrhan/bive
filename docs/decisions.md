# BIVE 결정 기록 (ADR)

> 운영 프롬프트 1단계 규칙에 따라, 문서(docs/spec/plan.md · prd.md · screens.md) 사이에 충돌하거나 구현에 필요한데 빠진 내용에 대해 **가장 보수적인 해석**을 골라 기록한다.
> 모든 항목의 상태는 `제안 (에이전트)`이며, 사람이 확인하면 `채택` 또는 `기각`으로 바꾼다. 기각 시 영향받는 코드 · 로드맵을 함께 고친다.
> 형식: 맥락 → 결정 → 결과. 근거 문서 위치를 ID로 적는다.

## ADR-001 요구사항 · 화면 ID 체계

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: 운영 프롬프트는 FR-001 / NFR-001 / SCR-01 형식을 요구하지만 PRD에는 이미 PRJ · NRM · RUN · JDG · DSN · TODO · COST · MET · COL · NFR 체계가 있고, 기획서 · 화면 정의서가 그 ID를 교차 참조한다.
- 결정: 요구사항 ID는 PRD 원본 ID를 그대로 쓴다 (FR-xxx 재번호 없음). 화면은 SCR-01~21을 부여하고 원본 ID(S-01 · P-01 · D-01 · R-01 · T-01 · X-01)를 병기한다. 매핑은 docs/spec/screens.md 1.3.
- 결과: 로드맵 커버리지 표의 행 키는 PRD ID와 SCR ID. 코드 · 커밋 메시지에서 화면은 SCR ID로, 요구사항은 PRD ID로 부른다.

## ADR-002 화면 정의서의 `PRD 반영 필요` 태그 처리

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: 화면 정의서 v0.5가 `PRD 반영 필요`로 표시한 항목(거절 사유 필수 NRM-04, 회귀 상한 2회 RUN-02, 승인 대기 상한 40건 TODO-04, 검토 대기열 처리 액션 TODO-02, 유형 C 종료 조건 RUN-07, 규칙 제목 NRM-02, 규칙 제목 변경 제안 TODO-01, ERD 블록 강조 제외 DSN-04, 항목 단위 질문 DSN-08, 작성 규칙 NRM-10)은 PRD v0.9에 이미 확정 반영돼 있다. 화면 정의서 미결 #13도 같은 이유로 종결 상태다.
- 결정: PRD v0.9를 기준으로 삼고 위 항목을 **확정**으로 취급한다. 화면 정의서의 태그는 문서 동기화 지연으로 본다.
- 결과: 구현 시 PRD 수용 기준을 따른다. 사람이 화면 정의서 태그를 정리하기 전까지 docs/spec/screens.md 원문은 고치지 않는다.

## ADR-003 설계 화면의 FE 표시 범위

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: 기획서 8장 #6 현재 안은 "서버 · 클라이언트 모두", PRD 2.2 비목표는 "설계 화면은 BE 중심, FE 표시 범위는 화면 정의서 미결 #1", 화면 정의서 미결 #1은 "현재 L0에 웹 · 모바일 앱 노드만 표시 `미정`".
- 결정: 보수적인 쪽인 **BE 중심**을 택한다. L0(SCR-09)에는 웹 · 앱 노드를 계약 연결선의 끝점으로만 표시하고, FE 내부(컴포넌트 · 라우트)는 파싱 · 표시하지 않는다. L1 · 흐름도 · ERD는 서버 코드만 대상으로 한다.
- 결과: 파서의 입력 범위가 BE 코드로 한정된다. FE 확장은 로드맵 밖(M3 이후 후보).

## ADR-004 항목 참조 없는 자유 지시

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: 화면 정의서 1.4 · SCR-20은 "참조 없이는 전송 불가"로 적었고, PRD 2.2 비목표와 PRD 미결 #3은 채팅형 자유 지시 UI 제외 여부를 `미정`으로 둔다.
- 결정: 더 제한적인 해석인 **참조 없는 전송 불가**를 따른다 (PRD DSN-07 · DSN-08 수용 기준과도 일치).
- 결과: 채팅 입력은 참조 칩이 비어 있으면 현재 선택 항목을 자동 참조하고, 선택 항목도 없으면 전송 버튼을 비활성화한다.

## ADR-005 블록 선언 파일의 위치

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: 기획서 2.1은 블록 선언을 "프로젝트 폴더 밖 저장소 (확정)"에 두면서 위치를 `미정`이라 하고, 기획서 3.3 · PRD DSN-01은 "설정 파일 `blocks`"(프로젝트 폴더 안)에서 읽는다고 한다. 기획서 8장 #1 · PRD 미결 #5도 이 점을 남은 쟁점으로 적는다.
- 결정: 무결성(NFR-01) 쪽으로 보수적으로 해석한다. **블록 선언의 원본은 프로젝트 폴더 밖 저장소**에 두고 파서 · 판정기 · 화면은 거기서 읽는다. 프로젝트 폴더 안 설정 파일에는 프로젝트 식별자만 둔다. 역할 에이전트에게 블록 경계를 알려야 할 때는 오케스트레이터가 읽기 전용 사본을 세션 작업 디렉터리에 넣어 준다.
- 결과: 에이전트가 블록 선언을 직접 고쳐 구조 검사를 우회할 수 없다. 사람이 "프로젝트 안 설정 파일"로 결정하면 저장소 경로만 바뀌고 데이터 모델은 유지된다.

## ADR-007 서브 에이전트 허용 여부

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: 기획서 3.2는 허용 여부 `미정`, 8장 #5의 v5 안은 생성 금지(격리 누수). 그런데 기획서 4.5 비용 집계와 SCR-16 수치 줄은 서브 에이전트가 있는 것을 전제로 한다.
- 결정: 보수적으로 **역할 에이전트의 서브 에이전트 생성을 허용하지 않는다** (NFR-02 역할 접근 제한과 일관). SDK 옵션으로 차단한다.
- 결과: SCR-16의 "서브 에이전트별" 열은 비표시. 비용 집계는 세션 → 단계 → 역할 → 실행만. 허용으로 바뀌면 열만 추가한다.

## ADR-008 LLM 작성 텍스트의 생성 주체 표시 범위

## ADR-009 작성 규칙의 역할 명칭

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: SCR-21 작성 규칙은 rule-writer · planner · implementer · test-writer · 채팅을 역할 축으로 쓰는데, 기획서 3.2 · PRD RUN-04의 세션 역할은 테스트 작성 · 구현 · 변이 주입뿐이다. rule-writer · planner는 다른 문서에 정의가 없고 변이 주입은 작성 규칙 목록에 없다.
- 결정: 세션 역할(RUN-04)과 문장 작성 주체(NRM-10)를 분리한다. 매핑: test-writer = 테스트 작성, implementer = 구현, rule-writer = 요구사항 → 규칙 자동 생성(NRM-02)의 수행 주체, planner = 제안 · ADR 작성 주체(DSN-07), 채팅 = 질문 답변 주체(DSN-08). 변이 주입 역할은 사람이 읽는 문장을 만들지 않으므로 작성 규칙 대상에서 제외한다.
- 결과: NRM-10은 P2이므로 M1 · M2에 영향 없음. 화면 문구는 화면 정의서 명칭을 쓴다.

## ADR-010 M1 대상 화면에 설정(예산 · 모델) 포함

- 상태: 제안 (에이전트) · 2026-10-15

## ADR-015 마일스톤 분할 (PRD 6장 → M0~M6)

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: PRD 6장은 M1 · M1 직후 측정 · M2 MVP(P1 전부) · M3 확장 4단계다. P1은 요구사항 30여 개 · 화면 15개로 마일스톤 하나로는 검수 · 회고 주기가 너무 길고, scaffold 단계가 없다.

- 결과: 로드맵 · GitHub 마일스톤 이름은 M0~M6. PRD 단계와의 대응은 docs/roadmap.md 0절.

## ADR-016 자동 테스트는 가짜 에이전트 어댑터로 수행

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: 이 VM과 CI에는 Claude 인증(API 키 · 구독)이 없다. 실제 Claude Agent SDK 호출은 비결정적이고 비용이 든다.
- 결정: `AgentAdapter` 인터페이스 뒤에 `ClaudeSdkAdapter`(실제)와 `ScriptedAdapter`(시나리오 재생)를 두고, 모든 자동 테스트 · e2e · QA는 ScriptedAdapter로 돈다. 환경 변수 `BIVE_AGENT`로 선택. 실제 SDK 완주는 사람이 1회 수행(needs-human).
- 결과: 판정 로직(JDG-01)은 어댑터와 무관하게 실행기 출력만 보므로 테스트 신뢰성에 영향 없음. 프롬프트 품질은 자동으로 검증되지 않는다.

## ADR-017 병합 시 기준 브랜치가 바뀐 경우

- 상태: 제안 (에이전트) · 2026-10-15

## ADR-030 대기열 유입 상한의 경계와 검토 대기열 건수 상한

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: TODO-04 "승인 대기 · 검토 대기열의 건수 · 체류 기간 상한 초과 시 신규 제안 중단 · 경고. 건수 상한: 승인 대기 40건(확정, 설정에서 변경 가능). 체류 기간 상한 `미정`". SCR-17 "대기 n / 상한 40 (초과 시 빨강)". 검토 대기열의 건수 상한 값은 없고, "초과"가 41번째까지 허용하고 42번째를 막는 것인지 41번째부터 막는 것인지 정해져 있지 않다(로드맵 v1 검토 지적 16 · 25).
- 결정: 대기 건수 n이 상한 N에 이르면(n ≥ N) 다음 제안부터 생성을 거부한다. 즉 승인 대기는 상한을 넘지 않는다(기본값에서 41번째 제안 거부). "초과"는 '상한을 넘게 될 신규 제안'으로 읽는다. 거부 오류는 `-32009` · 사유 `QUEUE_LIMIT_REACHED`이고, 제안 도구를 부른 세션은 도구 오류를 받고 끝나며 자동 재시도는 없다. 경고는 n ≥ N일 때 SCR-17 머리줄 "대기 n / 상한 N" 빨강, 사이드바 알림 배지 빨강, 배지 툴팁 "유입 상한 도달". 상한을 n보다 낮춰도 기존 제안은 지우지 않고 신규만 막는다. 검토 대기열의 건수 상한 기본값도 40(승인 대기와 별도 설정)이고 같은 규칙으로 신규 제안을 막으며 SCR-18 머리줄에 같은 형식으로 표시한다. 실행 생성은 막지 않는다(PRD에 없음). 체류 기간 상한은 `미정` 유지, 설정에 노출하지 않는다.
- 결과: M3-13. M3 완료 기준 흐름 8은 대기 40건 → 41번째 거부 → 상한 50 → 다시 허용.

## ADR-034 목록의 '문제 항목'과 필터 상태 유지 범위

## ADR-037 TypeScript 7과 ESLint 파서용 TypeScript 6 병행

- 상태: 제안 (에이전트) · 2026-10-15
- 맥락: architecture.md 6장은 `typescript` 7을 정했다. TypeScript 7.0.2(네이티브 구현)는 설치 · `tsc` 동작이 확인됐지만 기존 컴파일러 JS API를 내보내지 않고(`exports`가 `version.cjs`와 `unstable/*`뿐), `typescript-eslint` 8.71.2의 peer 범위는 `typescript >=4.8.4 <6.1.0`이라 ESLint가 TypeScript 파일을 파싱할 수 없다(M0-01).
- 결정: 타입 검사 · 빌드(`tsc`)는 각 패키지 devDependency `typescript@7.0.2`로 한다. 루트 devDependency에는 ESLint 파서 전용으로 `typescript@6.0.3`(peer 범위 안의 최신)을 둔다. pnpm은 루트의 `typescript-eslint` peer를 루트 `typescript`로, 패키지 스크립트의 `tsc`는 패키지의 `node_modules/.bin`으로 해석한다. 타입 정보가 필요한 lint 규칙(type-aware)은 쓰지 않는다.
- 결과: M0-01. `typescript-eslint`가 TypeScript 7을 지원하면 루트 `typescript`를 7로 올리고 이 ADR을 닫는다. 그 전까지 TypeScript 7에만 있는 문법은 lint 파싱 오류가 날 수 있다. 루트 `node_modules/.bin/tsc` · tsserver는 6.0.3이라 편집기 진단이나 루트 `npx tsc`는 CI(7.0.2)와 다를 수 있다.

## ADR-038 픽스처 헬스 체크 응답 · 자체 테스트 위치

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: M0-08은 `fixtures/sample-next-app`의 `GET /api/health` HTTP 테스트 1개만 요구하고 응답 형태 · 테스트 위치는 정하지 않았다. M1 · M3 완료 기준 흐름이 헬스 응답에 필드를 추가하는 규칙(서버 시각 · 버전 · 호스트 이름 등)을 새로 실행하고 그 규칙은 Red 확인(구현 전 실패, RUN-03 · ADR-026)을 거친다. 픽스처가 처음부터 그런 필드를 돌려주면 해당 규칙의 인수 테스트가 구현 전에 통과해 Red 확인이 끝나지 않는다. ADR-026은 BIVE 인수 테스트를 `bive-acceptance/<RULE-ID>/*.acc.ts`에 두고 판정 러너가 그 아래 전부를 실행한다.
- 결정: 픽스처의 `/api/health`는 데이터베이스를 한 번 읽고(`Item` 개수) `{ ok: true }`만 돌려준다(시각 · 버전 없음). 픽스처 자체 HTTP 테스트는 프로젝트 테스트 경로 `tests/http/*.test.ts`에 두고 `bive-acceptance/`는 비워 둔다(규칙에 매핑되지 않는 인수 테스트를 판정 러너가 줍지 않도록). 프로젝트 vitest 설정은 `bive-acceptance/**`를 명시적으로 제외한다. 서버 기동은 ADR-026과 같은 순서(임시 SQLite `DATABASE_URL`에 `prisma migrate deploy` → `next build` → `next start` 127.0.0.1 빈 포트)를 `tests/support/server.ts`(vitest globalSetup)가 한다.
- 결과: M0-08. M1 · M3 흐름의 헬스 응답 필드 추가 규칙이 Red 확인을 정상으로 거친다. 사람이 응답에 시각을 처음부터 넣기로 하면 M1 흐름의 요구사항 문장을 함께 바꾼다.

## ADR-039 IPC 오류 코드 판단 순서 · 패키지 간 import 해석

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: architecture.md 5장은 "스키마 불일치 = `-32602`"라고만 하고, JSON-RPC 표준의 `-32700`(해석 실패) · `-32600`(형식 위반) · `-32601`(없는 메서드)과의 관계를 정하지 않았다. 또 워크스페이스 패키지의 `exports`가 `dist`만 가리켜 다른 패키지가 shared를 쓰려면 빌드가 먼저 필요했다(M0-03).
- 결정: 받는 쪽은 JSON 해석 `-32700` → 메시지 형식(JSON-RPC 2.0 봉투) `-32600` → 메서드 등록 여부 `-32601` → 메서드별 파라미터 스키마 `-32602` 순으로 판단한다. 요청한 쪽이 받은 응답의 형식 · 결과가 메서드 스키마와 다르면 `-32602`로 처리한다. 봉투는 모르는 필드를 거부하고(strict), 파라미터가 없는 메서드에 `params`를 넣으면 `-32602`다. import 해석은 사용자 정의 조건 `@bive/source`(→ `src`)를 typecheck · vitest에서만 켜고 빌드 · 런타임은 `dist`를 쓴다(architecture.md 2장 끝).
- 결과: M0-03 · M0-05(파이프 서버). 표준 코드를 그대로 따르므로 되돌리기 쉽다. store · parser가 import 대상이 되면 같은 조건을 `exports`에 추가한다.

## ADR-040 프로젝트 등록부와 저장소 마이그레이션 규칙

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: ADR-025는 프로젝트별 저장소 `$BIVE_HOME/projects/<projectId>/`만 정했고, 여러 프로젝트를 나열(`project.list`)할 등록부의 형식과 위치, 스키마 변경 방식은 문서에 없다(M0-04).
- 결정: 등록부는 프로젝트별 DB와 분리한 SQLite 파일 `$BIVE_HOME/registry.db`(`registered_projects`: 프로젝트 ID · 등록 시각)로 둔다. 프로젝트 내용(이름 · 경로 · 기준 브랜치)의 원본은 프로젝트별 `bive.db`의 `projects` 행 하나뿐이다. 등록은 프로젝트별 DB 생성 · 행 저장 뒤 마지막에 등록부 항목을 넣고, 등록 해제는 등록부 항목만 지운다(규범 · 기록 보존). 등록부에 있는데 프로젝트별 DB가 없으면 목록 조회가 오류를 낸다. 스키마는 `packages/store/src/migrations/<project|registry>/<NNNN>_<name>.ts`를 순서대로 적용하고 `schema_migrations`에 SQL 해시를 남긴다. 기록과 코드가 다르거나 DB가 코드보다 새 버전이면 그 DB를 열지 않는다.
- 결과: M0-04. JSON 파일 대신 SQLite를 써서 쓰기가 원자적이고 같은 마이그레이션 러너를 쓴다. 같은 값을 두 곳에 두지 않으므로 경로 변경은 프로젝트별 DB만 고친다. 폴더 경로로 프로젝트를 찾는 색인은 두지 않는다(`.bive.json`의 `projectId`로 찾는다, M1-01). 필요해지면 등록부에 마이그레이션을 추가한다. `ProjectRepository.delete`는 물리 삭제다(Project만의 예외: 등록 실패 정리용이고 규범 · 기록이 아님). 규범 · 기록 엔터티(요구사항 · 규칙 · 제안 등)는 `deletedAt` 소프트 삭제다(NRM-07, ADR-047). DB 파일은 만들거나 열 때 0600으로 맞춘다(`-wal` · `-shm`도 같은 권한, M1-02).

## ADR-041 파이프 서버 인증 전 처리 · 프레임 상한 · 유휴 종료 · 단일 인스턴스 잠금

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: architecture.md 5장 · ADR-027은 `system.hello`의 토큰 확인과 "불일치 시 연결 종료"만 정하고, 인증 전 다른 메시지 · 프레임 크기 · 유휴 종료 기준 · 잠금 방식은 정하지 않았다. PRD 5.1은 "진행 중인 실행이 없고 앱이 닫혀 있으면 자동 종료", 사용자당 1개만 정한다. `system.hello`는 5장 표에서 M1이지만 M0-05 수용 기준이 토큰 인증을 요구한다(#8).
- 결정:
  - `system.hello { protocolVersion: 1, token }` → `{ orchestratorVersion }`을 M0-05에서 shared `METHODS`에 등록한다(`PROTOCOL_VERSION = 1`).
  - 인증 전에는 `system.hello` 요청만 받는다. 다른 메서드 · 알림 · 응답 모양 · JSON 아님 · UTF-8 아님은 `-32020`, hello 파라미터 위반(버전 불일치 포함)은 `-32602`, 토큰 불일치는 `-32020`이며 모두 응답 1건 뒤 연결을 닫는다. hello가 10초 안에 오지 않아도 `-32020` 후 닫는다(인증 안 된 연결이 유휴 종료를 막지 못하게). 인증된 연결의 두 번째 hello는 `-32009`. 토큰은 SHA-256 다이제스트를 상수 시간 비교한다.
  - 인증 뒤에는 ADR-039 순서를 따른다. JSON 해석 실패 · UTF-8 아님은 id `null`의 `-32700`이고 연결은 유지한다. 알림(id 없음)에는 어떤 경우에도 응답하지 않는다. 처리기 예외는 `-32603`(내부 메시지 미노출), 처리기 결과가 메서드 결과 스키마와 다르면 내보내지 않고 `-32603`.
  - 프레임 상한은 1 MiB(개행 제외). 넘으면 프레임 경계를 믿을 수 없으므로 id `null`의 `-32600` 후 연결을 닫는다. 줄 끝 `\r`은 떼고 빈 줄은 무시한다.
  - 수명: 연결 수는 인증 여부와 무관한 열린 파이프 연결 수, 실행 수는 `RunTracker.beginRun()` 핸들 수(실행 엔진은 M1). 둘 다 0인 상태가 `BIVE_IDLE_SHUTDOWN_MS`(기본 300000, 양의 정수만, 그 밖의 값은 종료 코드 2) 동안 이어지면 정상 종료한다. 기동 직후 아무도 접속하지 않아도 같은 기준으로 센다.
  - 단일 인스턴스: `$BIVE_HOME/run/orchestrator.pid`를 임시 파일의 hard link로 원자 생성한다. 기존 pid가 살아 있으면(`kill(pid, 0)` 성공 또는 `EPERM`) 아무 파일도 바꾸지 않고 "이미 실행 중"을 출력한 뒤 종료 코드 0. 죽은 pid · 형식이 틀린 파일이면 잠금을 인수하고 남은 소켓 파일을 지운 뒤 기동한다. 정상 종료(유휴 · SIGTERM · SIGINT) 때 소켓 · 토큰 · 잠금 파일을 지운다.
  - 권한: `run` 폴더 0700, 소켓 0600(listen 직후 chmod), 토큰 0600(임시 파일 → rename으로 교체, 기동마다 새 32바이트 난수). Unix 소켓 경로가 OS 제한(Linux 107 · macOS 103바이트)을 넘으면 기동하지 않는다(종료 코드 1).
  - 종료 · 기동 실패 정리는 자기 파일만 지운다: 토큰은 내용이 자기 토큰과 같을 때, 소켓은 자기가 bind한 파일(장치 · inode 일치)일 때, 잠금은 자기 pid일 때. 같은 경로에 다른 인스턴스의 소켓이 있으면 Node가 서버를 닫으며 경로를 지우지 않도록 닫는 동안 잠시 옆으로 옮겼다가 되돌린다.
  - 앱 클라이언트(#9)는 '이미 실행 중' 직후 또는 기동 직후 접속할 때 ENOENT · ECONNREFUSED를 짧게 재시도해야 한다(잠금을 잡은 뒤 소켓을 bind하기 전 틈이 있다).
  - 실행: `pnpm --filter @bive/orchestrator start`는 빌드 없이 tsx로 `src/cli.ts`를 `@bive/source` 조건과 함께 실행한다(ADR-039). 빌드 산출물은 `node packages/orchestrator/dist/cli.js`.
- 결과: M0-05. 앱(#9)은 같은 순서(접속 → hello → 요청)로 붙는다. 알려진 한계: 죽은 pid가 무관한 프로세스에 재사용되면 "이미 실행 중"으로 판단해 기동하지 않는다(보수적 방향, 잠금 파일을 지우면 풀림). 두 기동이 같은 죽은 잠금을 동시에 인수하는 좁은 경합은 인수 직전 재확인으로만 줄였다. Windows named pipe 실동작 · 권한은 실기기 확인이 필요하다(architecture.md 9장).

## ADR-042 앱의 오케스트레이터 기동 · 브리지 계약 · 실행 방식

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: architecture.md 2장은 app이 orchestrator를 import하지 못하게 하고(실행 파일 경로로만 기동), 5장은 렌더러 경로를 `window.bive.invoke` → preload(허용 목록) → `ipcRenderer.invoke('bive:rpc')` → main(zod 검증) → 파이프로만 정했다. 오케스트레이터를 어떤 런타임 · 경로로 띄울지(C-17, ADR-028 "패키징은 M1 실측 후"), `window.bive` 오류의 형태, 알림 채널, `app.pid`의 쓰임은 정해져 있지 않다(M0-06, #9).
- 결정:
  - 경로: app은 `$BIVE_HOME/run`의 파이프 · 토큰 · 잠금 경로 규칙을 `packages/app/src/main/run-paths.ts`에 따로 두고, `test/run-paths.test.ts`가 orchestrator 원본(`run-paths.ts`)과 OS별로 대조한다. `app.pid`도 같은 폴더에 둔다.
  - 기동: `orchestrator.pid`의 pid가 살아 있으면 붙고, 없거나 죽었으면 분리 프로세스(detached · stdio ignore · unref · windowsHide)로 띄운다. 접속은 토큰 파일 읽기 → 연결 → `system.hello` 순서이고, ENOENT · ECONNREFUSED · `-32020`(죽은 인스턴스의 토큰을 읽은 경우)은 100ms 간격으로 5초까지 재시도한다(ADR-041). 기다리는 동안 붙으려던 인스턴스가 사라지면 그때 띄운다. 기동 실패(실행 파일 없음)는 바로 오류다. 앱 종료 때는 연결만 닫고 오케스트레이터는 유휴 종료에 맡긴다(NFR-06).
  - 실행 방식: `BIVE_ORCHESTRATOR_MODE`(source | dist)가 있으면 그 값, 없으면 Electron `app.isPackaged`로 고른다. 개발(`source`)은 시스템 Node(`BIVE_NODE_PATH`, 없으면 PATH의 `node`, CLI는 자기 Node)로 `--conditions=@bive/source --import tsx packages/orchestrator/src/cli.ts`를 orchestrator 폴더에서 실행한다(`pnpm --filter @bive/orchestrator start`와 같음). 패키징(`dist`)은 잠정으로 Electron 실행 파일 + `ELECTRON_RUN_AS_NODE=1` + `resources/orchestrator/dist/cli.js`이며, 패키징 빌드가 없어 실측 전이다(C-17).
  - 브리지: `window.bive`는 `invoke(method, params)` · `on(event, cb)` 두 키뿐이다. 채널은 `bive:rpc`(invoke, `{ method, params }` → `{ ok: true, result }` 또는 `{ ok: false, error }`)와 `bive:event`(main → renderer, `{ event, params }`). `invoke`는 결과로 풀리고 실패하면 JSON-RPC 오류 객체 `{ code, message, data? }`로 거부된다. `on`은 구독 해제 함수를 돌려준다. 샌드박스 preload는 electron 외 모듈을 불러올 수 없어 메서드 검증을 하지 않고, main이 오케스트레이터에 접속(필요하면 기동)하기 전에 형식 `-32600` → `system.hello` 거부 `-32020` → 등록 여부 `-32601` → 파라미터 스키마 `-32602` 순으로 검증한다(ADR-039). 오케스트레이터에 접속하지 못하면 `-32603` "오케스트레이터 연결 실패", 그 밖의 예외는 `-32603` "내부 오류"이며 둘 다 `data`를 싣지 않는다. 원본 오류(로컬 경로 · 시스템 메시지)는 main 로그에만 남긴다. 창은 `contextIsolation: true` · `sandbox: true` · `nodeIntegration: false`를 명시한다.
  - `app.pid`: 앱 main이 시작할 때 자기 pid를 원자적으로 쓰고(0600) 종료할 때 자기 pid일 때만 지운다. 오케스트레이터 수명 판단에는 쓰지 않는다(연결 수 기준, ADR-041).
  - 개발 CLI(`pnpm --filter @bive/app cli`): `ping`, `rpc <method> [json]`. `rpc`는 이름이 `.list` · `.get` · `.status` · `.summary`로 끝나는 조회 메서드만 접속 전에 허용한다. 종료 코드 0 성공, 1 접속 · 원격 오류, 2 사용법 위반 · 허용되지 않는 메서드.
  - 빌드: electron-vite 출력은 `packages/app/dist/{main,preload,renderer}`. main은 shared를 번들에 넣고(빌드 전 shared `dist` 필요, ADR-039 유지), preload는 CommonJS 한 파일(`index.cjs`)이다.
- 결과: M0-06. #10 · #13의 가짜 브리지는 위 `window.bive` 계약(거부값 = JSON-RPC 오류 객체)을 흉내 낸다. 패키징 구성 이슈에서 `dist` 실행 방식을 실측하고 이 ADR을 고친다. Windows 분리 기동은 실기기 확인이 필요하다(architecture.md 9장).

## ADR-043 화면 e2e 하네스: 셸 화면 ID · 상태 이름 · 문구 검사 범위 · 브라우저 처리

- 맥락: architecture.md 8장은 화면 e2e를 Vite 개발 서버 렌더러 + 가짜 브리지 + `checklists/scr-xx.ts` + `artifacts/screens/<SCR-ID>/<state>.png`로 정했지만, SCR-01~21이 아닌 앱 공통 틀(셸)의 ID, 상태 이름의 표기, "화면 문구"에 무엇이 들어가는지, CI 러너의 브라우저 마련 방법은 정하지 않았다. 기존 `ci.yml` 주석은 "`playwright install` 금지"(ADR-028)를 적었지만 ADR-028은 이 VM의 사실 기록이다(M0-07, #10).
- 결정:

  - 가짜 브리지: 응답 표에 없는 메서드는 `-32601`, `system.hello`는 `-32020`으로 거부해 실제 main 순서(ADR-042)를 따른다. 응답 값은 IPC처럼 복제해 넘긴다.

GitHub 러너는 미리 깔린 Google Chrome이 있으면 그 경로를 지정하고, 없을 때만 `playwright install chromium --with-deps`로 설치하며 `~/.cache/ms-playwright`를 Playwright 버전별로 캐시한다. 산출물 `artifacts/`는 실패 여부와 관계없이 CI 아티팩트로 올린다.
  - Vite 서버는 HMR을 끄고 띄워 React 플러그인의 인라인 프리앰블 없이 index.html의 CSP를 그대로 둔다. 다른 작업 트리의 서버를 재사용하지 않도록 매번 새로 띄운다(포트 `BIVE_E2E_PORT`, 기본 5179).

## ADR-044 앱 레이아웃 · 경로 상태 · 디자인 토큰 · 채팅 접힘

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: M0-10(#13)은 사이드바 · 중앙 영역 · 오른쪽 채팅 자리와 다크 테마 토큰을 요구하지만, 화면(SCR-01~21)은 아직 없다. 화면 정의서 1.2는 메뉴 구성만 정하고 경로(라우팅) 방식, 화면이 없는 메뉴를 눌렀을 때의 표시, 프로젝트가 없을 때의 사이드바 상단은 정하지 않았다. prototype-map.md 3장은 토큰 이름 · 값만 있고 미디어 쿼리 기준(`--bp-chat-collapse`)은 CSS 변수로 쓸 수 없다. ADR-035는 다음 마일스톤 기능을 미노출로 둔다.
- 결정:
  - 경로: 라우터 라이브러리 없이 React 상태 하나(`NavigationProvider` · `useNavigation()`, `src/renderer/src/navigation/`). 경로 ID는 영어(`requirements` · `rules` …, 메뉴 밖 `todo` · `settings`), 화면에는 이름만 보인다. 주소(URL) · 뒤로 가기 · 새로고침 복원은 없다. Electron 단일 창 · `file://` 로드에서 URL 경로가 필요 없고, 되돌리기 쉽다(필요해지면 경로 ID를 그대로 라우터 경로로 쓴다).
  - 화면 꽂기: `src/renderer/src/screens/registry.ts`의 `SCREENS`(경로 → 컴포넌트)에 화면 이슈가 한 줄을 더한다. 중앙 영역은 등록된 화면을 그리고, 없으면 "<화면 이름> 준비 중" 한 줄 빈 상태, 아무것도 고르지 않았으면 "선택 항목 없음"(ADR-029 형식)이다. 메뉴는 내비게이션 뼈대라서 ADR-035의 미노출 대상이 아니다. 할 일 아이콘 · 설정 아이콘도 지금은 같은 빈 상태로 가고, 할 일(M1)은 탭 화면, 설정(SCR-21)은 모달로 바꾼다.
  - 사이드바 상단: 열린 프로젝트가 없으면 "프로젝트 없음", 할 일 배지는 건수가 있을 때만 그린다(근거 값 없음 = 미표시, NFR-03). 하단 연결 상태는 정상(연결됨)은 흐리게, 끊김만 색으로 강조한다(1.1 예외만 강조).
  - 토큰: `src/renderer/styles/tokens.css`의 `:root`에 표의 이름을 하나도 빠짐없이 두고 표에 없는 변수는 두지 않는다(새 토큰 이름 추가는 표를 먼저 고친 뒤). 설명만 있는 토큰은 표시 방식 이름을 값으로 둔다(`--status-normal: dot` · `--status-exception: label` · `--icon-set: lucide`). `test/tokens.test.ts`가 표를 읽어 이름 · 코드로 적힌 값을 대조한다. 레이아웃 스타일 `styles/app.css`에서 색 · 반경 · 글꼴 크기는 토큰만 쓴다(그림자 색도 `color-mix`로 토큰에서 만든다). 표에 없는 요소 크기(아이콘 버튼 28px · 배지 16px · 채팅 머리 53px · 테두리 1px)는 직접 적는다.
  - 연결 상태 색: 정상(연결됨 · 확인 중)은 점 아이콘도 글자와 같은 흐린 색(`currentColor`), 끊김만 `--color-danger`로 강조한다(1.1).
  - 채팅 접힘: 기준 폭은 `--bp-chat-collapse`를 렌더러가 읽어 `matchMedia('(width < 1100px)')`로 쓴다(값의 원본 하나). 접히면 그리드 열이 44px 띠가 되고, 띠를 누르면 360px 패널이 본문 위에 겹쳐 열린다(중앙 폭 유지). Esc · 닫기로 닫고, 창이 기준 이상으로 넓어지면 고정 패널로 돌아간다. 패널 안은 제목만 두고 탭 · 참조 칩 · 입력은 #82(M5-02)가 채운다.

## ADR-045 오케스트레이터 연결 상태: `system.status` · `system.connection` · 재접속

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: M0-10(#13) 수용 기준은 사이드바 하단이 `system.status` 성공 시 "연결됨", 끊기면 "연결 끊김"이고 앱은 오케스트레이터를 다시 띄우지 않고 1초 간격으로 재접속하는 것이다. architecture.md 5장은 `system.status`를 M1 `{projects[], runningRuns}`로 적었고, ADR-042는 "요청 때 연결이 없거나 끊겼으면 다시 접속(필요하면 기동)"이라 끊긴 뒤 다시 띄울 수 있었다.
- 결정:
  - `system.status`: 파라미터 없음 → `{ version, uptimeMs, connections, runsInProgress }`(strict, 수는 0 이상 정수). `connections`는 열린 파이프 연결 수(인증 여부 무관, ADR-041 유휴 종료 기준과 같은 값), `runsInProgress`는 `RunTracker.activeRunCount`(실행 엔진 전에는 0), `uptimeMs`는 기동부터의 경과(음수 없음). 프로젝트 목록은 `project.list`가 맡으므로 넣지 않는다. M0에서 shared `METHODS`에 등록한다.
  - `system.connection`: main이 만드는 렌더러 알림(파이프 알림 아님, 계약 `src/common/bridge.ts` `CONNECTION_EVENT`). 값은 `{ state: 'connected', status }` 또는 `{ state: 'disconnected' }`. main의 `ConnectionMonitor`가 바로 한 번, 이후 확인이 끝날 때마다 1초 뒤 `system.status`를 부르고 매번 결과를 보낸다(늦게 구독한 창도 1초 안에 따라잡음). 연결됨 상태에서 소켓이 닫히면 주기를 기다리지 않고 바로 끊김을 보낸다. 한 번의 확인은 10초 안에 끝나지 않으면 끊김으로 보고 지금 연결을 버린다(`dropConnection`, 응답 없는 오케스트레이터에서 감시가 멈추거나 대기 요청이 쌓이지 않게).
  - 렌더러: 처음 한 번 `system.status`를 직접 부르고(응답 전 "연결 확인 중"), 이후는 알림을 따른다. 알림이 먼저 오면 늦게 온 첫 조회 결과로 덮지 않는다. 오류 응답은 종류와 관계없이 "연결 끊김"이다. 상태 값(연결됨 · 끊김)만 들고 있어 같은 상태의 알림은 다시 그리지 않는다.
  - 재접속(ADR-042 수정): `OrchestratorLink`는 앱 실행 동안 첫 접속 시도 한 번만 기동을 허용한다(그 시도가 성공했는지와 무관). 첫 기동이 실패한 뒤의 재시도와 끊긴 뒤의 재접속은 모두 `ensureOrchestrator({ launch: false })`로 실행 중인 인스턴스에만 붙는다(잠금 pid가 살아 있지 않으면 바로 실패, 살아 있으면 ADR-042의 100ms · 5초 짧은 재시도). 그래서 기동 직후 죽는 오케스트레이터를 감시 주기마다 다시 띄우지 않는다. 렌더러 요청 경로도 같은 링크를 쓰므로 끊긴 뒤에는 어떤 요청도 오케스트레이터를 띄우지 않는다. 1초 간격 재접속은 위 감시 주기이며 ADR-041 · ADR-042의 기동 직후 짧은 재시도와 구분한다. 같은 접속 실패 로그는 다시 붙을 때까지 한 번만 남긴다.
- 결과: M0-10. 오케스트레이터가 죽으면 앱을 다시 시작하거나 다른 쪽(CLI 등)이 띄울 때까지 "연결 끊김"이다(중복 기동 방지 쪽의 보수적 선택). 다시 띄우는 버튼 같은 복구 동작이 필요하면 사람이 정하고 별도 이슈로 연다. 이전 버전 오케스트레이터(`system.status` 없음)가 떠 있으면 `-32601`로 "연결 끊김"이 보인다. M1 실행 시작 요청(`run.create`)이 들어올 때의 기동 허용 여부는 PRD 5.1 '실행 시작 시 기동'에 따라 M1-12에서 다시 정한다.

## ADR-046 화면 e2e 하네스 보완: 기본 포트 · 구독 독립 · 중복 주입 · 미노출 의미

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: #10(ADR-043) 리뷰의 비차단 지적. 기본 포트 5179가 고정이라 같은 VM의 여러 작업 트리가 동시에 e2e를 돌리면 충돌했고, 가짜 브리지의 `on`은 같은 함수를 두 번 구독하면 한 번으로 합쳐져 실제 preload(구독마다 독립)와 달랐다. 같은 페이지에 `mockBive`를 두 번 부르면 브라우저 안 재정의 오류로 조용히 깨졌고, 체크리스트 `absent`의 뜻(보이지 않음 / DOM에 없음)이 주석과 구현에서 달랐다.

- 결과: M0-10에서 함께 처리. ADR-043의 "기본 5179"는 이 ADR로 바뀐다.

## ADR-047 요구사항 수정 주체 · CRUD RPC 계약 · 표시 ID 순번

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: M1-02(#15) 수용 기준은 사람의 `requirement.update`가 제안 없이 바로 반영되고 "수정 시각과 주체가 바뀜"을 단언하는 것이다. 그런데 `Requirement` 스키마(architecture.md 3장)에는 생성 주체 `author`만 있고 수정 주체가 없다. architecture.md 5장 초안은 `requirement.get · update · delete`를 `{id}`만으로 적었지만 저장소는 프로젝트별 DB라 프로젝트 ID 없이는 찾을 수 없고, 누가 바꾸는지(사람 · 에이전트)를 RPC가 어떻게 아는지도 정하지 않았다. 표시 ID 순번을 어디에 두는지, 삭제된 번호를 다시 쓰는지, 삭제된 요구사항을 조회 · 수정할 수 있는지도 문서에 없다.
- 결정:
  - `Requirement`에 `updatedBy: Author`(마지막 수정 · 소프트 삭제 주체)를 더한다. 생성 직후 `updatedAt = createdAt`, `updatedBy = author`. 생성 주체 `author` · `createdAt`은 바뀌지 않는다. 변경 내용 이력은 NormChange(M3-12)가 맡는다.
  - RPC: 모든 `requirement.*` 파라미터에 `projectId`(ULID)가 필수다. 바꾸는 요청(`create` `{projectId, text, author}` · `update` `{projectId, id, text, author}` · `delete` `{projectId, id, author}`)은 주체를 싣고, 오케스트레이터는 `author.kind === 'human'`만 받아 승인 없이 바로 반영한다(NRM-01). 에이전트 주체는 `-32020`이다(에이전트 경로는 제안 승인뿐, NRM-04 · M1-09). 결과는 `{requirement}`(`get` 포함), 목록은 `{requirements}`로 감싸 이후 이슈가 필드를 더할 수 있게 한다. 사람이 만든 요구사항의 `normState`는 `approved`.
  - 본문은 공백만 있으면 `-32602`(받은 문자열은 그대로 저장). 등록부에 없는 프로젝트 · 프로젝트별 DB나 행이 없는 프로젝트 · 없는 요구사항은 `-32004`이고, 이때 저장소를 새로 만들지 않는다.
  - 삭제는 `deletedAt` · `updatedAt` · `updatedBy`를 채우는 소프트 삭제다. `list`는 삭제되지 않은 것만 표시 ID 순으로, `get`은 삭제된 것도 돌려준다(`deletedAt`으로 구분). 삭제된 것의 재삭제 · 수정은 `-32009`. 되살리기는 없다.
  - 표시 ID 순번은 프로젝트별 DB의 `display_id_sequences`(접두 → 마지막 순번)에 두고 생성 트랜잭션 안에서 올린다. 삭제돼도 번호를 다시 쓰지 않는다. 규칙 · 제안 등 다른 접두도 같은 테이블을 쓴다.
- 결과: M1-02. 마이그레이션 `project/0002_requirements`. #17(SCR-02 화면) · #38(SCR-06 편집)은 `author: {kind: 'human'}`을 실어 부르고, #22(M1-09)는 제안 승인 때 저장소 `ProjectStore.requirements`를 직접 써 에이전트 주체 요구사항을 넣으며, #21(M1-08)은 `requirement.create` 뒤 rule-writer 세션 시작을 붙인다. 주체를 요청에 싣는 방식은 파이프 접속 자체가 사람(앱)이라는 전제 위의 이중 확인이며, 에이전트는 파이프에 접근하지 않는다(NFR-01). 필드를 더한 것이므로 기각하면 `updatedBy`만 빼면 된다.

## ADR-048 공통 목록 · 카드 · 상태 배지 컴포넌트의 세부 규칙

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: 화면 정의서 1.4는 목록(검색 `/` · 필터 칩 · [문제만] · 결과 줄 · 목록별 유지 · 문제 우선 정렬), 카드(2줄 · 말줄임 + 툴팁), 상태 배지(정상은 흐린 점, 예외만 글자 · 색), 상세 접힘(판정 실패면 테스트 출력 자동 펼침)을 정하지만, 칩 개수를 무엇 기준으로 세는지, 예외 상태별 색, 카드 시각 표기, 정상 상태 점의 자리, 검색 일치 방식은 정하지 않았다. renderer는 shared를 `import type`으로만 가져와(architecture.md 2장) 상태 표시명 상수를 쓸 수 없다. 컴포넌트를 올릴 화면은 아직 없다(M1-03, #16).
- 결정:
  - 컴포넌트 이름 · 위치: prototype-map.md 표 2 이름 그대로 `packages/app/src/renderer/src/components/<Name>/`에 둔다(`ListView` · `FilterChips` · `Card2Line` · `StatusBadge` · `AuthorMark` · `CollapsibleDetail`). 스타일은 컴포넌트 폴더의 CSS 파일이며 색 · 반경 · 글꼴 크기는 토큰만 쓴다(ADR-044).
  - 검색: 공백으로 나눈 단어가 전부 들어 있으면 일치(대소문자 무시). 대상은 화면이 정하고 기본은 제목 + ID. `/` 키는 입력 중(입력 · 글상자 · 편집 가능 요소)이 아니고 조합 키가 없을 때만 검색 입력으로 초점을 옮긴다.
  - 칩: 기준 하나 = 칩 하나, 누르면 값 목록(여러 개 선택)이 열린다. 값별 개수는 그 기준을 뺀 나머지 조건(검색 · 다른 기준 · [문제만])을 지키는 항목 중 그 값을 가진 수다(고르면 결과가 몇 건 늘어나는지 보이도록). 0건 값은 비활성이고(이미 고른 값은 해제할 수 있게 활성), 값이 전부 0건이면 칩 자체가 비활성이다(ADR-035). 고른 값은 칩에 "기준: 값, 값"으로 보이고 ×는 그 기준의 값을 모두 해제한다. 메뉴는 Esc · 바깥 누르기 · 초점이 칩 밖으로 나가면 닫힌다.
  - 결과 줄: 검색어 · 고른 칩 값 · [문제만] 중 하나라도 있으면 "전체 n개 중 보이는 m개 · 초기화". 초기화는 그 목록의 필터 상태 전부를 비운다. 항목 0건은 "<대상> 없음" 한 줄(ADR-029), 필터 결과 0건은 결과 줄만 보인다.
  - 문제 항목 · 정렬: 문제 항목 = 카드 2줄째 예외(예외 상태 + 화면별 예외)가 1개 이상(ADR-034). 정렬은 문제 먼저, 같은 묶음 안에서는 카드 시각 최신순, 시각 없음은 뒤, 같으면 받은 순서.
  - 카드: 1줄 = 정상 상태의 흐린 점 · 제목 · 생성 주체 아이콘, 2줄 = 표시 ID · 예외 · 시각. 상태는 카드에 넘기면 정상은 1줄 점, 예외는 2줄 예외로 자동으로 나뉜다. 시각은 로컬 `YYYY-MM-DD HH:mm`, 해석할 수 없으면 미표시(NFR-03). 제목 · 2줄은 한 줄 말줄임이고 `title`에 전체 문구(2줄은 " · "로 이은 문구)를 둔다.
  - 상태 배지 색: 실패 · 변이 생존 `--color-danger`, 격리 · 재검증 필요 `--color-warning`, 미판정 `--color-accent`. 정상(통과 · 변이 검증됨 · 변이 미검증)은 글자 없이 `--status-normal-dot-color` 점이고 접근 가능한 이름 · 툴팁이 상태 이름이다. '승인' · '처리됨' 점은 그 상태를 쓰는 화면 이슈가 같은 정상 모양으로 더한다.
  - 표시명: renderer 컴포넌트에 판정 · 변이 · 생성 주체 표시명을 다시 적고 `test/status-badge.test.ts`가 shared `*_LABELS`와 같은지 대조한다.
  - 필터 상태 저장소: 렌더러 모듈 메모리의 목록 ID → 상태 맵(`useListFilter` · `setListFilter` · `resetListFilter` · `resetAllListFilters`). 컴포넌트가 사라져도 남고 렌더러를 다시 띄우면 사라진다. 브라우저 저장소 · 디스크에 쓰지 않는다(ADR-034).
  - 상세 접힘: 기본 접힘, `forceOpen`이 참이 되면 펼치고 그 뒤에는 사람이 다시 접을 수 있다.
  - 검사: 화면이 없으므로 e2e 전용 플레이그라운드 `packages/app/e2e/playground/list.html`(데이터는 이 폴더 안에만)을 e2e Vite 설정이 `/playground/<파일>`로 서빙하고 `e2e/list.spec.ts`가 검사한다. 제품 빌드에는 들어가지 않는다.
- 결과: M1-03. #17(요구사항) · #24(규칙) · #23(승인 대기) 화면이 같은 컴포넌트를 쓰고 목록 ID는 경로 ID(`requirements` 등)로 한다. 칩 개수 기준 · 예외 색 · 시각 표기를 사람이 바꾸면 `filter.ts` · `status.ts` · `time.ts`와 해당 테스트만 고친다.

## ADR-049 에이전트 어댑터 이벤트 모양 · 시나리오 형식 · 세션 순번 · 어댑터 선택

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: M1-06(#19)은 `AgentAdapter` · ScriptedAdapter · 시나리오 형식을 정한다. ADR-016은 어댑터 두 개와 `BIVE_AGENT`만 정했고, 결과 메시지의 필드 이름, 시나리오 파일 구조, 같은 역할 세션이 여러 번 열릴 때의 순서, 재기동 뒤 순서, `pause-implement`의 대기 방식, 잘못된 설정의 처리는 문서에 없다. 이후 #20 · #27 · #28 · #29 · #39가 이 모양을 그대로 쓴다.
- 결정:
  - 이벤트: `init`(세션 ID · 모델 · 도구 · MCP 서버) → 턴마다 `turn_start` → `tool_call` · `tool_result` 또는 `message` → 마지막 `result`. 결과는 SDK 결과 메시지와 같은 필드 이름(`subtype` · `total_cost_usd` · `num_turns` · `modelUsage`)과 SDK `ModelUsage`의 이름(`inputTokens` · `outputTokens` · `cacheReadInputTokens` · `cacheCreationInputTokens` · `costUSD`)을 쓴다. subtype은 SDK 값 중 `success` · `error_max_turns` · `error_max_budget_usd` · `error_during_execution`(SessionEndReason과 같은 값)만 두고, 그 밖의 SDK 오류 subtype은 #39에서 `error_during_execution`으로 옮긴다. 비용을 모르면 `total_cost_usd`는 0이 아닌 `null`(COST-02).
  - 도구: 어댑터는 세션에 주입된 `ToolExecutor.execute(name, args)`로만 도구를 부르고 결과(`ok` · `denied` · `error` + 본문)를 다음 턴 입력으로 쓴다. 실행기 예외는 `error` 결과로 바꿔 세션을 잇는다(SDK의 MCP 도구 오류와 같음). 중단 신호는 순회를 `signal.reason`(기본 `AbortError`)으로 끝낸다.
  - 시나리오: `packages/orchestrator/scenarios/<이름>.yaml`, zod strict 스키마. 역할별 `sessions[]`, 세션은 `turns[]`(도구 `{ tool, args }` · 메시지 `{ message }` · 대기 `{ pause: { file, until } }`)와 `result`. 대기는 턴으로 세지 않는다. `until: removed`(기본)는 파일이 없으면 만들고 지워질 때까지, `created`는 생길 때까지 기다린다. `modelUsage`의 `costUSD` 합은 `total_cost_usd`와 같아야 한다. 문자열 안 `{{이름}}`은 `biveHome` · `workDir` · 세션 `vars`(`requirementId` · `ruleId` 등, 실행 엔진이 넘김)로 채우고 값이 없으면 첫 이벤트 전에 실패한다. 모델 이름은 중립 이름(`model-a`)을 쓴다.
  - 세션 순번: 같은 (실행, 역할) 세션은 시나리오 순서대로 쓰고, 다 쓰면 마지막 세션을 반복한다. 실행 밖 세션(규칙 작성 · 채팅)은 실행 ID 없이 하나의 순번을 쓴다. 재기동 뒤에도 순서가 이어지도록 실행 엔진(#27)은 저장된 세션 수로 `roleSessionIndex`를 넘긴다. 그래서 `pause-implement`는 "실행마다 첫 구현 세션"만 대기하고 재개 뒤 새 구현 세션은 대기하지 않는다(roadmap M1 흐름 10).
  - 한도: ScriptedAdapter는 성공 결과의 `total_cost_usd`가 `maxBudgetUsd`를 넘으면 `error_max_budget_usd`, `num_turns`가 `maxTurns`를 넘으면 `error_max_turns`로 subtype만 바꾸고 값은 파일 그대로 둔다(실제 SDK가 한도에서 멈추는 것과 같은 판정 입력). 턴 중간에 멈추지는 않는다.
  - 선택: `BIVE_AGENT`(`scripted` | `claude`, 빈 값은 미설정 = `claude`), `BIVE_SCENARIO`(scripted일 때만, 기본 `happy-path`). 잘못된 값 · 없는 시나리오 · 형식이 틀린 시나리오는 잠금 · 토큰을 만들기 전에 실패하고 CLI 종료 코드 2(환경 변수 오류와 같음). `claude`는 M1-26 전까지 같은 인터페이스의 자리로, 세션을 순회하면 "ClaudeSdkAdapter 미구현(M1-26)" 오류로 끝난다. 선택 결과는 `Orchestrator.agent`에 보관한다.
- 결과: M1-06. #20은 `ToolExecutor`를, #27은 `roleSessionIndex` · `vars` · 결과 이벤트를, #39는 SDK 메시지를 이 이벤트로 옮기는 일을 맡는다. 시나리오는 정적이라 같은 픽스처에 같은 시나리오를 거듭 재생하면(예: happy-path 병합 뒤 다시 서버 시각 테스트) 새 테스트가 구현 전에 통과해 Red 확인을 넘지 못한다. 파이프라인 e2e는 시나리오마다 새 픽스처 복사본을 쓰고, roadmap M1 흐름 10 · 11처럼 같은 픽스처에서 이어 재생하는 경우의 처리는 해당 이슈(#33 · #42)에서 정한다.

## ADR-050 제안 · 승인 RPC 계약 · 부모 해제 규칙 · 승인 기록 해시 형식

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: M1-09(#22)는 제안 승인 · 수정 후 승인 · 거절 RPC와 승인 기록(행동 · 주체 · 시각 · 수정 diff · 이전 해시)을 요구한다. architecture.md 5장 초안은 `proposal.approve {id, editedPayload?}` · `proposal.reject {id, reason}`만 적었고 프로젝트 ID · 처리 주체를 어떻게 싣는지, 처리 결과가 무엇인지, 어떤 종류의 제안을 지금 반영할 수 있는지, 제안 등록 경로가 무엇인지 정하지 않았다. NRM-04는 "수정 내용과 주체 기록"을 확정했지만 `ProposalDecision`에는 주체가 없다. 수용 기준은 요구사항 삭제 뒤 자식 규칙이 남고 `parentRequirementId`가 비기를 요구하는데, `Rule` 스키마는 내장 규칙이 아니면 부모가 필수라 이 상태를 표현할 수 없다. ADR-027은 승인 기록이 이전 항목의 해시를 포함한다고만 정하고 해시 형식은 정하지 않았다.
- 결정:
  - RPC: 모든 `proposal.*` · `approvalLog.list`에 `projectId`가 필수다. 처리 요청 `proposal.approve {projectId, id, author, edited?}` · `proposal.amend {projectId, id, author, edited}`(수정 후 승인, approve에 `edited`를 실은 것과 같다) · `proposal.reject {projectId, id, author, reason}`은 사람 주체만 받고 에이전트 주체는 `-32020`(ADR-047과 같은 이중 확인). 없는 제안 `-32004`, 대기 아님 `-32009`, 빈(공백만 포함) 사유 `-32001` + `data.reason = 'REJECT_REASON_REQUIRED'`, 수정 본문이 종류와 맞지 않으면 `-32001` + `EDITED_PAYLOAD_INVALID`. 사유 키 자체가 없으면 `-32602`. 승인 결과는 `{proposal, applied: {entity: 'Requirement', requirement} | {entity: 'Rule', rule}, approvalLog}`, 거절 결과는 `{proposal, approvalLog}`. 조회는 `proposal.list {projectId, state?, kind?}` · `proposal.get` · `proposal.count {projectId}` → `{pending, pendingByKind}`(모든 종류 키, 할 일 배지용) · `proposal.markRead`(처음 읽은 시각만) · `approvalLog.list {projectId, targetRef?}` → `{entries, chain: {valid, brokenAtSeq}}`.
  - 제안 등록은 파이프 RPC가 없고 오케스트레이터 내부 API `ProposalService.submit(projectId, {kind, payload, rationale, author(agent), source, risk?, runId?, adrId?})`뿐이다. 항상 `pending`으로 들어가고 규범 테이블은 건드리지 않는다. 승인된 규칙 · 계약을 직접 고치는 RPC(`rule.update` · `contract.update` 등)도 두지 않는다(`-32601`).
  - M1에서 등록 · 승인할 수 있는 종류는 본문 스키마가 있는 `requirement_new {text}` · `rule_new {title, statement, kind, checkKinds, parentRequirementId}` 둘뿐이다. 나머지 종류는 enum만 두고 해당 이슈(설계 변경 DSN-07, 계약 M3-04, 규칙 제목 변경 NRM-10 등)가 본문 스키마와 반영 로직을 더한다. 수정 후 승인의 `edited`는 본문 전체이며 원래 본문과 같으면 그대로 승인(`approve`)으로 기록한다. 원래 본문은 바뀌지 않고 수정 본문은 `decision.editedPayload`와 승인 기록 `detail.diff {before, after}`에 남는다.
  - 승인은 규범 생성 · 제안 처리 · 승인 기록 추가를 트랜잭션 1개로 한다. 반영된 규범의 생성 주체는 제안한 에이전트(ADR-008), 규범 상태 `approved`, 생성 시각은 승인 시각이다. 승인 전에 부모 요구사항이 삭제된 규칙 제안의 승인은 `-32009`.
  - `ProposalDecision`에 `by: HumanAuthor`(처리 주체)와 `appliedRef`(승인 시 반영된 규범, 필수)를 더한다. 잠정 승인(`provisional`)은 상태 값만 두고 쓰지 않는다(ADR-012).
  - `Rule`에 `parentDetachedAt`을 더한다. `requirement.delete`는 같은 트랜잭션에서 살아 있는 자식 규칙의 `parentRequirementId`를 `null`로, `parentDetachedAt` · `updatedAt`을 삭제 시각으로 바꾼다. 규칙은 지우지 않는다. 내장 규칙이 아니면 부모 또는 해제 시각 중 하나가 있어야 한다. 부모 없는 규칙의 추적성 결함 표시는 M3-11.
  - 승인 기록 `ApprovalLogEntry {seq, at, action, actor(사람), targetRef, clientId, detail {diff?, reason?, appliedRef?}, prevHash, hash}`. `clientId`는 요청이 들어온 파이프 연결 번호(`pipe-N`, 증거용). `hash = SHA-256("bive-approval-log-v1\n" + 정규 JSON(hash를 뺀 필드))`, 정규 JSON은 객체 키 사전순 · 공백 없음 · `undefined` 키 제외. 첫 `prevHash`는 0 64자. `approval_log` · `proposals`의 수정 · 삭제(제안은 본문 수정 · 처리된 제안의 재처리 · 삭제)는 DB 트리거로 막는다. `INSERT OR REPLACE`는 `recursive_triggers`가 꺼진 연결에서 DELETE · UPDATE 트리거를 건너뛰므로, 두 테이블에 같은 키(`seq` · `hash`, `id` · `display_id`)가 이미 있으면 거부하는 BEFORE INSERT 트리거를 두고 연결도 `recursive_triggers = ON`으로 연다(이중 방어). `requirements` · `rules`에는 불변 트리거가 없어 `REPLACE`가 `UPDATE` 이상의 우회가 되지 않으므로 따로 막지 않는다. 트리거를 지운 변조는 검증이 드러낸다: 체인(`seq_gap` · `prev_hash_mismatch` · `hash_mismatch` · `malformed`, 처음 어긋난 순번)과 대조(처리된 제안마다 상태에 맞는 승인 기록이 있어야 함, 없으면 `decision_without_log`). `approvalLog.list`는 형식이 깨진 기록을 `entries`에서 빼고 `chain`으로 알린다(오류로 응답하지 않는다). 한계: 기준점(외부에 둔 마지막 해시)이 없는 체인이라 끝 기록을 잘라 낸 것은 체인만으로 검출할 수 없고, 처리된 제안과의 대조로 그 제안의 기록이 사라진 경우만 잡는다(`run_start` 등 제안이 아닌 기록의 잘라내기는 못 잡는다).
- 결과: M1-09. 마이그레이션 `project/0003_rules_proposals_approval_log`. #21(M1-08)은 `ProposalService.submit`(또는 열린 저장소용 `submitProposal`)으로 `rule_new`를 등록하고, #23(M1-10)은 `proposal.count` · `proposal.markRead`, #40(M1-27)은 `proposal.list` · `proposal.approve` · `proposal.amend` · `proposal.reject` · `approvalLog.list`, #24(M1-11)는 `ProjectStore.rules`, #25(M1-12)는 `ProjectStore.approvalLog.append`(`run_start`)를 쓴다. `provisional_grant` 기록의 주체 형태(정책은 사람이 아님)는 M3-17에서 정한다(지금 `actor`는 사람만). 기각하면 `amend`를 빼고(approve의 `edited`로 충분) `parentDetachedAt` 대신 규칙 삭제나 부모 유지로 바꾼다.

## ADR-057 설정 예산 · 모델의 모델 · 검사 범위 · RPC 계약 · 모달 배치

- 상태: 제안 (에이전트) · 2026-10-16
- 맥락: M1-05(#18)는 설정(SCR-21)의 예산 · 모델 섹션과 `settings.validateForRun()`의 `SETTINGS_INCOMPLETE`(`-32010`)를 요구한다. 화면 정의서는 "실행 전체 · 역할별 예산 한도, 역할별 모델"만 정하고, 기획서 4.5는 한도를 `maxBudgetUsd` · `maxTurns`로 부른다. M0의 `Settings` 스키마는 역할별 USD 한도가 test-writer · implementer 둘뿐이고 실행 전체 턴 한도가 없어 수용 기준(rule-writer 포함 역할별 모델 · USD · 턴, 실행 전체 한도)을 담지 못했다. ADR-024는 rule-writer · planner · 변이 주입 · 채팅 세션도 모델 · 예산 필수라고 하지만, 로드맵은 planner · 변이 주입 · 채팅의 설정 칸을 M4-01 · M3-07 · M5-01이 더하게 했다. `validateForRun`이 값을 돌려주는지 오류를 던지는지, 변경 주체, 저장 방식, 역할 행 이름, 모달 열림 상태의 위치(ADR-044는 톱니가 경로 `settings`로 간다고 적음), 프로젝트 열기(#14) 전 화면의 프로젝트 ID 출처도 문서에 없다.
- 결정:
  - 모델: `Settings = { projectId, run {maxBudgetUsd, maxTurns}, roles {<AgentRole>: {model, maxBudgetUsd, maxTurns}}, approvalQueueLimit(기본 40), provisionalPolicy, autoMode, installAllowlist, updatedAt, updatedBy }`. `roles`는 모든 역할 키를 갖고 값 `null`이 미설정이다. USD 한도는 0보다 큰 수, 턴은 1 이상 정수, 모델 ID는 사용자가 입력한 문자열(공백만 금지, 200자 이하, 목록 없음)이다. 저장은 미설정을 허용한다(로드맵 M1 흐름 2가 rule-writer만 먼저 저장). 한 번도 저장하지 않으면 기본값이고 `updatedAt` · `updatedBy`가 `null`이다.
  - 저장: 프로젝트별 DB 마이그레이션 `project/0004_settings`의 1행 테이블(`singleton = 1`, `body` JSON 객체 + `updated_at` · `updated_by`). 행이 없으면 기본값이고, 저장 뒤 역할이 늘면 그 역할만 미설정으로 채운다(M3-07의 변이 주입 역할 추가 대비).
  - RPC: `settings.get {projectId}` → `{settings}`. `settings.update {projectId, patch, author}` → `{settings}`, `patch = { run?: {maxBudgetUsd?, maxTurns?}, roles?: {<역할>?: {model?, maxBudgetUsd?, maxTurns?}} }`(없는 키는 그대로, `null`은 미설정으로)이고 그 밖의 키(승인 대기 상한 · 잠정 승인 · 자동 모드 · 설치 허용 목록)는 스키마가 거부한다(`-32602`, 해당 화면 이슈가 키를 더한다). 사람 주체만 받고 에이전트 주체는 `-32020`(에이전트가 자기 예산을 바꾸지 못하게, ADR-047과 같은 이중 확인). 없는 프로젝트 `-32004`.
  - 검사: `settings.validateForRun {projectId, roles?}`는 오류가 아니라 값으로 돌려준다: `{ok: true}` 또는 `{ok: false, code: -32010, reason: 'SETTINGS_INCOMPLETE', message: '예산 · 모델 미설정', missing: [...]}`. `missing`은 `run.<필드>` · `roles.<역할>.<필드>` 경로를 실행 전체 → 역할 순서 → 필드(model · maxBudgetUsd · maxTurns) 순으로 나열한다. 실행 전체 한도는 항상 검사하고, 역할은 `roles`를 생략하면 M1 필수 역할 rule-writer · test-writer · implementer(`RUN_REQUIRED_ROLES`)다. 설정이 필요한 작업(실행 생성 #25, 규칙 자동 생성 세션 #21, 이후 planner · 채팅 · 변이 주입)은 오케스트레이터 내부 `requireRunnableSettings(store, roles?)`로 같은 검사를 하고 미설정이면 `-32010` 오류(메시지 "예산 · 모델 미설정", `data {reason: 'SETTINGS_INCOMPLETE', missing}`)로 거부한다. 통과하면 설정을 돌려주므로 실행의 예산 · 모델 스냅샷에 쓴다.
  - 검사 범위: M1은 rule-writer · test-writer · implementer만 필수다. planner · 채팅 값은 저장할 수 있지만 M1 화면에는 행이 없고(ADR-035, 로드맵 M4-01 · M5-01이 행과 검사를 연다), 변이 주입 역할은 `AgentRole`에 아직 없어 M3-07이 역할과 행을 더한다. 각 이슈는 자기 역할을 `roles`로 넘겨 검사한다.
  - 화면: 모달 틀은 공용 컴포넌트 `components/Modal`(820 × 600, 바깥 누르기 · Esc · ×, 초점 가두기, 닫으면 열기 전 초점으로 복귀, prototype-map.md 표 2)이고 내용은 `screens/settings-modal/`(prototype-map.md 표 1, ADR-044 경로 보정)이다. 왼쪽 섹션 목록은 "예산 · 모델" 하나뿐이고 나머지 섹션은 DOM에 없다. 열림 상태는 경로가 아니라 렌더러 모듈 메모리의 모달 상태다(모달이 현재 화면 위에 겹치도록, ADR-044의 톱니 → 경로 `settings` 부분을 바꾼다). 역할 행 이름은 화면 정의서 명칭(rule-writer · test-writer · implementer, ADR-009). 입력은 레이블만(자리 표시 글자 없음), 빈 필수 칸은 경고 테두리, 형식이 틀린 칸은 위험 테두리와 "입력 오류"(저장 요청 없음). [저장]은 보이는 칸 전부를 패치로 보내고 성공하면 "저장됨"과 함께 `validateForRun`을 다시 읽어 "설정 완료" · "예산 · 모델 미설정"을 보인다. 읽기 실패 "설정 불러오기 실패", 저장 실패 "저장 실패", 열린 프로젝트가 없으면 "프로젝트 없음" 한 줄(ADR-029 형식).
  - 프로젝트 ID: `src/renderer/src/project/ProjectContext.tsx`의 `useProject()`(값 없음이 기본)를 쓰고 #14가 값을 채운다. 그 전의 e2e는 앱 전체를 프로젝트와 함께 그리는 플레이그라운드(`e2e/playground/app.html`, ADR-048 방식)에서 연다.
- 결과: M1-05. #25는 `run.create`에서 `requireRunnableSettings`를 쓰고 `Run.budgetSnapshot`(지금 test-writer · implementer USD만)을 이 모델에 맞춰 정한다. #21은 rule-writer 세션 시작 전 `requireRunnableSettings(store, ['rule-writer'])`, #28 · #30은 `settings.roles[역할]`의 모델 · 한도로 세션을 연다. 실행 전체 한도를 역할 검사에서도 늘 요구하는 것은 보수적 선택이며, 채팅처럼 실행이 아닌 세션에서 빼야 하면 해당 이슈가 옵션을 더한다. 기각하면 `validateForRun`을 오류 응답으로 바꾸고 화면은 오류의 `data.missing`을 읽는다.
